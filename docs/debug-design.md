# 调试设计

本文记录模拟器运行时的调试指标、统计口径和接入顺序。测试套件的运行方法、判据和传输协议见[真机测试计划](hardware-testing.md)。外壳上常驻的信息见 [UI 布局](ui-layouts/index.md)。模拟目标与音画同步方式见[产品设计](product-design.md)，模块边界见[架构](architecture.md)。

外壳上的信息首先要回答游戏有没有按原速运行、声音有没有断、画面有没有及时显示，以及内存是否够用。CPU、PPU、JIT、显示或 SD 等环节的详细数据用于后续定位问题。速度正常不表示模拟正确，正确性仍由[真机测试计划](hardware-testing.md)中的外部判据检查。

## 游戏时常驻的信息

游戏页布局使用四组指标。表中的名称对应界面的英文标签。

| 面板 | 主值 | 空间足够时的附加信息 | 用途 |
|---|---|---|---|
| `SPEED` | 模拟速度，百分比 | `EMU` 产出帧率、`DRW` 首次显示的游戏帧率 | 判断游戏是否按原速运行，并区别模拟和显示问题 |
| `FRAME` | 每帧模拟工作耗时的 p95，ms | 平均耗时、有效样本数 | 发现平均值掩盖的偶发卡顿 |
| `AUDIO` | 待提交 PCM 队列剩余的声音时长，ms，数字前标 `BUF` | `U` 输出欠载次数，本窗口增量和累计值；`MIN` 本窗口最低水位 | 判断爆音、断音是否来自供数不及时 |
| `MEM` | 片内可分配空闲内存，KiB | PSRAM 空闲量，MiB；`IDLE` 两个核各自的空闲比例 | 避免 PSRAM 还有空间、片内内存却已经不足的误判，并看出哪个核还有余量 |

游戏页还常驻显示运行状态、执行后端、存档状态和未处理错误，显示方式见 [UI 布局](ui-layouts/index.md)。运行状态包括 `NO ROM`、`LOADING`、`RUN`、`PAUSE`、`TEST`、`ERROR`；后端标识中，`INT` 表示解释器，`JIT` 表示动态编译后端。暂停期间读数停在暂停前的值，`MEM` 照常刷新；继续运行或切换速度以后，新的统计窗口攒够数据之前保持原来的读数，载入新游戏时读数清空。

存档状态使用 `CLEAN`、`DIRTY`、`WRITING`、`ERROR`。只有所有尚未保存的修改都已按存档协议成功写入并完成刷新，才回到 `CLEAN`；写入期间又发生修改时，不能把新修改误标为已保存。失败状态保留到成功重试或用户明确处理，不被下一次普通状态刷新覆盖。

### 在不同尺寸的面板上取舍

| 布局 | 建议内容 |
|---|---|
| Sila P4 和 Sila P4X 屏幕两侧的四个窄格 | 主值和单位下面逐行列出全部附加信息 |
| JC1060P470 的一行四格 | 主值下方补一项：`EMU` 帧率、平均耗时、欠载次数、两个核的 `IDLE`。这一行放不下 PSRAM 空闲量，所以不显示 |
| Tab5 的 2×2 四格 | 在格子底行补充全部附加信息 |
| OSPTEK ESP32-P4C5、慧勤智远 ESP32-S31 CB 和乐鑫 ESP32-S31-Korvo-1 的 2×2 四格 | 格子比 Tab5 的窄，`MEM` 的底行左边是两个核的 `IDLE`，右边是 PSRAM 空闲量；其余三格和 Tab5 相同 |
| Waveshare ESP32-C5-Touch-LCD-2.8 | 没有 VFD，游戏页不显示这些指标，要看时用串口控制台的 `stat`。固件只把一半的帧交给显示（`GBX_DISPLAY_GAME_HALF_RATE`），原速时 `gap` 的平均值接近两帧的时长，约 33.5ms |
| 后续板子 | 按可用区域选择相同指标的紧凑或完整表达，不为每块板子重新定义统计口径 |

小面板不自动轮播数据，避免同一位置的数字忽然换了含义。`U --(+--)` 的括号外是欠载累计次数，括号内是最近统计窗口的增量；`N` 是帧耗时的有效样本数；`IDLE` 后面的两个数依次是 core 0 和 core 1 的空闲比例。各字段的稳定 ID、单位和枚举值保存在 [telemetry-fields.json](ui-layouts/telemetry-fields.json)，各板 `assets/ui/<板子>/board.json` 的 VFD 配置通过 `binding` 关联它们。

## 速度、帧率和时间的口径

### 模拟速度

`speed_percent = 100 × 本窗口推进的模拟时间 / 本窗口经过的宿主墙钟时间`。

模拟时间每跑完一帧才累加一次，所以窗口两端各取跑完某一帧时的累计模拟时间和当时的墙钟时间，不在 UI 的采样时刻读累计值，否则会差出最多一帧。模拟停住时，窗口终点改用采样时刻，速度随之下降。`EMU` 用 PPU 交付帧的时刻，按同样的办法计算。

模拟时间取所有设备共用的时间线，不按执行的指令条数计算，也不把宿主 CPU 利用率当成速度。KEY1 倍速下 CPU 每秒的周期数翻倍，但是 PPU 的帧周期不变，所以原速运行时 `SPEED` 仍然是 100%，`EMU` 仍然约为 60。暂停、加载和单步与连续运行分开统计。LCD 关闭时仍按设备实际推进的模拟时间计算速度。

### 三种帧率

| 指标 | 计数位置 | 不能拿来代替它的量 |
|---|---|---|
| `EMU`，模拟产出帧率 | PPU 交付完整游戏帧时 | 主循环次数、UI 重绘次数 |
| `DRW`，首次显示的游戏帧率 | 带有新游戏帧 ID 的缓冲首次成为显示扫描来源时 | `flush` 调用次数、UI 单独更新、同一游戏帧的再次扫描 |
| `SCAN`，显示扫描率 | 显示驱动的 VSYNC 计数 | 像素时钟参数推算值、示例宏中的“60Hz”名称 |

每个游戏帧都有单调递增的 ID，不能通过比较画面内容决定是不是新帧，因为静止的游戏也会正常产出帧。缓冲复制完成不等于新帧已经显示，见 [DSI/DPI 文档](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32p4/api-reference/peripherals/lcd/dsi_lcd.html)；显示后端无法确认实际切换时刻时，`DRW` 显示未采集。面板刷新率与模拟帧率不一定相同，所以重复扫描或 `DRW` 低于 `EMU` 本身不说明性能不足。显示统计分别记录按策略跳过、被较新帧替换、超时丢弃和重复扫描的次数，不只给一个总的 `DROP`。

### 每帧工作耗时

`FRAME` 统计模拟一帧的墙钟耗时：从开始模拟这一帧，到模拟的 PPU 结束这一帧为止，和 `EMU` 计数的是同样的帧。它包含模拟线程被抢占的时间，也包含渲染和混音的工作线程落后太多、模拟线程停下来等它们的时间；不包含为维持原速而主动等待，也不包含渲染器在另一个核上画完这一帧和等待屏幕扫描的时间。单核固件没有工作线程，渲染和混音在模拟线程上进行，所以都算在内。LCD 关闭等不能交付常规帧的状态另行标注，不混入正常帧耗时。

p95 是定位卡顿的指标，不是单独的通过标准，缓冲可以吸收短时波动，最终还要看速度、音频欠载和显示等待。原速下 `FRAME` 的平均值比一帧的 16.7ms 少得越多，模拟所在的核余量越大；另一个核上的渲染跟不跟得上，要看那个核的 `IDLE` 和画面交付间隔。

### 画面交付间隔

画面交付间隔是相邻两帧交给显示的时间间隔，统计 p95 和平均值，窗口和 `FRAME` 相同，只算同一速度下开始模拟的帧。原速下平均值接近 16.7ms；没有丢帧时，p95 因为交付时刻的抖动也会高于平均值，一帧没赶上交付时会出现约 33ms 的间隔。它判断画面是否连续，游戏页不显示，串口控制台的 `stat` 打印它（`gap`）。p95 使用固定窗口并显示样本数，样本不足时显示 `WARMUP`，窗口参数见 [telemetry-fields.json](ui-layouts/telemetry-fields.json)。加载新 ROM、切换后端、速度或统计模式时清空窗口。

详细诊断把一帧分成模拟 CPU 和设备推进、PPU 渲染、APU/混音、JIT 编译、ROM 缓存等待、格式转换/缩放/旋转、UI 绘制、等待空闲显示缓冲和主动节流等阶段。阶段可能嵌套或在双核上重叠，不能直接求和作为一帧时间。异步硬件任务要区分提交耗时和完成耗时。

### 核的空闲比例

`IDLE` 是本窗口里每个核运行自己的 idle 任务的时间占比，两个核分开显示，时间来自 FreeRTOS 的任务运行时间统计。PC 版取不到这项数据，显示 `N/A`。

### 2 倍速

2X 和 1X 分开统计，切换速度时各窗口重新开始。`SPEED` 的算法不变，跑满 2 倍时是 200%。`EMU` 把没有画出来的帧也计入，跑满 2 倍时约为 120；`DRW` 最多约为 60，因为 2X 只画屏幕能显示的帧。`FRAME` 每个模拟的帧都有样本，没有画出来的帧也算，跑满 2 倍时平均值不超过 8.3ms。2X 不生成声音。`AUDIO` 的主值显示 `OFF`，`U` 和 `MIN` 不采集，显示 `--`。

## 串口控制台

正式固件在串口控制台上接受几条命令，用来在板上试玩游戏，或者由电脑上的脚本重放一段按键并截图核对：载入 ROM 并选择后端、按时长按下和松开按键、打印游戏页的指标、截取游戏画面或菜单画布、静音、切换 1X 和 2X、读取和设置板上时钟、把卡上的文件取回电脑。命令和参数写在 `main/console.cpp` 的注释里，电脑上用 `tools/console.py` 收发和重放，见[工具说明](../tools/README.md)。重放用的命令文件和参考截图放在本地的 `roms/tests/`，不入库。参考截图是本模拟器的输出，只用来确认重放走到了预期的画面，不能当作正确性的判据。

`<板子>-profile` preset 编出打开 `GBX_PROFILER` 的 release 正式固件，只在做性能分析时构建。它同时打开 JIT 的计数器，耗时包含计数和采样的开销，所以前后对比的两边都要用这个构建。它在控制台上多出这些命令，写在 `main/profile.cpp` 里：

- `tasks` 统计各任务占一个核的比例，`prof` 在指定的核上定时采样被打断的程序地址，用 `tools/profile_report.py` 汇总。
- `stalls` 在指定的秒数里，CPU 每次等 GBA 的渲染线程时，打印之前约 140ms 里各任务占核的比例，以及最近 8 帧各自的渲染时间和各部分的指令数，用来分清是渲染本身跟不上，还是核 0 被别的任务占去了。
- `pstat` 统计呈现任务各部分的耗时，以及游戏帧的发布、覆盖和取走。发布或取走不等于完成显示。
- `cache` 读出缓存控制器的访问计数（两级缓存、两个核的指令和数据总线），`cacheprobe` 在核 1 上按已知的步长读内存，用来核对这些计数的含义，见 [ESP32-P4 的性能特性](esp32p4-performance.md)。
- `memory internal` 和 `memory psram` 列出片内或 PSRAM 堆里 1KB 以上的块，标出哪些是任务栈，再打印空闲量、开机以来的最低空闲量和各任务栈所在的内存与从没用到的字节数，用来找能挪动或缩小的内存。
- `stat` 多打印最慢的一帧、JIT 的累计计数和 JIT 走 C++ 慢路径的访存，字段写在 `components/app/src/app.cpp`。
- `record` 和 `play` 录制、回放每帧的按键，让两个后端以及改动前后使用相同的输入。回放从录制开始时的卡带 RAM 和 RTC 出发，不读也不写存档，结束时打印速度、欠载、帧耗时、JIT 计数和机器状态的 hash。同一段录制在两个后端上、在改动前后回放，hash 都应该相同。文件格式写在 `components/app/src/replay.h`。

## 详细性能诊断

### 宿主 CPU 和内存

| 项目 | 显示内容 | 注意事项 |
|---|---|---|
| 双核负载 | 每个核心的忙碌百分比、主要任务的运行时间与等待时间 | 按当前窗口的计数差值计算 |
| 片内内存 | 可分配空闲量、最大可分配块、观测到的最低空闲量 | “片内空闲”不等于芯片全部物理 SRAM 剩余量 |
| PSRAM | 可分配空闲量、最大可分配块、观测到的最低空闲量 | 总空闲量足够但最大块不足，仍可能分配失败 |
| 专用内存池 | JIT 代码池、ROM 缓存、帧缓冲、显示缓冲、音频缓冲和 UI 缓存的已用/容量 | 与所属 heap 的用量可能重叠，不能重复相加 |
| 栈 | 关键任务的最小剩余栈 | 按需低频采集 |
| 内存错误 | 最近一次分配失败的字节数、内存能力要求、调用模块 | 堆完整性检查和分配追踪按需开启，不默认每帧运行 |

内存查询区分片内、PSRAM 和可执行内存，能力集合重叠时不重复相加。接口见 [ESP-IDF heap 文档](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32p4/api-reference/system/heap_debug.html)和 [FreeRTOS 文档](https://docs.espressif.com/projects/esp-idf/en/v6.1/esp32p4/api-reference/system/freertos_idf.html)。

### JIT

JIT 诊断记录代码池用量、有效块数、编译块数与编译耗时、淘汰和失效次数，以及回退解释器的次数与原因，片内代码池和 PSRAM 的第二级分开记录。这些计数给出窗口增量和累计值，以便区别首次运行的正常编译和反复编译同一段代码。

“命中率”必须标明分母。编译块数的占比不代表执行占比，内存访问 helper 调用也不等于回退解释器。无法低成本准确采集执行量时，只显示编译、回退和失效次数。比较解释器和 JIT 时使用相同的 ROM、输入与统计区间，并写明冷热启动和是否清空了代码缓存。

### 显示

显示诊断包含 `EMU / DRW / SCAN`、丢弃与重复的原因、队列深度、最旧待显示帧的年龄、缓冲状态，以及转换、缩放、旋转、UI 绘制和等待可用缓冲的耗时，用来检查低频 UI 有没有意外触发整屏重绘。按复制计数算出的字节率只能叫逻辑复制量，不能标成实测的 PSRAM 带宽。没有外部测量手段时，不显示自动统计的“撕裂次数”。

### 音频

主面板的队列时长是已经生成、尚未提交给 I2S 的 PCM sample frame 数除以输出采样率，立体声的一组左右声道算一个 sample frame。它表示软件队列的水位，不是从按键到声音的总延迟。

欠载只统计正常播放时输出端需要数据却没有数据的情况，暂停和开始预填充期间不计。主动静音时输出端照常取数据，取不到仍然算欠载；游戏本身输出的静音 PCM 属于正常供数。

### ROM、SD、存档和 RTC

| 项目 | 显示内容 |
|---|---|
| ROM | 文件名、大小、校验标识、实际选择的 GB/GBC/GBA 模式、mapper/存档类型、加载状态 |
| ROM 缓存 | 全量加载或分页模式、容量与占用、缺页次数、预取次数、因缺页阻塞的耗时 |
| SD | 挂载状态、实际配置的总线宽度和时钟、读写延迟、最近错误码和重试次数 |
| 存档 | 脏数据是否尚未保存、最近成功写回时间、写入/刷新耗时、错误 |
| RTC | 模拟 RTC 的时间、宿主时间来源、是否可信、游戏时钟偏移 |

分页加载时优先记录缺页阻塞和尾延迟，因为高命中率可能掩盖少量很慢的读卡。不为显示命中率在每次 guest 访存上计时。存档错误提升到游戏页的状态提示。RTC 读到了数字不代表时间可信，日期非法、失电标志或时间来源缺失都要显示出来。

## 模拟状态和正确性调试

这些内容在暂停后按需查看，不常驻在游戏边上滚动刷新。CPU、设备和内存必须来自同一个暂停点或一致快照，附带 guest 时间、帧 ID 和快照序号；不能分别读取还在变化的字段，拼出硬件上不可能出现的状态。

| 类别 | 内容 |
|---|---|
| GB/GBC CPU | PC、SP、AF/BC/DE/HL、IME、IE/IF、HALT/STOP 与挂起状态、当前指令和映射到的 bank |
| GB/GBC 设备 | LY、STAT/PPU 模式和行内位置、LCDC、滚动与窗口寄存器、OAM DMA、CGB VRAM DMA、DIV/TIMA/TMA/TAC、速度切换、MBC bank、RAM 使能和 RTC 状态 |
| GBA CPU | R0–R15、CPSR、当前模式与 ARM/Thumb 状态、对应的 banked registers/SPSR、中断请求和屏蔽、当前指令 |
| GBA 设备 | VCOUNT/DISPSTAT、显示模式、背景与窗口、混合、DMA/定时器运行状态、WAITCNT/预取、声音 FIFO 和卡带存档接口状态 |
| 图形检查 | 原始 framebuffer、tile map、tile、OAM、调色板及像素来源；所有视图来自同一快照 |
| 内存与追踪 | 按需查看的地址范围、断点/观察点、最近的指令或总线事件；固定容量、有限时间窗口 |

寄存器和时序的含义以 [Pan Docs](https://gbdev.io/pandocs/) 和 [GBATEK](https://problemkaputt.de/gbatek.htm) 为准，这里只列要观察的状态。GBA 中正常发生的未定义指令异常等 guest 行为，要和模拟器尚未实现某条指令或内部断言失败区分开。

解释器和 JIT 对照出错时，报告第一处差异的 guest PC、指令、寄存器、内存或总线事件，以及对应的模拟周期，不只保留最终整帧不一致。两边一致也不能自动称为正确。

测试状态显示套件、用例 ID、当前后端、执行/传输进度、超时或通信错误，以及判定和判定方。判定尚未完成时显示 `PENDING`，缺少 JIT 运行结果时显示 `NOT RUN`。批量测试不使用游戏页的原速告警。

## 硬件诊断和运行记录

硬件信息包括板型、芯片修订、固件 Git 版本与 dirty 标志、构建 preset、ESP-IDF 版本、CPU/PSRAM 时钟、PSRAM 容量、显示驱动与时序、启用的后端及采样选项，配置值和实际测量值分别标注。性能报告带上这些信息，避免把不同芯片配置的结果混在一起比较。

输入诊断记录原始触点、转换后坐标、物理与虚拟按键，以及输入事件到模拟侧收到状态的时间。这个时差只表示软件输入路径，不是按键到画面的完整延迟。触摸 I2C 错误和断连需要计数，尤其要检查方向键和 A/B 同时按下时是否丢失状态。

电压、电流、电量、充电和温度按板级能力显示。没有可靠读数时显示 `--`，确认不支持时显示 `N/A`，不能用无电池时的采样值或未经验证的换算推断电量。

最近事件记录类别、错误码、宿主时间、guest 时间或帧 ID、发生次数和简短上下文，重点保留显示提交失败、音频欠载、SD 错误、存档失败、输入断连、内存分配失败、模拟器断言及测试差异。崩溃上下文只有被日志或转储保存后才能恢复，不假设重启后 PSRAM 中的记录还在。

## 采样、告警和开销

主界面低频更新，采样窗口和刷新参数见 [telemetry-fields.json](ui-layouts/telemetry-fields.json)。任务列表、栈和完整 heap 信息按需读取。错误事件及时进入队列，输入采样和音频供数保持各自的实时节奏，不跟随 UI 降频。

每个指标同时携带有效性和采样时间：未采集为 `--`，平台不支持为 `N/A`，过期为 `STALE`，不能统一显示 0。错误计数保留本次运行累计值，并显示最近窗口增量，避免一次短错误被平滑掉。

速度持续低于目标、音频水位持续偏离目标、缓冲积压和连续分配空间不足可以提示告警，阈值依据缓冲容量、目标节奏和实测抖动确定，不把宿主 CPU 利用率高直接标红。存档失败、分配失败和内部断言等明确错误立即标红并显示文字，不只依赖颜色。扫描重复和按策略丢帧默认作为中性统计。

各模块在帧、音频块、JIT 块和 I/O 完成等边界累计计数。每指令、每周期的路径不做堆分配、字符串格式化或虚调用。UI 读取采样任务汇总好的快照，不持锁阻塞模拟线程。追踪缓冲、帧耗时样本和事件队列使用固定容量，并统计因缓冲已满而丢弃的记录数。

游戏页上的常驻指标一直采集，不能关闭。详细性能诊断只编进 `GBX_PROFILER` 构建，通过串口控制台使用。追踪由运行时开关控制，现在只有测试使用。开关关闭时，每条指令、每次访存和每个周期都会走到的路径上，没有为诊断增加的判断；打开时换用带探针的实现，比如换一套总线函数，或者重新生成带探针的 JIT 代码。编译、失效和回退这类只在少数事件发生时才累加的计数一直统计。

打开开关以后，诊断工作尽量放在模拟所在的核以外。模拟所在的核上的探针只把定长记录写进固定容量的单生产者单消费者缓冲，缓冲满时丢弃记录并计数，不等待。测试采集使用同样的探针，但是不丢弃：测试记录是判定依据，记录不全的用例不能判为通过。汇总、格式化、编码和界面绘制都由另一个核完成。模拟所在的核仍然要承担写记录和复制快照的开销，另一个核变忙也可能拖慢渲染和混音，所以打开开关以后的影响以板上实测为准。

## 接入顺序

1. 显示验证阶段先接硬件/固件标识、VSYNC、帧缓冲状态、UI 绘制耗时、内存、触摸和错误记录。没有模拟器时，`SPEED` 和 `EMU` 显示未采集。
2. GB 解释器接入时增加模拟速度、帧耗时、后端、音频队列、欠载、ROM 和存档状态，形成游戏时的常驻信息。
3. 性能调试阶段增加阶段计时、每核负载和等待、显示队列、JIT 编译与失效、ROM 分页阻塞。寄存器和图形检查随各设备实现接入。
4. 测试执行协议接入后，增加用例进度、测试判定和解释器/JIT 差异报告。板级电源与传感器功能验证后，再显示相应测量值。
