# 任务 1-2：GBC 可玩版本

这是[路线图](../../roadmap.md#gbc) GBC 段里程碑 1 的第二个任务：加上 KEY1 倍速，让 GBC 游戏在板子上可玩，能在 GB 上运行的游戏可以选择在 GB 还是 GBC 上运行，并加上 LCD 颜色校正、CGB 的即时存档和 2X。界面的改动先用 `tools/ui/` 出效果图，再实现，效果图不需要用户确认。这个任务依赖 1-1。

开工时在[任务状态](status.md)里把这个任务标为“进行中”。

## 范围

倍速：

- 按产品设计“GBC”一节实现 KEY1 和 STOP 的速度切换。STOP 按 Pan Docs 流程图中 CGB 的分支处理。调度器的 `Tick` 已经能表示倍速下的 CPU 周期，见 `common/scheduler.h`。
- 解释器和 JIT 同时实现。JIT 在倍速时把块内的 M-cycle 按当前速度换算成模拟时间。速度只在 STOP 时切换，块在这里退出。速度切换让 CPU 停下的时间计入模拟时间。
- blargg `cpu_instrs` 和 `interrupt_time` 已经在测试索引里，依赖这个任务。AGE `speed-switch` 下适用于 CGB E 的用例要登记进索引，`caution` 目录除外。固定回归加入一个倍速用例，名单和理由写进真机测试计划。

界面设计：

- ROMS 列表中 CGB 标志第 7 位置位的游戏都能启动，包括 0xC0 的 GBC 专用游戏，底栏不再写 `GB MODE`。徽标仍然按卡带头显示，列表上不表示游戏会按哪种模式启动。
- PALETTE 增加 COLOR，选项是 GRAY、GREEN 和 COLOR，表示卡带插在 GB 上还是 GBC 上。选 GRAY 或 GREEN 时，黑白游戏和 CGB 标志为 0x80 的游戏按 GB 模式运行，用选中的颜色显示。选 COLOR 时，黑白游戏按 DMG 兼容模式运行，颜色由兼容调色板决定；0x80 的游戏按 CGB 模式运行。0xC0 的游戏不看这一项，总是按 CGB 模式运行。默认值是 GRAY，这样升级以后，原来就能启动的游戏仍然按 GB 模式运行。
- SETTINGS 增加颜色校正，选项是 OFF 和 ON，默认 OFF。SETTINGS 一共 6 行，行高从 24 像素改成 21 像素，一页放下，不滚动。
- 游戏运行中不能在 GB 和 GBC 之间切换。游戏按 GB 模式运行时，PALETTE 可以在 GRAY 和 GREEN 之间切换，COLOR 显示为灰色；按 CGB 模式或兼容模式运行时，PALETTE 整行显示为灰色。颜色校正在主界面里总是可以修改，因为 0xC0 的游戏总是彩色的；游戏中按 GB 模式运行时显示为灰色。修改颜色校正立即生效。
- CGB 模式和兼容模式的即时存档保存彩色缩略图，保存的颜色不经过校正，显示时按当前的颜色校正设置处理。GB 模式的缩略图仍然按当前的 PALETTE 上色。
- 机型灯表示模拟的机器：GB 模式点亮 GB 灯，CGB 模式和兼容模式点亮 GBC 灯。
- 效果图用 `tools/ui/` 生成。

运行和呈现：

- app 按 ROM 头和 PALETTE 的设置选择运行模式，运行模式在启动时确定。PC 版使用同样的规则。
- 呈现任务支持 CGB 模式和兼容模式的彩色帧，两种缩放方式都要能用。GB 模式的调色板处理不变。
- 颜色校正只在呈现时进行，作用于 CGB 模式和兼容模式的画面，默认关闭。Pan Docs “RGB Translation by CGBs” 只有定性描述，没有给出换算方法。依据用 [Handheld Color Space Project](https://github.com/Brankale/Handheld-Color-Space-Project) 中 Pokefan531 对一台 GBC 屏幕的测量：用 X-Rite ColorMunki Photo 在反射模式下测出白、黑、R、G、B 等颜色在 380–730nm 的光谱，以及 32 级的灰阶和各分量的阶梯。找到的其他 GBC 颜色校正公式是目测调出来的或者出处不明，而且来自模拟器，都不使用。
- 只用这份原始测量数据。本项目的脚本由光谱算出 RGB 到 XYZ 的矩阵和各分量的响应曲线，换算到 sRGB，生成 BGR555 的查找表；这个项目里的 shader 和推导出的参数都不用。数据只测了一台机器，作者标注为不完整、可能不可靠，以后还可能更新，所以按 `refs/README.md` 的规则固定到一个提交，加进两个 fetch 脚本和索引，仓库里只提交生成脚本和算出的表。白点用 D65 还是 D50、是否保留测得的黑电平，先生成对比图，看过以后由你决定，理由写在生成脚本里。Pan Docs 的定性描述用来检查结果。
- PALETTE 的 COLOR 和颜色校正写进设置文件，旧文件缺少的项用默认值。
- `record` 录下运行模式，`play` 按录下的模式运行。没有记录运行模式的录制按 GB 模式回放，这样 GB 段录的文件还能用来比较 GB 模式的速度。

即时存档：

- `Snapshot` 加入 CGB 的状态：WRAM 和 VRAM 的全部 bank、调色板 RAM、HDMA 的进度、速度模式和 KEY1，以及其他 CGB 寄存器。渲染核保存的帧改为彩色。
- 状态记录机型和运行模式，按架构的规则增加格式版本。运行模式和当前游戏不同的即时存档不读取，SAVE / LOAD 里说明原因。
- 按 4-1 的测试协议，从 1-1 的 CGB 测试 ROM 中选一组。存档时刻覆盖倍速运行中、HDMA 进行到一半和 DMG 兼容模式，后端组合覆盖“解释器存、解释器读”“JIT 存、JIT 读”和两种跨后端的组合。

2X：

- 2X 在 CGB 模式和兼容模式下都生效，KEY1 倍速打开时也能使用。
- `SPEED` 在 KEY1 倍速下仍然按原速计算，见调试设计。
- 用即时存档回到倍速游戏负载重的位置，按两个核的实测负载重新检查渲染、混音和呈现的分工。

## 约束

- GB 模式的行为、测试结果和速度不能因为本任务变差。
- 颜色校正和缩略图都不改变模拟结果。测试比对的帧不经过校正。
- 每条指令、每次访存的路径上不为本任务增加检查。
- 菜单、设置的读写和存档文件的工作不在模拟所在的核上运行。
- 改动解释器、设备执行代码或 JIT 运行时 helper 时，按 `cmake/core_layout.cmake` 的规则放置，检查 map 中的地址。

## 完成标准

- UI 布局文档有新界面的说明和效果图，`render_previews.py --check` 通过。
- 改动影响了哪些模块，就按[真机测试计划](../../hardware-testing.md#选择本次运行的测试)运行这些模块的 ROM，开发完就运行。STOP 的改动影响 CPU 执行，要运行对应操作码组的 SM83 单步用例。任务结束时做一次两种机型的全量回归：GB 段里程碑 2 和 3 的全部测试、1-1 的全部 CGB E 测试和这些倍速用例。两个后端都通过，结果一致，回退清单为空或者已经和用户确认。第一次运行 SM83 单步时，先按真机测试计划重新建立解释器的验证基准。测试时间在路线图的预算以内，超出时先和用户确认优化方案。
- 按[双后端优化要求](../../hardware-testing.md#每个任务的双后端优化)，用打开倍速和使用 HDMA 的本地 GBC 游戏分别分析和优化解释器、JIT，提交两边各自的优化前后数据和剩余瓶颈。游戏只用于本地的性能分析，规则同 GB 段 [3-4](../gb/task-3-4.md)。
- 选出的 CGB ROM 在全部存档时刻和四种后端组合下都按套件原来的判据通过，结束状态和不中断运行的结果相同。
- 用户按测试点在 JC1060P470 上试玩，至少包括一个打开 KEY1 倍速的 GBC 游戏和一个不开倍速的 GBC 游戏。黑白游戏和 CGB 标志为 0x80 的游戏，在 PALETTE 选 GRAY 或 GREEN 和选 COLOR 时都试玩。用相同的即时存档、输入和统计区间，在两个后端的 1X 和 2X 下记录 `SPEED`、`FRAME` p95 和音频欠载次数，以及板型、芯片修订和主频，每种配置测一轮。能不能达到原速和 2 倍速以实测为准；达不到原速时，先定位剩余瓶颈，再和用户商定下一步。
- 在 JC1060P470 上比较颜色校正打开和关闭时的呈现开销。运行模式和颜色校正的选择在重启以后保留。
- 开发过程中只构建要刷进板子的固件和 PC 的 debug 版。用户确认可以提交时，全部板子的正式固件和测试固件构建一次，没有新的警告。

## 实现与验证

都在 JC1060P470 上测量，芯片 ESP32-P4 v1.0，主频 360 MHz。测试 ROM 的速度取测试固件 `jc1060p470-test-release` 报告里的倍数，算法同 1-1。游戏的数字来自 `jc1060p470-profile` 固件回放同一段录制，这个固件带 JIT 计数和采样的开销。报告都在 `build/test-reports/` 下。

### 倍速

解释器的连续执行循环按速度编译成两份，`sm83_run_block` 保持原来的代码，只在原速下运行，倍速用 `sm83_run_double_speed`，调用方按当前速度选择。JIT 的块里仍然按 M-cycle 计数，同步时间时按 `Context::mcycle_shift` 换成 tick。切换速度时 CPU 停下的长度，以及 DIV、定时器、串口和 DIV-APU 停止、恢复的时刻，在 PC 上按 AGE 的 `lcd-align-ly-cgbE`、`spsw-tima-cgbE`、`spsw-div-cgbBCE` 和 `spsw-ch2-lc-delay-cgbBCE` 搜索确定，依据写在 `Memory::switch_speed()` 和 `Apu::align()` 的注释里。只用于 CGB 的函数按 `tools/link_core_layout.py` 的名单排在 GB 的热代码后面。

没有建模的：按 AGE `lcd-align-ly-cgbE` 和 `ly-cgbE` 的源码，CGB E 第 153 行的 LY 比 DMG 多保持一段时间，读 LY 时还有 `LY & (LY+1)` 的毛刺，所以这两个用例在 PC 测试程序上不通过。它们不在测试索引里，也不在本任务的完成标准里。AGE 的 `oam-read`、`stat-int` 和 `halt-m0-interrupt` 在 DMG 模式下本来就不通过，mode 0 中断比实机早约 3 dot，这几个用例不在 GB 段的测试范围里，没有处理。

| 优化前 | 12.919 / 23.041 / 64.891 ms | 8.384 / 17.904 / 58.318 ms |
| UI 复制按列写 | 10.764 / 12.077 / 19.514 ms | 6.935 / 10.461 / 19.973 ms |
| HBlank DMA 按块写 | 10.262 / 11.833 / 18.698 ms | 6.304 / 10.516 / 19.846 ms |

UI 复制。优化前解释器的大部分帧在 10–12 ms，但是有 80 帧在 26 ms 以上，最慢的 64.9 ms，这些帧执行的指令数和其他帧一样。慢帧大约每 57 帧出现一次，也就是墙钟的每秒一次，和游戏页每秒重画一次指标的时刻对得上。把重画的周期临时改成 10 秒以后，慢帧也变成每 10 秒一次，解释器回到 99.5%，欠载 7 次。`tasks` 显示 core 1 上只有模拟任务，采样显示 core 1 的空闲时间正好是节奏控制的等待，所以慢帧期间模拟一直在运行，只是变慢了。原因在 core 0：JC1060P470 的面板转了 270 度，小的 UI 矩形由 CPU 按 UI 的行复制，每个像素写到不同的缓存行，`pstat` 的复制与旋转耗时是 113.1 ms/s。改成按 UI 的列复制，也就是 CPU 显示后端原来的写法，两个后端共用 `put_rect()`。5 秒里同样是 5 次重画、38 个矩形、391,248 个像素，耗时降到 7.3 ms/s。这个改动对 GB 模式同样有效。

HDMA。HBlank DMA 和 GDMA 原来逐字节经过 `peek()` 读源、经过 `Ppu::write_vram()` 和 `Ppu::change()` 写目标。优化前的解释器采样里，`copy_block` 1.8%，`write_vram` 1.5%，`peek` 1.3%，`Ppu::change` 2.1%（也包括 CPU 写 VRAM）。HDMA1 到 HDMA4 丢掉低 4 位，所以一块 16 字节总在源的同一页、VRAM 的同一个 128 字节页里：源是可以直接访问的页时一次复制，HBlank DMA 的一块在同一时刻写入，只有第一个字节走原来的路径，PPU 在 mode 3 时其余字节也照原样记录。即时存档里不对齐的 HDMA 地址视为损坏。改完以后解释器 1X 的采样里，这条路径从约 6.7% 降到 1.6%（`copy_block` 0.7%，`write_vram` 0.7%，`Ppu::change` 0.2%），JIT 1X 时 `copy_block` 占 core 1 的 0.5%。上表只回放了一次，最终固件上解释器又回放了 3 次，run 平均在 10.42 到 10.78 ms 之间，所以解释器这一行的差别在多次回放的波动以内；JIT 的 run 平均是 6.24 ms，和表里的 6.30 ms 接近。

2X，同样的录制和固件，两项优化以后：解释器 163.8%，FRAME p95 12.2 ms；JIT 197.9%，FRAME p95 10.9 ms。2X 不生成声音，不计欠载。

两个核的分工。JIT 1X 时 core 1 空闲 53.1%，其中包括代为转换显示帧的 7.3%（`convert_step`）；core 0 空闲 69.0%。解释器 1X 时 core 1 空闲 32.1%，core 0 空闲 60.1%，其中 `convert_step` 转换显示帧占 7.6%。1X 时两个核都有余量；2X 时解释器的 core 1 已经不够用，不能再往上面放工作。所以渲染、混音和呈现的分工不变：JIT 1X 时显示帧的转换仍然交给 core 1，解释器和 2X 时留在 core 0。

这两项优化以后剩余的瓶颈如下。之后 JIT 又改过一轮，结果见“Shantae 的人物和 bank 切换”。

- 解释器 2X 只有 163.8%，模拟本身就超过了 2X 的帧时间：run 平均 10.2 ms，2X 每帧只有 8.4 ms。1X 的采样里 `sm83_run_double_speed` 和倍速的 `block0` 合计占 core 1 的 49.7%，`Memory::map` 2.0%，`Scheduler::dispatch` 1.7%，其余每项都在 1.5% 以下。剩下的主要是逐条解释 Shantae 等 VBlank 时的随机数循环。
- JIT 2X 是 197.9%。1X 回放里最慢的帧仍然落在每秒重画指标的时刻：JIT 约 14 到 20 ms，其他的帧大多在 6 到 8 ms；解释器约 16 到 20 ms，其他的帧大多在 10 到 12 ms。2X 时 JIT 的 run 最大是 18.3 ms，而 2X 按墙钟控制节奏，慢帧欠下的时间不补。core 1 上 `update_deadline` 3.4%、`Sm83Jit::execute` 3.8%、gateway 的慢路径约 3%、`Memory::map` 1.9%，后者来自每帧约 51 次 ROM bank 切换和 22 次 SVBK 切换。这段录制里 JIT 编译了 863 个块，淘汰 1,004 次，从第二级恢复 221 次。
- core 0 上 CGB 的渲染（`segment_cgb` 和 `consume`）约 10%，混音约 5%，没有成为瓶颈。

### Shantae 的人物和 bank 切换

用户试玩时发现，Shantae 开始游戏以后，人物走出房间就不显示了，并在槽位 1 存了这个位置；用户还看到 2X 时 core 1 只剩 17% 空闲。用串口的 `file` 命令把槽位文件取到电脑上，在 PC 测试程序上用解释器读档，同样看不到人物，所以问题不在 JIT。

原因在 PPU。Shantae 的 STAT 中断用 LY=LYC 分割画面，LYC=0 时的处理程序在 0x0ABC，它打开 OBJ，把 LYC 设成状态栏所在的行；处理程序里还有一个关掉 OBJ 的分支。我们的 PPU 在第 153 行 LY 变成 0 时请求了一次 LYC=0 的中断，进入第 0 行时又清掉 LY=LYC、在 mode 2 重新比较，STAT 中断线再升一次，所以同一帧请求了两次。处理程序一直运行到第 6 行，返回以后马上响应第二次请求，这一次走的是关 OBJ 的分支，这一帧就没有画精灵。

`ppu.cpp` 改成进入第 0 行时保留 LY=LYC，因为 LY 从第 153 行起已经是 0，STAT 中断线一直是高电平，不会再有上升沿。第 0 行的 OAM 中断沿事件也只在 mode 2 中断源打开时才安排。依据是 Gambatte 的 `lyc0int_m0irq_1` 和 `lyc0int_m0irq_ds_1`：在 dmg08 和 cgb04c 上，第 153 行的请求以后，到第 1 行的 mode 0 之前没有新的 STAT 请求。ares 的 [#60](https://github.com/ares-emulator/ares/issues/60) 报告过同样的症状，“invisible character sprites”，由 LY 和 STAT 中断时序的修正 [d50e9d2](https://github.com/ares-emulator/ares/commit/d50e9d2f5db0d3b7adfeed0a1331a0a479f55464) 修好。

PC 测试程序上，Gambatte 按文件名给出期望值的用例在 CGB 上有 3,020 个，通过 1,773 个，DMG 上有 1,644 个，通过 1,112 个，两个数都和改动前相同。`lyc0int_m0irq_1` 和 `_ds_1` 改为通过，同一目录的 `_2` 和 `_ds_2` 改为不通过。后两个在第 1 行 mode 0 开始以后读 IF，期望看到 mode 0 的请求，我们在这个时刻还没有请求；改动前它们能通过，是因为第 0 行多出来的那次请求已经置位了 IF。改动前就不通过的 `lycint152_m0irq_2` 也是在 Gambatte 期望看到第 1 行请求的时刻还没有请求。这个时序没有处理，Gambatte 也不在测试索引里。另外 `frame1_m2stat_count_ds_1` 的输出变了，改动前后都不通过。

修好以后，PC 上从槽位 1 读档，人物正常显示；板上两个后端读同一个槽位，截图里人物也都在。

性能。Shantae 每帧切换约 51 次 ROM bank、22 次 SVBK，HBlank DMA 约 78 块（见“游戏的负载”）。原来每次映射变化和每次 VRAM DMA 让 CPU 停下，JIT 的批次都要停下回到 `System`，映射变化还让整张分发表失效。这一轮改了 JIT 的运行时，对所有游戏都起作用，没有针对 Shantae 的特殊处理：

- 映射变化以后，下一次取指先检查被换掉的窗口里有没有正在运行的块，有就停下，没有就在新的映射下接着在原生代码里运行。追踪运行仍然停下。
- 分发表的标签改成目标 PC 和目标所在窗口的 bank，`Memory::code_tags` 随映射更新，所以 bank 换回来以后原来的表项还能用。
- VRAM DMA 让 CPU 停下以后，批次接着运行。
- 批次的上限原来是 1024 个 M-cycle。只把上限提高到 16384 时，blargg `cpu_instrs` 的 JIT 从 16.06 倍降到 13.77 倍（测试固件，报告 `bisect-chain1024` 和 `shantae-legs-gb-speed`），因为推迟的事件要等批次结束才一起派发，扫描线成批交给另一个核，模拟所在的核要等渲染。所以批次每运行 1024 个 M-cycle 就回到 C++ 派发推迟的事件，然后接着运行，最多运行 65536 个 M-cycle 才返回。第一版在每段结束时把已经连接过的出口又连接了一次，重复的连接记录在块回收时留下了悬空的写入，dmg_sound 在板上崩溃；现在只连接仍然指向公共出口的连接字。
- `Memory::map` 换 ROM bank 时只改页的读指针。没有 OAM DMA 和追踪时，SVBK 直接改写 D000–DFFF 和回显区的页。

### 颜色校正

数据来自 Handheld Color Space Project 中 Pokefan531 的测量，提交 `66b7f4c`，由两个 fetch 脚本下载到 `refs/docs/gbc-lcd/`。`tools/lcd_colors.py` 用 colour-science 0.4.6 处理：440 nm 以下的读数无效，按 440 nm 的值补齐；两个角度取平均；光谱按 D65 积分；三原色按比例缩放，使它们相加等于白；各分量的响应取各自的阶梯。脚本加 `--compare` 生成对比图，按图选的是：

- 白点：屏幕的白在 D65 下是 xy (0.299, 0.324)，比 D65 偏蓝偏绿。直接显示时浅色都带青色，Pan Docs 的例子 `$03EF` 成了浅绿；按 D50 积分则偏黄绿。看反射屏的人会适应屏幕的白，所以用 Bradford 把屏幕的白适应到 D65。适应以后 `$03EF` 是 Pan Docs 说的淡而发灰的黄色，颜色饱和度低的特点保留下来。适应以后光源的选择影响很小，选 D65。
- 黑电平：屏幕黑的反射是白的 28%，保留的话每个暗色后面都垫着一层灰，所以扣掉，黑显示成黑。

app 在启动时按生成的参数算出 32768 项的 BGR555 到 RGB565 表，放在 PSRAM。

呈现开销用同一段录制回放，SCALING 是 SMOOTH，`pstat 5000` 取计时段中间的 5 秒，固件是 `jc1060p470-profile`。解释器原速时转换在 core 0 的呈现任务里：颜色校正打开和关闭时，画游戏帧的耗时是 214.1 和 228.1 ms/s，每帧 3.58 和 3.82 ms；core 0 的采样里 `convert_step` 占 7.6% 和 8.0%。JIT 原速时转换交给 core 1：打开时是 185.0 ms/s；关闭时测了两次，503.1 和 197.7 ms/s，第一次多出来的是等 core 1 上的转换任务的时间，不是转换本身。查表和原来按位换算的开销没有测出差别。

设置在重启以后保留：在正式固件上把 PALETTE 选成 COLOR、COLOR FIX 选成 ON，重新烧录固件让板子重启，SETTINGS 里仍然是这两项。检查完已经改回 GREEN 和 OFF。

### 即时存档

状态格式升到第 3 版，系统字段区分 GB 模式、CGB 模式和兼容模式，CGB 的两种模式在 DMG 的字段后面接着保存 CGB 的状态。槽位文件升到第 2 版，记着运行模式，缩略图在 GB 模式下是 5,760 字节的灰阶等级，在两种彩色模式下是 46,080 字节的 BGR555。旧版本的状态和槽位文件不读，按“不做”一节不做迁移。

测试协议升到第 9 版，存档时刻的等待条件加上倍速运行中和 HBlank DMA 进行中。CGB E 选了 5 个 ROM：`spsw-tima-cgbE` 在切换速度的停顿中、CPU 醒来以前存档，`interrupt_time` 在倍速运行中存档，SameSuite `hdma_mode0` 在 HBlank DMA 进行中存档，cgb-acid2 和兼容模式的 dmg-acid2 在判定的那一帧画到一半时存档。`gbc-1-2-final-states` 里两种机型 13 个 ROM、56 次读档都通过，结束状态和不中断运行的结果相同，四种后端组合都在里面。开发中还在 PC 上对 6 个 CGB 存档时刻做了存档、解码、恢复再运行到结束的比较，结果都相同。
