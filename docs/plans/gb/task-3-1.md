# 任务 3-1：APU 和 MBC3 RTC

这是[路线图](../../roadmap.md)里程碑 3 的第一个任务：在模拟核心里实现 DMG 的 APU 和 MBC3 的 RTC，并把 `dmg_sound`、`rtc3test` 和 `mbc3-tester` 接进板上的测试通路。APU 按输出采样率生成 PCM，CPU 能读到的状态在 CPU 所在的核上计算，声道合成和混音按双核分工放在 PPU 渲染所在的核上。RTC 在运行时按模拟时间推进。解释器和 JIT 同时实现。板上的音频输出在 3-2，RTC 状态的保存和补算在 3-3。

开工时在[任务状态](status.md)里把这个任务标为“进行中”。

## 范围

APU：

- 四个声道：CH1 的 sweep，CH1 和 CH2 的占空比，CH3 的波形 RAM 和输出电平，CH4 的 LFSR。每个声道的 length timer、envelope、触发和 DAC 开关，以及 NR50、NR51 的混音和 NR52 的总开关。声音寄存器的读写屏蔽已经在 2-1 实现。
- frame sequencer 由 DIV 的计数位驱动，写 DIV 和 STOP 对它的影响按 Pan Docs “DIV-APU”一节实现。DMG 特有的行为按“Obscure Behavior”一节和 `dmg_sound` 各子测试覆盖的内容实现，包括 CH3 播放时读写波形 RAM、APU 关闭期间写 length 计数器，以及触发时 length 和 sweep 的细节。
- CPU 能观察到的状态在 CPU 所在的核上按访问时刻计算，比如 NR52 的声道状态位、length 到期、sweep 溢出关闭声道，以及 CH3 播放时读到的波形 RAM。这部分用 2-1 的事件和追赶方式实现。
- 波形合成、混音和重采样放在 PPU 渲染所在的核上。CPU 所在的核把声音寄存器和波形 RAM 的写入、触发连同模拟时刻放进任务，另一个核只根据任务生成 PCM。APU 和 PPU 共用这个核上的工作线程时，要说明两种任务怎么排队，以及队列满时谁等待。
- 系统接口增加取得立体声 PCM 的方式，以及小幅调整重采样比例的接口，3-2 用它按音频缓冲的水位控制运行节奏。输出采样率由调用者给定。

MBC3 RTC：

- S、M、H、DL、DH 寄存器的选择、读写和有效位，latch 的 0 到 1 写入序列，DH 的 halt 位和 day carry，越界值的计数和回绕。写各个寄存器对秒以下计数的影响按 `tests.md` 的“Sub-second writes”一节实现。
- RTC 按模拟时间推进，由模拟时钟折算出 32768Hz 振荡器的计数。依据是 `tests.md`：rtc3test 用 GB 的定时器和 DIV 给 RTC 计时，tick 间隔的容差是 1ms，sub-second 测试的容差是 1.5ms。
- `mbc3-tester` 的 ROM 是 4MiB，卡带类型为 0x11，DMG 参考图上 256 个 bank 全部通过，所以 4MiB 的 MBC3 卡带要按 MBC30 使用 8 位的 ROM bank 号。MBC30 的识别方法和 RAM bank 的处理按 Pan Docs “MBC30”一节实现，依据写进注释。
- 系统接口增加读取和设置 RTC 完整状态的方式，包括秒以下的计数、halt 和 carry，以及把一段经过的时间加到 RTC 上的接口。状态取出再写回以后，RTC 不能多走或少走。

测试通路：

- `tools/prepare_gb_tests.py` 加入 `rtc3test`、`mbc3-tester` 和它们的 DMG 参考图。
- 测试索引加入 `dmg_sound`，按套件说明运行 36 秒模拟时间以后比对画面；加入 `mbc3-tester`，运行 40 帧以后比对画面；`rtc3test` 的三个子测试各占一项，先按套件说明的按键选择子测试，再按规定的模拟秒数运行，最后和对应的参考图比对。排错时可以单独运行 `dmg_sound/rom_singles` 下的 ROM，它们的结果不计入通过。
- 测试协议支持按键脚本：索引记录每次按下和松开的按键及模拟时刻，测试固件在两个后端上按相同的模拟时刻提交。测试开始时 RTC 的初始状态固定，写进索引。
- 结束状态加入 PCM 输出的摘要，两个后端的摘要必须相同。

## 不做

- I2S 输出、音频缓冲和节奏控制，这些在 3-2。
- RTC 状态的保存、读取板上 RTC，以及补算关机和暂停期间的时间，这些在 3-3。
- 真实时间等待。`rtc3test` 和其他 ROM 一样按模拟时间运行。
- CGB 的声音差异、PCM12 和 PCM34 寄存器，以及 `cgb_sound`。

## 约束

- APU 和 RTC 都不逐个周期推进。CPU 访问声音寄存器、波形 RAM 或者选中的 RTC 寄存器时，先把相应的设备推进到这次访问在 M-cycle 内的准确时刻，JIT 访问这些地址时不能走快速访存。切换 RAM bank 和 RTC 寄存器按 2-3 的映射变化处理。
- 另一个核生成的 PCM 不能反过来影响 CPU 能观察到的状态。合成跟不上时，CPU 所在的核按 2-4 的规则等待，不丢弃任务。
- PCM 只由寄存器写入和它们的模拟时刻决定，和宿主耗时无关。两个后端，以及 `isolated` 和 `concurrent` 两种核安排，得到的 PCM 必须相同。PCM 摘要只用来比较两个后端，不把模拟器生成的 PCM 存成标准答案。
- 模拟核心不读取宿主时间。经过的时间只由调用者通过系统接口给出，所以两个后端得到的 RTC 状态必须相同。
- 按键脚本要保证 ROM 读取按键时按键确实处于按下状态，按下和松开的时刻、持续时长和依据写进索引。
- 新增的设备执行代码按 `cmake/core_layout.cmake` 的规则放置，改动以后检查 map 中的地址。
- 回退、测试时间和回传大小沿用 2-1 的规则。

## 实现与验证

APU、RTC、MBC30 和另一个核上的工作线程的模块边界见[架构](../../architecture.md#模拟器)，按键脚本、RTC 初始状态和 PCM 摘要的用法见[真机测试计划](../../hardware-testing.md#运行整机-rom)。测试协议升到 v5，字段布局在 `tests/protocol/rom_test.h`，索引升到 v5。

几项“由你决定”的选择如下，理由都写在代码注释里：

- CPU 所在的核保存 frame sequencer、length、CH1 的 sweep、NR52 的声道位和 CH3 读取波形 RAM 的时刻，另一个核保存波形、envelope、LFSR 和混音状态。声音任务是带模拟时刻的写入，后面跟着 CPU 所在的核推算出的声道关闭、sweep 周期和 envelope 步进。PCM 是交错的 16 位立体声，测试使用 48000Hz。
- 重采样把每次电平变化按它落在输出帧区间里的位置分摊到相邻两帧，相当于对每帧区间求积分；之后按 Pan Docs “Obscure Behavior”给出的电容保持率做高通滤波。
- RTC 的秒以下计数按 tick 保存，不换算成 32768Hz 的计数，所以取出再写回的状态精确到 tick。RTC 的初始状态是各计数为 0、正在计时、没有 carry。
- 卡带头声明的 ROM 超过 MBC3 能寻址的 2MiB（大小码大于 6），或者 RAM 超过 32KiB 时，按 MBC30 处理，ROM bank 号用 8 位。依据是 Pan Docs “MBC30”一节。`mbc3-tester` 的 ROM 是 4MiB、卡带类型 0x11，按这个规则识别为 MBC30。
- 按键脚本记录每次按下和松开的模拟时刻，索引用 0.25 秒开始、按住 0.1 秒、松开 0.1 秒的节奏，依据是 `rtc3test` 每帧读一次按键。

以下结果都来自 Sila P4，ESP32-P4 v1.3、360MHz、ESP-IDF v6.1，构建 preset 为 `sila_p4-test-release`，模拟机型 DMG-C，使用 `isolated` 调度：两个后端依次在 core 1 执行，渲染和混音在 core 0。固件包含本任务的改动。

`dmg_sound`、`mbc3-tester` 和 `rtc3test` 的三个子测试在两个后端上都通过，两边的 CPU 状态、模拟时间、内存摘要、帧、PCM 摘要和结束时的 RTC 状态都相同。sub-second writes 在运行中做了 70 次 RTC 状态取出和写回，仍然和参考图一致。这 5 个 ROM 加上 `cpu_instrs` 和 `dmg-acid2`，在 `concurrent` 调度下的结果和 `isolated` 下逐项相同，包括 PCM 摘要。锁步诊断交出声音任务的时机和正常运行不同，`div_write` 在两种运行方式下的 PCM 帧数和摘要也相同。

全量运行选中 130 个 ROM，129 个通过，`oam_bug` 和以前一样只记录结果，JIT 没有回退。整次运行的墙钟时间是 98.0 秒，预算 300 秒。`run_jit.py` 的全部检查通过。`dmg_sound/rom_singles` 只用于排错，不在全量运行里；PC 解释器上 12 项都报告“Passed”，板上运行过其中 01 和 10 两项，两个后端的画面上也都显示“Passed”。第一次连续运行这两项时，电脑正在同时编译固件，第二项的结果收到以后出现了传输超时；电脑空闲时重跑两项都正常完成，原因未确认。

本任务没有修改 SM83 的指令语义和平坦总线，改动集中在 IO 寄存器的处理、`System` 的运行循环和设备代码，所以没有运行 SM83 单步测试。

本任务构建过 Sila P4 的 `test-release` 和 `test-profile`，以及 PC 的 GUI 和无窗口 debug 构建，没有新的警告。JC1060P470 和 Tab5 的正式固件和测试固件，共 8 个 preset，在最后一次改动之前也编译通过，没有警告。最后一次改动只恢复了 `System::run` 中一行对执行批次的截断。PC 上 MSVC 报出的警告都在本任务之前已有的代码行上。

## 性能分析和优化

测量条件和上一节相同。速度是模拟时间除以执行时间，执行时间包括冷缓存编译和等待已经提交的渲染、声音任务完成，不包括取走 PCM 和计算摘要。性能分析版固件的数字含采样开销，只用来看分布。

### 新增 ROM 的速度

| ROM | 解释器 | JIT | 解释器耗时，秒 | JIT 耗时，秒 | PCM 帧数 |
|---|---:|---:|---:|---:|---:|
| `dmg_sound` | 4.20× | 15.13× | 8.573 | 2.379 | 1728000 |
| `mbc3-tester` | 3.83× | 15.36× | 0.262 | 0.065 | 48218 |

### 对已有 ROM 的影响

开工前的固件来自同一提交，在同一块板子上运行原来的 125 个 ROM，和本任务完成后的全量运行比较。解释器各 ROM 速度比的几何平均是 0.990，执行时间合计从 36.69 秒变成 37.02 秒；JIT 的几何平均是 0.969，执行时间合计从 13.26 秒变成 13.51 秒。JIT 速度比最低的 10 项都只运行 17–72ms，每项多用约 1–4ms；运行超过 200ms 的 10 项，速度比在 0.955–1.023 之间。

为了区分来源，把完成后的固件改成不生成 PCM（采样率为 0）再测一次。下表的速度依次是开工前、采样率为 0、48000Hz：

| ROM | 解释器 | JIT |
|---|---|---|
| `cpu_instrs` | 4.33× / 4.27× / 4.27× | 17.52× / 17.45× / 17.13× |
| `mem_timing-2` | 4.40× / 4.43× / 4.40× | 16.55× / 16.36× / 15.91× |
| `dmg-acid2` | 6.57× / 6.52× / 6.49× | 11.47× / 11.27× / 10.91× |
| `halt_ime0_ei` | 4.36× / 4.29× / 4.27× | 10.54× / 10.26× / 9.98× |
| `timer/div_write` | 3.07× / 3.00× / 3.01× | 5.24× / 5.06× / 5.06× |

JIT 的差距大约一半在采样率为 0 时已经存在，来自 CPU 所在核上的 APU 处理、两种任务共用工作线程，以及执行代码地址的变化；另一半随 48000Hz 输出出现，包括另一个核上的合成，以及测试固件在 CPU 所在核上取走 PCM。取走 PCM 的时间已经从执行时间中扣除，但它对缓存的影响没有扣除。几个短 ROM 每项多出的约 1ms 不来自最后等待声音任务完成：把这段等待移出计时只少了约 0.1ms。其余来源没有拆开测量。

### 优化过程

第一版实现在板上通过以后，先测了它的速度，再按性能分析的结果修改。保留的改动有三项。

测试固件原来用 SHA 引擎计算 PCM 的 SHA-256。性能分析显示它约 35MB/s，并且分块屏蔽中断：JIT 运行 `cpu_instrs` 时，CPU 所在核上的临界区和哈希合计约占 10% 的采样。PCM 摘要只用来比较两次运行，所以换成 128 位的非加密摘要，临界区的采样降到 0.5%。同一批修改还把 APU 读取模拟时间和写 DIV 时的处理改成内联：第一版的性能分析中，`div_write` 的解释器采样里 `Apu::restart_divider` 和 `Memory::next_div_edge` 合计约占 2.8%。这两项一起测量，`cpu_instrs` 的 JIT 从 16.84× 提高到 17.07×，解释器没有变化。`div_write` 不在这组测量里，和第一版相比，它从解释器 2.93×、JIT 4.78× 提高到 3.02× 和 5.05×。`rtc3test` range 的两个后端却从 20.63× 和 20.41× 降到 19.23× 和 19.05×，`dmg-acid2` 的 JIT 也从 10.53× 降到 10.31×。性能分析显示 range 运行时 core 0 已经饱和，CPU 所在的核有 28% 的时间在等待；用 SHA 计算摘要时，被扣除的那段时间里 core 0 还能追赶进度，计时可能因此少算了等待。`dmg-acid2` 没有做这项分析。

混音器原来每一帧都做两路高通滤波。声音不变时，电容的值经过一段时间就不再变化，之后每帧的输出都和上一帧相同，所以这时只复制上一帧，直到下一次电平变化。改动前后，板上 15 个代表 ROM 的 PCM 帧数和摘要都相同，PC 上 4 个 ROM 的 PCM 哈希也相同。结果如下：

| ROM | 改动前解释器 | 改动前 JIT | 改动后解释器 | 改动后 JIT |
|---|---:|---:|---:|---:|
| `rtc3test` range | 19.23× | 19.05× | 23.62× | 23.36× |
| `rtc3test` basic | 10.41× | 11.72× | 11.40× | 13.01× |
| `rtc3test` sub-second writes | 4.38× | 6.30× | 4.46× | 6.48× |
| `dmg_sound` | 4.20× | 14.54× | 4.21× | 15.12× |
| `dmg-acid2` | 6.30× | 10.31× | 6.49× | 10.93× |
| `mem_timing-2` | 4.42× | 15.46× | 4.42× | 15.89× |
| `cpu_instrs` | 4.28× | 17.07× | 4.28× | 17.15× |

另外，取走 PCM 时按段复制，不再逐帧复制。这一步在扣除的时间里，执行时间的测量看不出差别；性能分析中原来占 CPU 所在核 2.1% 采样的 `Mixer::read` 不再出现。

下面几项没有收益，已经撤销。前三项是同时改的，`rtc3test` range 的两个后端从约 21.5× 降到约 17.9×，`dmg-acid2` 的 JIT 从 10.72× 降到 10.37×，之后逐项恢复来定位：

- 去掉运行结束时的交出，声音任务只按间隔交出：恢复以后，range 从 18.58× 和 18.47× 回到 20.63× 和 20.41×。
- 每 2048 帧才取走一次 PCM：改回每段都取走以后，range 从 17.96× 和 17.76× 提高到 18.58× 和 18.47×。
- 声音任务提交时不唤醒工作线程：恢复唤醒以后，range 的变化在 1% 以内，`cpu_instrs` 的 JIT 从 16.31× 提高到 16.63×。在最终的代码上单独再试一次，10 个 ROM 的速度变化都在 ±1% 以内。
- 去掉运行循环在交出时刻对执行批次的截断：在去掉运行结束交出的那组试验里，`cpu_instrs` 的 JIT 从 16.93× 降到 16.31×。最终的测试运行里每段都在交出间隔之内结束，截断不会发生。
- 把取走 PCM 和计算摘要放到 core 0 的传输任务里：core 0 的临界区升到 7.4%，渲染跟不上，CPU 所在核有 12% 的时间在等待，JIT 运行 3 个 ROM 时丢了 PCM 帧。

### 剩余瓶颈

`rtc3test` range 这类大部分时间在 HALT 里的 ROM，CPU 所在的核跑到 20 倍以上原速，这时 core 0 几乎没有余量：渲染和它的 memcpy 合计约 68%，CPU 所在的核有 15% 的时间在等工作线程。下一步应该先减少渲染每行的开销，混音只占 8%。

JIT 在已有 ROM 上仍比开工前慢 3.2%（几何平均），一半与是否生成 PCM 无关，具体来源还没有拆开测量。

## 审查后的修正

完成以后的三轮代码审查一共指出了 8 个问题，都已经修正：

- `set_rate()` 和 `set_speed()` 原来不先补上已经过去的 frame sequencer 步进。`step_block()` 结束时不交出声音，如果这时调整采样率或速度，之后才补进的 envelope、sweep 事件时刻反而更早，批次里的时间顺序就乱了。现有的调用方不会遇到这种情况。现在两者都先同步。
- 写 NR43 原来只在触发时检查 shift 14 和 15。Pan Docs NR43 一节说这两个值让 LFSR 停止移位，现在 CH4 播放时写入也会停下，改回其他值时恢复。恢复后第一次移位的相位没有资料，取写入后一个完整周期。
- Pan Docs Audio details 的“Pulse channels”和“Obscure Behavior”说，APU 上电后 CH1、CH2 第一次触发时，第一个 duty step 输出 0。原来直接按 duty 表输出，25% 和 50% 会马上输出音量。复位时，启动 ROM 留下的 NR52 表明 CH1 已经触发过，CH2 按上电后还没有触发处理。
- 播放中改写 NR11、NR21 的 duty，原来要等下一个 duty step、envelope 步进或别的事件才重算输出，现在写入时就按新 duty 输出。Pan Docs 没有写 duty 改变什么时候生效，这是根据“Pulse channels”一节说输出由 duty step 的各位运算得到所做的推断。
- 复位原来不清理上一轮的输出，还没读走的帧和丢帧计数会带到复位以后。现在混音器处理到复位时记下位置，读取方跳过之前的帧，丢帧计数从 0 开始。这些帧占的缓冲位置要等读取方跳过以后才重用，因为读取方可能正在复制它们；第一版修正在复位后立即重用了这些位置，第二轮审查指出了这个竞争。
- 复位会丢掉还没交出的批次，其中的采样率和速度设置也一起丢了。按用户确认的做法，采样率和速度修正是宿主的输出设置，跨加载和复位保留：`Apu` 记住最近的设置，在复位批次里重新发送。`system.h` 原来写的“加载后默认为 0”已经改正。
- 混音器复位时原来保留采样率，复位批次恢复寄存器时，初始电平是否计入积分器，取决于混音器之前收到过的采样率。所以复位前是否调用过 `finish_audio()`，或者同一个系统是否运行过别的 ROM，都会让之后的 PCM 不同。现在采样率为 0 时电平变化直接计入积分器，采样率从 0 变为非 0 时，高通滤波的电容按已经充到当前电平处理；混音器复位时连同采样率一起清零，复位批次先恢复寄存器，再恢复采样率。这样复位以后的状态只由复位批次决定，加载 ROM 时也不会因为电容从 0 开始充电而出现一个台阶。

这些行为 CPU 读不到，没有测试 ROM 能检查。PC 上用一个不入库的临时程序检查：ROM 只运行 `JR -2`，程序直接写声音寄存器，再按 Pan Docs 的描述和接口说明检查 PCM、帧数和丢帧计数，共 14 项。修正前的代码有 13 项失败，修正后全部通过；剩下 1 项检查运行中关闭再打开采样率以后的帧数和电平，修正前也通过。

板上用修正后的 `sila_p4-test-release` 运行 `dmg_sound`、`mbc3-tester`、`rtc3test` 的三个子测试、`cpu_instrs`、`dmg-acid2` 和 `div_write`，条件同上。8 个 ROM 在两个后端上都通过，两边结果相同。`concurrent` 调度下的结果逐项相同，包括 PCM 摘要，`div_write` 锁步诊断的 PCM 也和正常运行相同。速度和修正前相比变化都在 ±1% 以内。第三轮修正前后，8 个 ROM 的 PCM 摘要逐项相同：测试固件在加载以后才设置采样率，高通滤波只看电平和电容之差，两者同时平移不改变输出。

和修正前相比，只有 `dmg_sound` 和 `cpu_instrs` 的 PCM 摘要变了。`cpu_instrs` 在 53.52 秒结束测试时先关闭再打开 APU，然后以 50% duty 触发 CH1。修正前第一个 duty step 输出高电平，约 12 帧；修正后这一步输出 0。此后高低电平切换的时刻相同，只是高通滤波的状态不同，数值略有差别。

修正后重新构建了 Sila P4 的 `test-release` 以及 PC 的 GUI 和无窗口 debug 构建，没有新的警告。执行代码段从 64974 字节变为 65664 字节，测试固件的应用镜像从 480144 字节变为 480848 字节。
