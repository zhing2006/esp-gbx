# 任务 5-2：JIT 代码体积和两级代码缓存

减小 JIT 生成的代码，并把 PSRAM 里的块副本改成可以直接执行的二级代码缓存。按顺序做四项：标志位活跃性，RVC 和 Zcb，Zba、Zbb、Zbs，两级代码缓存。最后比较两种配置：一种是片内代码池加 PSRAM 二级，另一种不用片内代码池，把这部分片内 RAM 配成 L2 cache。这个任务依赖 5-1。

## 范围

### 标志位活跃性

- 编译块时分析 H、N、C 在被覆盖之前会不会被读取，不会被读取的就不计算。Z 已经是按需计算的，沿用现有做法。
- 读取 F 的指令都算读取，比如 PUSH AF、ADC、SBC、DAA、条件跳转、RLA、RRA 和 CCF。离开原生代码的地方也算读取：每条指令开头的取指检查都可能转到慢路径，访存 helper 会回到 C++，还有出口、事件和中断引起的退出，以及从块中间恢复的入口。所以不能只看块里后面的指令读不读；离开原生代码时必须能得到完整的 F，可以在这些位置补算。

### RVC 和 Zcb

- 编码器支持 16 位的压缩指令，生成代码和 gateway 在能用的地方使用压缩形式。P4 的各个修订都支持 C 扩展。
- 连接字和其他发布以后还会改写的位置，保持固定长度和 4 字节对齐。安装时修补的调用在发布之前写入，只要求 2 字节对齐。分支回填按实际的 2 字节或 4 字节编码处理，并检查距离。顺序执行会经过的补齐位置要填有效指令。块副本和恢复时的修补遵守同样的规则。
- Zcb 先在板上核对再使用，见下一节。

### Zba、Zbb、Zbs

- 先在 Sila P4（v1.3）和 Sila P4X（v3.2）上逐条执行要使用的 Zcb、Zba、Zbb 和 Zbs 指令，核对结果，并确认不支持的指令会触发非法指令异常。现有的资料对不上：数据手册写 HP CPU 支持 “Zc extensions (Zcb, Zcmp, and Zcmt)” 和 Zb，没有区分修订；《ESP32-P4 Chip Revision v3.x User Guide》把 Zb 列为 v3.x 新增；IDF v6.1 只在 v3.x 及以上的修订把 `zcb` 加进 `-march`，任何 P4 修订都不加 `zba_zbb_zbs`（`components/soc/project_include.cmake`）。
- 按构建配置的芯片大版本选择：v1.x 的构建按 v1.3 的核对结果启用，v3.x 的构建按 v3.2 的结果启用。同一大版本的其他修订按相同处理，比如 JC1060P470 的 v1.0 和 v3.x 构建允许的 v3.1，这些修订没有单独核对。
- 候选的用法有：BIT、SET、RES 用 `bext`、`bset`、`bclr`，移位和旋转用 `rori`、`rol`，零扩展用 `zext.h`，地址计算用 `sh1add` 等。具体用哪些，按代码体积和实测结果决定。

### 两级代码缓存

- `store.h` 在 PSRAM 里保存的 ROM 块副本改成可以直接执行的二级代码缓存。块被片内代码池淘汰以后，下次就在二级里原地执行，不再先交给解释器；在二级里执行得多的块，在批次之间搬回片内。块在两级都没有时，仍然按现有的重装退避交给解释器。有片内代码池时，RAM 里的块仍然只在片内。
- PSRAM 和片内 RAM 的地址相距约 127MB，超出了 JAL 的 ±1MB 范围，二级里的块不能用现在安装时修补的 JAL 调用片内的 gateway。可以在 PSRAM 里放一份 gateway，也可以改用 `auipc` 和 `jalr`。块间连接的连接字保存的是绝对地址，不受距离限制。
- 淘汰、失效、bank 映射变化和复位时，指向两级的连接、动态目标分发表的表项和可以恢复的执行位置都要正确地撤销或者改指向，旧代码不能再被执行。
- 先在两种修订上核对 PSRAM 里写入的代码能够执行：执行权限，以及发布时写回数据缓存、作废指令缓存、执行 `fence.i` 的顺序和范围。依据写在可执行内存的实现里。
- 二级满了以后怎样丢弃、二级的容量是否调整、什么时候把块搬回片内，由你决定。容量和元数据的变化记入资源统计。
- 比较两种配置：一种是片内代码池加二级，L2 cache 保持 128KB；另一种的片内代码池为 0，全部生成代码在 PSRAM 里执行，RAM 里的块也在 PSRAM，原来代码池占的片内 RAM 改配成 L2 cache，用能装下的最大一档。按实测结果选择，由用户确认。选定的配置写进 P4 的默认配置。

### 测量

- 测量在 Sila P4 上进行。Zba、Zbb、Zbs 这一项另外在 Sila P4X 上测改动前后各一次；v1.3 没有启用这些扩展时，Sila P4 上不测这一项。两种配置在 Sila P4 和 Sila P4X 上都比较，因为选定的配置要写进所有 P4 板。
- 用 V-Rally Championship Edition 的两个即时存档测量，做法和 4-3 相同：构建 preset 为 `sila_p4-profile`，Sila P4X 用 `sila_p4x-profile`，用串口控制台载入 ROM，再载入槽位，之后不按键，用 `stat` 和 `tasks` 统计 10 秒。每做完一项都测量 JIT 的 1X 和 2X，记录 `SPEED`、模拟任务的比例、两个核的 `IDLE`、`FRAME` p95 和平均值、欠载次数，以及编译、恢复、淘汰、改由解释器执行的次数、代码池和二级的用量。
- 这个任务不改解释器。解释器只在全部做完以后用同样的方法复测一次，确认没有变慢。

## 不做

## 约束

- JIT 的模拟结果和解释器一致。
- 在 v1.3 或 v3.2 上核对不通过的扩展，同一大版本的固件不能生成。
- 发布以后还会改写的位置只由所属的核用对齐的 32 位写入更新，沿用架构文档的规则。代码的生成、发布和执行仍然由同一个核负责。
- 改动 JIT 运行时 helper 或块查找时，按 `cmake/core_layout.cmake` 的规则放置，检查 map 中的地址，并上板测量布局对性能的影响。
- 每条指令、每次访存的路径上不增加检查。块入口为搬回片内而增加的计数，它的开销要计入测量。
- 没有实测收益的改动撤销，或者由用户确认保留。代码体积和内存占用的变化要记录。

### 标志运算和压缩指令的占比

profile 版启动 JIT 时打印 gateway 里各段共用代码的位置，`tools/profile_report.py` 据此把 gateway 的采样按段拆开。在 Sila P4 上用 `prof 1 5000` 对 core 1 采样 5 秒，都是 JIT 1X，代码副本 8MiB：

| 存档 | 空闲 | 设备 | JIT 运行时 | gateway 合计 | 其中访存 | 其中标志运算 | 块里的代码 | 编译 |
|---|---|---|---|---|---|---|---|---|
| V-Rally 槽位 2 | 68.4 | 10.3 | 5.9 | 3.6 | 2.2 | 0.7 | 2.0 | 0.1 |
| 史前人槽位 1 | 73.3 | 6.0 | 3.6 | 2.6 | 1.3 | 0.5 | 1.3 | 0.3 |

单位是 core 1 采样的百分比。标志运算指 gateway 里的 `zero_flag`、INC/DEC、ALU、移位和 BIT 共用代码，在两个存档上分别只占 0.7% 和 0.5%。标志位活跃性只能省掉其中被块内后续指令覆盖的那部分，上限就是这两个数，比模拟任务比例在两轮之间的差别还小。

同一个 profile 版里还临时统计了生成代码中能换成 16 位形式的指令。统计从开机累计，包括上面两次采样之前 V-Rally 和史前人从载入起编译的 2560 个块、165788 字：数据字（块头、描述、连接字、代码副本）占 24.4%，调用 gateway 的 `jal` 占 23.6%，有 C 扩展 16 位形式的指令占 21.6%，只有 Zcb 形式的为 0。把 A 和 F 换到 a3、a4 以后，能压缩的指令只增加到 21.9%。按这个比例，压缩指令最多能让生成代码小约 10.8%，补齐 4 字节对齐的位置还要再少一些。

### 标志位活跃性

编译块时向后找第一条读或写 H、C 的指令。如果它覆盖了当前指令写的 H 或 C，而且不读它们，当前指令就改调不计算这些位的共用代码，并把输入存进 `Context::flag_inputs`。中间那几条指令的取指慢路径都可能离开原生代码，所以这些慢路径在调用 `group` 之前先调用对应的补算，从存下的输入算出完整的标志位。这几条指令开头不登记块中间的恢复入口，因为补算用的输入是本次运行存下的，从别处进来的运行没有存过。用到这一做法的是 ADD、ADC、SUB、SBC、CP、INC、DEC 和 ADD HL,rr。移位和旋转不做：省掉 C 只少 1 到 2 条指令，存输入又要多一条。N 总是计算，因为设置它最多只要一条指令。块的结尾、EI 之后的指令、跨页的 RAM 指令和带预取字节的块都不省略。如果编译出的出口落在省略范围里，编译就失败，这一块交给解释器。

`run_jit.py` 新增了两项检查，解释器和 JIT 各一项：一段 11 条指令的运算序列，在每条指令执行期间安排一个事件，让块在下一个边界停下，核对停下时和继续执行到结尾时的寄存器和 F。期望值按 Pan Docs 的标志位定义手算。去掉补算调用以后，JIT 这一项失败，结果是 0xe08，期望值是 0xffe。恢复以后，Sila P4 上 `run_jit.py` 全部通过，`run_roms.py --regression` 的 10 个 ROM 两个后端都通过，结果一致。

### 压缩指令

汇编器改为按字节计位置，编码器加了 C 扩展的各条指令，`emit()` 把有 16 位形式的指令换成 16 位形式，生成的块和 gateway 都这样生成。读作数据或发布以后还会改写的字保持 4 字节对齐：块头、调用后面的描述字、连接字和代码范围、代码副本和连接表。后面跟着数据的调用如果不在 4 字节边界上，前面补一条 `c.nop`。安装时修补的 `jal` 可以落在任何偶数偏移上，跨两个字时按两个对齐的 32 位字读改写，代码副本里的重定位也改成字节偏移。块内的跳转和跳过出口的条件分支先按 `c.j`、`c.beqz`、`c.bnez` 生成；如果距离不够，整块改用 32 位形式重新编译，这种情况出现了多少次没有统计。ROM 取指组返回 hot stream 的距离改用半字计数，10 位最多 2046 字节，超出时编译失败，块按原来的规则缩短。条件跳转判断 C 和 Z 时，临时寄存器从 t0 换成 a1，这样分支可以用 `c.beqz` 和 `c.bnez`。Zcb 没有用：前面的统计里没有只有 Zcb 形式的指令。

### 两级代码缓存

`store.h` 的代码副本改成了可以原地执行的第二级。每份副本在 PSRAM 里按自己的位置修补调用并发布。PSRAM 离片内 RAM 太远，`jal` 够不着片内的 gateway，所以第二级按 1 MiB 分段，每段开头放一份 gateway，块里的调用改指本段的那一份。gateway 不含指向自身的绝对地址，可以直接复制；它本身也挪进了代码池那次分配的开头。块在代码池里被淘汰以后，C++ 的查找、直接连接和分发表都进入它在第二级的副本，从块中间恢复时也进入副本里的同一位置。副本的入口把 CLOCK 标记换成了对 gateway 里 `count_entry` 的调用，每次进入把块头里的计数减一；计数用完时块在执行之前退出，C++ 把它拷回代码池，并把指向副本的连接改指代码池里的块。第一次的计数是 64，每拷回一次加倍，最多 8192。第二级满了按先进先出丢弃，丢弃时和代码池淘汰一样撤销连接和分发表表项。块在两级都没有时，仍然按原来的重装退避交给解释器。RAM 里的块只在代码池里。

PSRAM 里的代码先在 Sila P4（v1.3）上核对过：在 PSRAM 里写入代码，写回 L1 数据缓存、作废 L1 指令缓存、执行 `fence.i` 以后可以执行；在同一位置改写、再发布一次，执行的是新代码。把 PSRAM 上的这两步缓存操作去掉以后，`run_jit.py` 在映射执行的检查里 Guru Meditation 崩溃，没能报告结果。Sila P4X 上没有运行这些检查；v3.x 的依据是 IDF 给 PSRAM 配的 PMP 表项可以执行，见架构文档的“JIT 后端”。

`run_jit.py` 增加了 5 项检查，期望值按 ISA 和 Pan Docs 计算：

- PSRAM 里代码的首次执行和改写后的执行，各一项。
- 第二级的 `CodeStore` 在 3 个分段里存 4000 个 1 KiB 的块，绕回一圈。在原来丢弃的位置写入的新块执行结果正确，丢弃按先进先出，每条记录回收一次且范围正确，调用目标能换回原来的地址。
- 解释器和 JIT 各一项：代码池只有 8 个块、第二级约 8 KiB 的 JIT 上，24 个用 JP 串成环的 ROM 块跑 40 轮，每轮在 INC B 之后或 JP 之后停下，所以下一轮从块中间恢复；再跑 48 个新块把旧副本挤出第二级，环再跑 20 轮；然后在 bank 1 和 2 的同一地址之间来回切换。核对每轮的 B、PC、指令数和时间，JIT 那项还要求淘汰、进入第二级、拷回和丢弃都发生过。

| 2X | 36.6 | 5.71 / 4.35 | 1327 / 182 / 528 / 738 / 2383 |

三次 1X 是同一个固件。这个存档每次测量落在不同的阶段，计数分成两种：改由解释器 738 次的那种慢，702 次的那种快。没有第二级时，2048 个槽位测过 1X 一次，属于 702 次那种，是 23.5%；2X 是 36.2%。所以在这个存档上，第二级没有测出速度上的变化。统计段里编译的约 1330 个块，只有 328 到 383 个存进了第二级，和没有第二级时相同，其余是 RAM 里的块，只在代码池里。第二级没有丢弃过记录，ROM 块不会走到重装退避，所以改由解释器执行的也都是 RAM 里的块，第二级接不住这部分。

资源的变化：gateway 加了 `count_entry`，从 8368 字节增加到 8404 字节；第二级的 8 个分段各放一份，按缓存行取整后各 8448 字节，共 66 KiB，从 8 MiB 的第二级里扣。块中间的恢复入口每条加了块标识，从 32 字节增加到 40 字节，8192 条共 320 KiB，在 PSRAM 里。片内 RAM 的用量没有变化，V-Rally 用 JIT 游戏中片内空闲仍然是 115 KiB。

### 两种配置的比较

配置 B 打开 `CONFIG_GBX_JIT_CODE_PSRAM`，代码池连同 gateway 都放进 PSRAM，所有生成的代码都在 PSRAM 里执行，L2 缓存从 128 KB 加到 256 KB。代码池的大小、槽数和第二级都和配置 A 相同。配置 B 的片内空闲是 220 KiB，配置 A 是 115 KiB；512 KB 的 L2 缓存比 256 KB 还要多 256 KiB 片内 RAM，装不下，所以 B 用的是 256 KB。在 Sila P4 上测了一轮，构建方式是在 `sila_p4-profile` 的 sdkconfig 上改这两项：

| 槽位 | 速度 | 模拟任务 %，A → B | `FRAME` p95 / 平均 ms，A → B |
|---|---|---|---|
| 1 | 1X | 14.8 → 14.2 | 5.71 / 4.59 → 5.45 / 4.39 |
| 1 | 2X | 24.2 → 23.7 | 3.90 / 3.17 → 3.72 / 3.05 |
| 2 | 1X | 23.1 → 28.9 | 5.92 / 5.47 → 6.06 / 5.98 |
| 2 | 2X | 39.8 → 49.9 | 4.80 / 4.69 → 5.53 / 5.46 |

`SPEED` 和欠载同上，计数两种配置相同。槽位 1 的代码约 64 KB，B 略快；槽位 2 的代码约 204 KB，B 的模拟任务比例多了约 25%。史前人槽位 1 上，B 的 1X 两次都是 738 次那种阶段，分别是 25.8% 和 25.9%，2X 是 35.6%，和 A 在同样阶段的结果相近。B 的测试固件在 Sila P4 上 `run_jit.py` 的 162 项全部通过，`run_roms.py --regression` 用默认代码池和 `--small-pool` 各跑一次，两个后端都通过，结果一致。

P4 的默认配置用 A：片内代码池加 PSRAM 第二级，L2 缓存 128 KB。`CONFIG_GBX_JIT_CODE_PSRAM` 留作选项，默认关闭，以后 GBA 的片内 RAM 不够时再考虑。两种配置没有在 Sila P4X 上比较：这一项没有改 v3.x 特有的代码。

### 收尾

全部做完以后，在 Sila P4 上用测试固件 `sila_p4-test-release` 运行了全量：SM83 单步的 500000 条用例两个后端都通过，JIT 全部原生执行，没有回退；`run_roms.py --all` 的 105 个验收 ROM 两个后端都通过，结果一致，只记入报告的 25 个里 `oam_bug` 没有可用的参考结果，其余通过。`check_rv32_encoding.py` 核对了 14959 条编码，没有差异。Sila P4X 上没有运行全量。Zba、Zbb、Zbs 只在 v3.x 上启用，它们在 Sila P4X 上的验证只有前面那次 `run_jit.py` 和固定回归；两级代码缓存没有在 Sila P4X 上运行过。

解释器用同样的方法复测了一轮，固件 `sila_p4-profile`：

| 槽位 | 速度 | 模拟任务 %，基线 → 现在 | `FRAME` p95 / 平均 ms，现在 |
|---|---|---|---|
| 1 | 1X | 33.5 → 33.4 | 8.64 / 7.60 |
| 1 | 2X | 62.2 → 61.5 | 6.60 / 6.26 |
| 2 | 1X | 39.3 → 38.6 | 7.90 / 7.60 |
| 2 | 2X | 71.4 → 71.6 | 7.03 / 7.00 |

`SPEED` 都在 99.9% 到 100.0% 或 199.9% 之间，欠载都是 0。和两轮基线的平均值相差不超过 0.7 个百分点，解释器没有变慢。

PC 的 debug 构建没有警告。用户确认可以提交以后，全部板子的正式固件和测试固件都构建通过，改动过的文件在 JC1060P470 和 Sila P4X 上重新编译，没有警告。

各项的结果：标志位活跃性没有测出收益，块变大，已经撤销；压缩指令让平均每块小了 9% 到 10%，gateway 从 10040 字节减到 8368 字节，速度没有测出变化；Zba、Zbb、Zbs 只用在 v3.x，没有测出收益，仍然保留；两级代码缓存在 V-Rally 上用不到，在史前人上没有测出速度变化，ROM 块被淘汰以后只要副本还在第二级，就不再交给解释器；两种配置里片内代码池加二级在 V-Rally 槽位 2 上明显更快，选定为 P4 的默认配置。剩下的瓶颈：V-Rally 和史前人用 JIT 时，模拟任务里设备和 JIT 运行时的 C++ 代码占得比生成的代码多，见前面“标志运算和压缩指令的占比”的采样；史前人反复编译 RAM 里的块，每 10 秒约 1000 个，这部分第二级接不住，但是在那次采样里编译只占 core 1 的 0.3%。

### 剩余瓶颈的跟进

收尾以后，在 Sila P4 上用 `sila_p4-profile` 对 core 1 采样了 5 秒，JIT 1X，单位是 core 1 采样的百分比：

| 存档 | 设备 | JIT 运行时 | gateway | 块里的代码 | 编译 | 解释器 |
|---|---|---|---|---|---|---|
| V-Rally 槽位 2 | 10.4 | 5.7 | 3.6 | 2.0 | 0.2 | 0.0 |
| 史前人槽位 1 | 6.2 | 3.2 | 2.3 | 1.1 | 0.2 | 0.0 |

V-Rally 上没有哪个 C++ 函数超过 2%，最多的是 `update_deadline` 1.7、`Ppu::begin_transfer` 1.6、`careful_write` 1.3 和 `careful_read` 1.0。显示转换 `convert_step` 在两个存档上分别占 9.1 和 9.9，它不算在模拟任务里。史前人反复编译 RAM 里的块，编译和解释器加起来也只占 0.2，所以这一项没有做。

只做了两项简单的。一是 profile 版的 `stat` 加了一行慢路径的计数，二是 `careful_write` 写声音寄存器、波形 RAM、SCY、BGP、OBP0、OBP1、WY、WX 和 HRAM 时，不再重新计算推迟的期限。改动前后的固件都带这些计数，V-Rally 槽位 2 在 1X 下每 2 秒的计数如下：

| 项目 | 次数 |
|---|---|
| 慢路径读，几乎都是 IO | 约 57000 |
| 慢路径写 VRAM | 约 92600 |
| 慢路径写 IO | 约 17300，其中 SCY、SCX 和 BGP 各 5400，P1 360 |
| 慢路径写 0x8000 以下 | 约 1900 |
| 重新计算期限，改动前 → 改动后 | 约 19200 → 7800 |

模拟任务的比例在 1X 下从 23.2% 到 22.7%，2X 下从 40.0% 到 39.5%，各测了一轮，差别没有超出两轮基线之间的差别。改动以后，在 Sila P4 上用 `sila_p4-test-release` 运行 `run_jit.py`，162 项全部通过；`run_roms.py --all` 的 105 个验收 ROM 两个后端都通过，结果一致，只记入报告的 25 个里 `oam_bug` 没有可用的参考结果，其余通过。

慢路径的写里 VRAM 最多，每秒约 46000 次。让生成的代码直接写 VRAM 没有做。
