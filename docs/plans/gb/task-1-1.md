# 任务 1-1：SM83 解释器

这是[路线图](../../roadmap.md)里程碑 1 的第一个任务：在 `components/core/` 里写 SM83 解释器，让它执行 SingleStepTests 的单步用例时，寄存器、内存和每个 M-cycle 的总线状态都和预期一致。后面的任务都依赖它。1-2 用它打通板上的测试通路，1-5 拿 JIT 的结果和它比对，以后 JIT 遇到不能翻译的指令时也回退到它。

开工时在[任务状态](status.md)里把这个任务标为“进行中”。

## 先读

- 路线图的“1. SM83 和测试通路”，以及[架构](../../architecture.md)的“分层”“目录”和“代码规则”。
- `refs/tests/sm83/README.MD`：用例格式，以及总线状态在 M-cycle 之间采样的含义。
- 硬件行为以 `refs/docs/pandocs/` 为准，逐周期的时序看 `refs/docs/gbctr.pdf`。`refs/docs/Opcodes.json` 可以用来生成解码表。

## 范围

- 新建 `components/core/`，按架构文档的目录划分。CMakeLists 和其他组件一样写成两用，PC 版和测试固件都要能编译它。
- 实现 `refs/tests/sm83/v1` 里 500 个操作码文件对应的全部指令，包括 CB 前缀的指令和 HALT、STOP、EI、DI。
- CPU 通过总线接口访问内存。每个 M-cycle 的地址、数据和读、写、内存请求信号都要能被观察到，没有访存的 M-cycle 也算在内，因为用例逐个 M-cycle 检查总线。
- 这个里程碑只需要平坦的 64KiB 内存这一种总线实现，用例本身就假设没有内存映射和 IO 寄存器。
- 解释器能从任意给定的 CPU 和内存状态开始，执行一条指令以后返回。单步用例要这样执行，JIT 回退时也要这样调用。

## 不做

- 调度器、内存映射、IO 寄存器、中断分派和其他设备，这些在里程碑 2。
- 板上的测试固件和 runner，这是 1-2 的内容。
- 整机性能优化。本任务先建立正确、清楚的 CPU 指令语义和总线接口。

## 约束

- 里程碑 2 会把平坦内存换成真实的内存映射，并且在每次访问之前把设备推进到当前时刻。CPU 和总线之间的边界要让这次替换不必重写指令的实现，但是现在不要实现这些设备。
- 总线访问每个 M-cycle 都会发生，所以不能用虚函数分派。如果用模板参数选择总线，先量一下代码体积。
- 逐周期记录总线状态只有测试需要。游戏运行时不记录，记录功能也不能给每次访存增加开销。
- 非法操作码，比如 D3、DB、DD，没有单步用例，但是游戏和测试 ROM 有可能执行到它们。解码时不能把它们当成走不到的分支，要按 Pan Docs “CPU Instruction Set”一节的描述让 CPU 锁死。

## 由你决定

CPU 状态怎么组织、解码用 switch 还是编译期生成的表、总线接口的形式，以及 `gb/` 下的文件怎么划分。选择的理由写在代码注释里。如果改变了模块边界，同步更新架构文档。

## 开发期间的验证

板上的测试通路要到 1-2 才有。在这之前，可以在 PC 上写一个临时程序，读取 `refs/tests/sm83` 的 JSON，和解释器的结果对照，用来排错。这个程序不提交，不加进 CTest，也不写进文档，因为按 AGENTS.md 的规定，验收测试在板子上运行。

## 完成标准

- 在临时对照中跑完全部用例，并且全部通过。如果有用例不过，而你判断是用例本身有错，列出用例名和依据，不要为了通过去迁就它。
- PC 的 debug 构建和至少一个测试固件 preset 编译通过，没有新的警告。
- 这里的通过只是开发期间的结果。要等 1-2 在板子上跑通全部单步用例，解释器才算通过测试，汇报时不要说成已经通过测试。

## 收尾

- 满足全部完成标准以后，在[任务状态](status.md)里把这个任务标为“已完成”。
- 更新架构文档中“`components/core/`……还没有建”的说法，以及路线图“现状”一节。
- 向用户汇报做了哪些设计选择、临时对照的结果，以及发现的用例问题。

## 开发核对结果

解释器及平坦总线已经实现，开发核对覆盖了全部 500,000 条单步用例。板上验证由[任务 1-2](task-1-2.md)完成，条件和结论保存在运行报告中。

原始 SingleStepTests/sm83 的 1,000 条 STOP 用例预期 PC 只加 1。对应的[生成器](https://github.com/raddad772/jsmoo/blob/b3807b55f03cdad2191810b2a770781d73c41870/misc/code_generation/sm83_test_generator.js#L1075-L1078)没有跳过第二个字节，也没有建模完整的暂停与唤醒条件。按 [Pan Docs](https://gbdev.io/pandocs/Reducing_Power_Consumption.html#using-the-stop-instruction)及其引用的 [CPU 内部行为资料](https://gist.github.com/SonoSooS/c0055300670d678b5ae8433e20bea595#nop-and-stop)，没有中断请求和唤醒输入的普通 STOP 路径应当使 PC 加 2；当前实现与修订都限定在这个条件下，完整唤醒行为留到里程碑 2。

[`tools/fix_sm83_stop.py`](../../../tools/fix_sm83_stop.py) 生成 `sm83-stop-pc-v1` 副本，只修正 STOP 的最终 PC，保留来源和修订元数据。原始套件不变，预期值按硬件规则计算，不从模拟器输出生成。不能把修订套件通过写成原始套件全部通过。
