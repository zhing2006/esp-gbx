# 任务 3-4：JIT 块间连接和跳过忙等

用本地的 5 个 GB 游戏在板上实测两个后端的速度和瓶颈，按实测结果优化 JIT 的块间连接。解释器按双后端优化要求同样分析和优化。这个任务依赖 3-2，可以和 3-3 同时进行。

开工时在[任务状态](status.md)里把这个任务标为“进行中”。

- [架构](../../architecture.md)的“模拟器”，尤其是整机 JIT 的公共入口、块内连接和代码失效的说明。

- 2-1 至 2-4 的 JIT 前端，以及 3-2 的运行流程和常驻指标。

## 范围

- 按帧录制和回放按键：试玩时录下每帧的按键状态，回放时按帧提交，让两个后端以及优化前后使用相同的输入。录制和回放是性能分析的工具，只放在 `<板子>-profile` 版里，正式 release 不包含。录制从载入 ROM 开始，文件里带上这时的卡带 RAM 和 RTC，回放从同样的状态开始。回放期间不写回卡带存档，也不出现 RTC 不可信的提示。录制文件放在卡上，位置由你决定。
- 测量用的游戏是仓库根目录 `roms/gb/` 下的 5 个本地 GB 游戏，每个游戏只录一段有代表性的画面，不需要长流程。除了 3-2 列出的 Dangan GB、Pokémon Gold 和 Pokémon Yellow，另外两个见下表。本地的文件名和 3-2 写的不同，以 SHA-1 为准。商业游戏只用于本地的性能分析：不提交，不写进 fetch 脚本，不进入测试索引，也不作为任何测试的判据，报告里和 Dangan GB 的数据分开写。

|---|---|---|---|
| `V-Rally 锦标赛版.gb`，V-Rally Championship Edition | MBC1，256KiB ROM，没有卡带 RAM | 0x00 | `67d2a6e41b6a1d8372808535ac8c8222d7c53480` |
| `史前人.gb`，Prehistorik Man | MBC1，128KiB ROM，没有卡带 RAM | 0x00 | `1139d6b799b8585bbb7868bd3bca5ba9dea4eef5` |

- 测量在 1X 下用 Sila P4 的 `<板子>-profile` 版进行，优化前后都用这个构建，测速时不运行 `prof` 和 `pstat`。1X 下 `SPEED` 最高只到 100%，所以优化效果主要看 CPU 所在核的 `IDLE`，以及 `FRAME` 的平均值和 p95；同时记录 `SPEED`、欠载次数，以及 JIT 的编译、失效、回退次数和代码池用量。现有指标不够时可以在 profile 版里增加计数，最后只留下对以后优化有用的，正式 release 不增加统计代码。再用 `prof` 或临时计时找出热点，比如 C++ 中的块查找、helper 调用和忙等循环各占多少时间。
- 1X 下 core 0 每秒只渲染约 60 帧。3-1 的剩余瓶颈（见 [3-1 的剩余瓶颈](task-3-1.md#剩余瓶颈)）出现在不节流运行时，这里按 profile 版测得的 core 0 负载决定是否优化渲染。
- 在正式固件的实际负载下，用 profile 版重新确定工作线程的轮询长度，即 `components/core/src/gb/offload.h` 的 `kPolls`，或者按上一次轮询是否等到新任务决定要不要轮询，并确认它不会让 core 0 上优先级更低的呈现和 LVGL 长时间排不上。
- 按测量结果优化现有的块间连接，比如扩大能连接的出口类型或者减少连接未命中，具体做什么以实测为准。
- 减少代码池的抖动。V-Rally Championship Edition、Pokémon Yellow 和 Prehistorik Man 在测量画面里用到的块合计 0.67 到 1.19 MiB，远大于 224 KiB 的代码池，JIT 的大部分时间花在反复安装被淘汰的块上，V-Rally 的 JIT 比解释器慢约 5 倍。办法按实测选择，比如让反复被淘汰的块改由解释器执行、减小生成代码的体积、降低重新安装的成本。
- 跳过忙等不做。两个后端共用一份实现做过三版，回放结果都和基线一致，但是 JIT 原生执行这类循环本来就便宜，判断的开销超过了省下的时间，Dangan GB 上 JIT 反而变慢。代码已经撤销，测量数据和原因写进报告。
- 解释器按同样的游戏和输入分析瓶颈并优化。

## 不做

- Zb 等扩展指令和 PSRAM 中的冷代码区，这些在里程碑 5。
- 新的设备功能。

## 约束

- 代码改写、bank 切换和代码淘汰都要让相关的连接失效，沿用架构文档中的规则。
- JIT 运行中改由解释器执行的块，结果必须和原生执行相同。
- 只保留正确并且有实测收益的改动，没有收益的尝试撤销，在报告里说明。代码体积和内存占用也要记录，不能用未说明的资源增长换取速度。
- 改动解释器、设备执行代码或 JIT 运行时 helper 时，按 `cmake/core_layout.cmake` 的规则放置，检查 map 中的地址，并上板测量布局对性能的影响。
- 比较时保持板型、芯片修订、主频、构建配置、ROM、输入、统计区间和核安排一致，冷热启动和是否清空代码缓存写进记录。

## 实现与验证

以下数据都来自 Sila P4，ESP32-P4 v1.3、360MHz、PSRAM 200MHz，ESP-IDF v6.1，构建 preset 为 `sila_p4-profile`，1X，CPU 在 core 1，渲染和混音在 core 0。固件包含本任务的改动。每次回放都重新载入 ROM，JIT 的代码池和代码副本从空开始；统计区间从录制的 mark 到结束，mark 之前的帧用来预热。数字包含 profile 版计数的开销。同一配置换一次构建，结果差过约 8%，来自代码布局的变化；同一个固件重复回放，Dangan GB 相差不到 1%，Pokémon Yellow 约 3%。

5 段录制的帧数和 mark 位置如下：Dangan GB 4212 帧，从第 2974 帧开始计时；Pokémon Gold 2397 帧，从第 713 帧；Pokémon Yellow 4869 帧，从第 3385 帧；V-Rally Championship Edition 5985 帧，从第 4939 帧；Prehistorik Man 6108 帧，从第 4793 帧。

本任务没有运行 SM83 单步和整机 ROM 测试，由 3-5 用两个后端跑全量。每次改动以后用回放核对机器状态的 hash，下面所有回放的 hash 都和优化前相同。

### 保留的优化

LYC 中断的时刻。IME 打开、IE 里使能了 STAT 中断时，推迟派发的期限原来总是取下一个 PPU 事件，而 PPU 每条扫描线都有事件，所以期限很短。现在 STAT 没有打开中断源时不再按 PPU 事件限制期限，只打开了 LY=LYC 时按扫描线时序算出 LY 下一次等于 LYC 的时刻（`Memory::next_interrupt` 和 `Ppu::next_lyc`）。同一个固件对比：Dangan GB 的 JIT 从 2.619 / 3.657 降到 2.407 / 3.267，Prehistorik Man 从 7.072 / 15.630 降到 6.597 / 14.440。

代码池重装退避。V-Rally、Pokémon Yellow 和 Prehistorik Man 用到的块远多于代码池能放下的，JIT 的大部分时间花在反复安装被淘汰的块上。被淘汰过的 ROM 块再次未命中时，先改由解释器执行若干次，每重新安装一次次数翻倍，最多 127 次；批次从被淘汰的块中间恢复时，也由解释器做完剩下的指令。`Reinstall` 表按块标识的散列记录块的指令条数和退避级别，代码副本也记下块的指令条数。这一项让 V-Rally 的 JIT run 平均值从 32.57ms 降到 8.96ms，Pokémon Yellow 到 3.04 / 4.69，Prehistorik Man 到 4.68 / 6.85，Dangan GB 2.42 / 3.15，Pokémon Gold 3.55 / 4.18。

生成代码改用共用代码。访存、出口、ROM 块的取指慢路径、大部分标志运算和 POP/PUSH 改为调用 gateway 里的共用代码。V-Rally 从载入到结束生成的代码从 526315 字降到 162090 字，平均每块从 185 字降到 64 字，每条指令从 20.7 字降到 6.8 字；run 从 8.96 / 12.79 降到 6.57 / 8.79，计时段里的安装从 25913 次降到 9886 次。改之前生成代码的构成是：访存的热段 25.4%，运算 25.5%，取指的冷段 19.4%，取指检查 9.7%，出口 9.6%；改之后，取指的检查和慢路径（每条指令热段 2 字、冷段 2 字）占 59%。

代码池的槽数从 512 增加到 1024。块变小以后，512 个槽先用完，代码池只用到约 131KB。槽结构从 32 字节缩到 16 字节，使用标记和安装编号移到两个单独的数组里，1024 个槽的数组仍然在片内分配的大小以内。V-Rally 的 run 从 6.57 / 8.79 降到 4.61 / 6.05，计时段里的安装降到 3589 次，改由解释器执行的次数从 269776 降到 11601，代码池用到约 221KB。

声音任务的交接间隔从 1/64 s 改为 1/32 s。CPU 所在的核等待工作线程的时间，在 JIT 变快以后变多了：最后一项改动之前，计时段里 Dangan GB 等了 4962 次、共 369ms，Pokémon Yellow 3084 次、670ms，V-Rally 979 次、144ms，Prehistorik Man 2362 次、574ms，Pokémon Gold 1 次。在 Pokémon Yellow 上临时记录每次等待开始时工作线程在做什么：1481 次、593ms 是在混音，大约每帧一次，每次约 400µs；2935 次、228ms 在渲染扫描线；1091 次、79ms 在轮询；工作线程睡眠时开始的等待没有。临时统计本身让等待变多了，所以这里只看比例。游戏每帧的运行有 1/59.7 s，比原来的交接间隔长，每帧中途都会交出一批声音，混这一批的时间里 JIT 已经产生了超过队列容量的 16 行。间隔改为 1/32 s 以后，每帧只在运行结束时交出一次声音，混音在 CPU 所在的核等下一帧时进行。ROM 测试每段只运行 1/128 s，不受影响。PCM 只由写入和写入的时刻决定，和任务怎样划分无关，回放的 hash 也没有变。Pokémon Yellow 的 JIT run 从 2.575 / 3.120 降到 2.218 / 2.776，等待从 3084 次、670ms 降到 1918 次、122ms，frame 从 3.587 / 4.224 变为 3.602 / 4.183。

工作线程的轮询长度 `kPolls` 保持 1024。在 Pokémon Yellow 的 JIT 回放中，1024 次轮询约 125µs；找到新任务的 216930 次轮询里，99.8% 在 50µs 以内，超过 100µs 的只有 9 次；落空 1596 次，约每帧一次，CPU 所在的核在两帧的运行之间不产生任务。工作线程睡眠时没有出现过等待，所以等待不是轮询长度造成的。缩短轮询只能省下每帧一次落空的约 125µs，约占 core 0 的 0.75%。最终固件上 Pokémon Yellow 的 JIT 回放中，6 秒的 `tasks` 里 core 0 的 IDLE0 占 65.5%，`gbx-render` 17.7%，`present` 9.8%，`taskLVGL` 3.1%；6.4 秒的 `pstat` 里，游戏帧发布 384 帧，呈现任务取走 383 帧，取走时都在发布后 5ms 以内。被覆盖的 1 帧发生在扫描等待阶段，而面板的扫描约 59.66Hz，比游戏的 59.73 帧每秒慢，平均约 14 秒必然要覆盖一帧。呈现任务和 LVGL 没有长时间排不上。

### 撤销和没有做的尝试

跳过忙等做过三版，两个后端共用一份实现，回放的 hash 都和基线一致，但是 JIT 原生执行这类循环本来就便宜，判断的开销超过了省下的时间，Dangan GB 上 JIT 反而变慢，代码已经撤销。

“几条指令共用一次取指检查”评估以后没有做：V-Rally 的热代码平均约两条指令一串，估计只能省下约 15% 的代码，而检查失败时要退出到解释器；共用代码以后，编译和安装只占 core 1 采样的 2.6%。

mid 表的冲突没有修：在共用代码之前测量时，它在计时段里只造成 37 次编译，其余的编译来自代码副本装不下，当时 V-Rally 从载入起生成了约 2.1MB 代码，超过 2MiB 的代码副本。

### 剩余瓶颈

V-Rally 在共用代码、512 个槽时的 core 1 采样（8 秒）：空闲 52.4%，设备 13.6%，JIT 运行时 12.6%，其中 `execute` 5.8%、`update_deadline` 3.4%、慢路径访存 2%，解释器 10.7%，生成代码 5.2%，编译和安装 2.6%。计时段里 V-Rally 和 Prehistorik Man 还分别编译了 611 和 1093 个块，共用代码以后没有再拆分这些编译的来源。

CPU 所在的核剩下的等待发生在工作线程渲染扫描线的时候：HALT 多的画面里，CPU 产生一行的时间比渲染一行短。core 0 上，最后一项改动之前 Pokémon Yellow 的采样里，把一帧的灰阶换成颜色交给显示约占 5.8%，每帧约 1ms，`Renderer::segment` 5.0%，轮询 3.4%，混音约 2.4%，呈现任务的 `draw_game` 8.5%，空闲 62.7%。1X 下这些等待不影响 `SPEED`，只占用 CPU 所在核的空闲时间，不再优化渲染。

### 资源变化

和开工时的代码用同一 preset 比较：

- release 镜像从 893804 字节增加到 898156 字节，增加的 4352 字节都在 flash 的 `.text`。片内 RAM 的静态段：`.text` 都是 71878 字节，`.bss` 从 53256 字节减到 53248 字节，`.data` 都是 13696 字节。release 镜像里没有录制、回放和计数的符号。
- profile 镜像从 908224 字节增加到 923168 字节，比 release 多增加的约 10.6KB 来自只在 profile 版里的录制、回放和计数。
- gateway 从 1652 字节增加到 10040 字节，在 JIT 初始化时从片内可执行内存分配，不占 224KiB 的代码池。
- 代码池的槽数从 512 增加到 1024：槽数组仍是 16KiB，另加使用标记和安装编号两个 4KiB 数组，片内 RAM 多用 8KiB。
- `Reinstall` 表 16KiB，在 PSRAM。`Context::save` 从 12 项增加到 14 项。
- 最终固件运行 V-Rally 的 JIT 时，片内 RAM 剩余 159931 字节，最大可分配块 65536 字节。

### 构建

PC 的 debug 构建，Sila P4 的 `sila_p4-release`、`sila_p4-profile` 和 `sila_p4-test-release` 都编译通过，没有新的警告。`sila_p4-test-release` 的 CMake 提示 `tests/device` 组件用了 `platform` 的私有头文件目录，本任务没有改动这部分。

## 审查后的修正

代码审查指出了 5 个问题，都已经修正：

- ROM 块的取指慢路径从当前映射重新读取指令字节，再按读到的指令撤销内联检查预加的周期。上一条指令切换了 bank 时，原生代码要经过这个慢路径才退出，而新 bank 同一地址可能是另一条指令，撤销的周期就和预加的不同，模拟时间会出错。现在描述字里保存编译时的取指周期数，撤销时用它。
- 共用的 PUSH 代码直接写内存，入口核对过代码字节的 RAM 块用 PUSH、CALL 或 RST 写到自己的代码时发现不了。这类块的 PUSH 改回经过代码页检查的写入。
- 复位以后的第一行在 320 tick 结束，`Ppu::next_lyc()` 却按完整的一行计算，得到的期限偏晚，JIT 可能越过 LY=LYC 的中断时刻。现在当前行按它的行相位实际结束的时刻计算。
- profile 版没有回放时，按键也被换成 0，游戏收不到按键。现在只在回放结束、等待报告的几帧里不给按键。
- 回放报告的编译、恢复、淘汰、回退、代码池用量、欠载、CPU 等待工作线程的次数和 JIT 计数器，原来在最后一帧之后又运行 29 帧才读取，包含了这 29 帧；时间和 hash 只统计到最后一帧。现在这些计数在最后一帧结束时读取。上文表里的这些计数是修正之前的，包含这 29 帧。

修正以后，PC 的 debug 构建，以及 Sila P4 的 `sila_p4-release`、`sila_p4-profile` 和 `sila_p4-test-release` 都编译通过，没有新的警告。在 Sila P4 上用修正后的 `sila_p4-profile` 回放了 V-Rally 的 JIT：hash 和优化前相同，速度 100%，没有欠载，run 4.634 / 5.783，frame 6.026 / 7.292，编译 611、恢复 2551、淘汰 3208 次，改由解释器执行 12466 次，代码池用量 224656 字节，这些计数不再包含最后一帧之后的帧。其余游戏没有重新回放。
