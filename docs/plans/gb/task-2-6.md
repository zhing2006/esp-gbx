## JIT 性能分析

当前最值得先分析的是 `cpu_instrs`：它几乎贡献了全量验收中 JIT 相对解释器的全部净耗时差。少量 ROM 的分项计时还确认了两类开销：编译和代码安装占用了一部分时间，已有机器码的执行路径也不总是快过解释器。代码池淘汰、短块的连接与退出、访存检查都是后续需要分开测量的候选，现有数据还不能给这些候选排出准确的耗时比例。

### 测量条件和口径

数据来自 Sila P4，ESP32-P4 v1.3、360MHz、ESP-IDF v6.1，构建 preset 为 `sila_p4-test-release`。模拟机型是 DMG-C，使用 `isolated` 调度，两个后端依次在 core 1 执行，渲染在 core 0。固件包含本任务的改动。最终验收固件的 ELF SHA-256 为 `13a0fb620b4bc59e6e087ba47663a41b6296a9e778c99007c43520fea5398f78`。

`1×` 表示 GB 原速。每个 ROM 的速度用模拟时间除以执行墙钟时间，包含设备执行、渲染等待、测试 worker 的调度让步，以及 JIT 的冷缓存编译和安装；不包含 ROM 读卡、初始化、最终状态摘要和结果回传。整套测试的墙钟预算另计，不能把它和各 ROM 的执行时间相加值混用。

分项计时使用了临时插桩，不能代替最终固件的速度。临时计时代码没有保留在最终固件中，对应表格单独说明测量方式。

### 全量差距集中在哪里

100 个验收 ROM 在两个后端上各模拟了合计 118.080 秒，结果全部一致，没有回退。

| 指标 | 解释器 | JIT |
|---|---:|---:|
| 执行墙钟时间合计 | 43.074 秒 | 47.637 秒 |
| 总模拟时间除以总执行时间 | 2.741× | 2.479× |
| 各 ROM 速度的中位数 | 3.159× | 3.231× |
| 各 ROM 速度范围 | 2.216–4.265× | 1.975–5.639× |

JIT 在 62 项上更快，但总执行时间多了 4.563 秒，也就是多用了约 10.6%。`cpu_instrs` 单项多用了 4.578 秒；其余 99 项合计，JIT 反而少用了 15.4ms。因此，如果目标是降低这套验收的总耗时，应该先给 `cpu_instrs` 做分项计时。它还没有编译、安装和执行的时间拆分，不能把下文短 ROM 的比例套到它身上。

### 编译、安装和其余执行的分项计时

下表是完成索引优化后的首次执行，每个 ROM 从空代码缓存开始，单位为 ms。安装总时间包含发布，因此表中的“安装，不含发布”已经扣除了发布时间，四个 JIT 分项可以相加得到 JIT 总时间。“其余执行”是总时间减去编译和安装总时间，包含生成代码、C++ 查找与 helper、设备、渲染等待和调度，不能把它称为纯原生代码耗时。

| ROM | 解释器总时间 | JIT 总时间 | 编译 | 安装，不含发布 | 发布 | 其余执行 |
|---|---:|---:|---:|---:|---:|---:|
| `instr_timing` | 358.62 | 472.51 | 24.23 | 39.25 | 14.30 | 394.73 |
| `mem_timing` | 1114.92 | 1149.01 | 28.82 | 35.45 | 14.17 | 1070.57 |
| `dmg-acid2` | 72.30 | 67.88 | 3.03 | 1.67 | 1.61 | 61.57 |
| `timer/tima_reload` | 69.89 | 89.69 | 6.13 | 5.06 | 3.25 | 75.25 |
| `mbc5/rom_1Mb` | 71.75 | 74.63 | 3.07 | 1.67 | 1.50 | 68.40 |

`instr_timing` 的编译和安装合计占 JIT 总时间的 16.5%，但扣除这两项以后，394.73ms 仍比解释器的 358.62ms 高 10.1%。`tima_reload` 的对应比例是 16.1%，其余执行比解释器高 7.7%。这两个样本说明，只消除首次编译成本还不足以让所有执行路径快过解释器。

`mem_timing` 的其余执行比解释器低约 4.0%，但是编译和安装增加了 78.44ms，最终总时间仍较高。`dmg-acid2` 和 `mbc5/rom_1Mb` 的其余执行也较低。不同 ROM 的开销构成不同，不能把 JIT 的差距统一归因于编译器或访存。

这组分项测量每种情况只有一次运行，适合定位数量级，不用于判断不足 1% 的差别。减去分项时间也不是“关闭编译以后会达到的速度”：编译和执行交替可能改变 cache 状态，简单相减没有消除这种影响。

### 本轮已经减少的开销

JIT 淘汰块时复用单项索引删除，避免每次安装重建整张哈希索引。分项运行中，`instr_timing` 的安装总时间从 71.98ms 降到 53.55ms，`mem_timing` 从 73.16ms 降到 49.62ms；发布部分仍分别约为 14.3ms 和 14.2ms。因此，已经确认的收益主要来自减少安装过程中的索引维护，而不是减少缓存发布。

| ROM | 解释器优化前 | 解释器优化后 | JIT 优化前 | JIT 优化后 |
|---|---:|---:|---:|---:|
| `instr_timing` | 360.33 | 357.48 | 482.91 | 463.89 |
| `mem_timing` | 1120.95 | 1103.13 | 1171.53 | 1143.36 |
| `dmg-acid2` | 74.07 | 72.69 | 67.65 | 67.66 |
| `timer/tima_reload` | 70.32 | 69.74 | 89.01 | 88.48 |
| `mbc5/rom_1Mb` | 72.96 | 71.63 | 74.39 | 74.46 |

解释器扩大连续执行批次后，这五个样本提速约 0.8–1.9%。JIT 在前两个样本上分别提速约 4.1% 和 2.5%，`tima_reload` 约 0.6%，其余两个基本不变。最终 ELF text 从 428278 字节降到 428022 字节，data、BSS 和代码池容量没有增加；热代码区域保持在 `0x48000060` 至 `0x4800b97a`。

“写内存后先检查窗口是否不变，再决定是否重算期限”的 JIT 尝试没有保留：它在 `mem_timing` 上重复测得约 0.5% 的变慢。这个结果只否定了本次具体改法，不能据此判断期限计算没有优化空间。

### 可能的剩余瓶颈和下一步测量

**先给 `cpu_instrs` 补充分项计时。** 它有 6566 次淘汰和 488 次取指失效，但这些次数不能直接换算成 4.578 秒的耗时差。应该使用相同的 55 秒模拟区间，分别记录编译、发布、安装的其余部分，以及执行的时间分布，再按 ROM PC 或测试阶段定位。`instr_timing` 可以继续作为短样本，`mbc2/bits_unused` 可以作为没有淘汰和失效的对照。不能通过缩短套件规定的模拟时长来改善验收数字。

缓存方面，`components/jit/src/cache.cpp` 的 `insert()` 仍从头扫描空闲 slot，`gap()` 沿代码块链表寻找连续空间；每淘汰一个块后还会重新寻找空间。安装的非发布部分在两个 blargg 分项样本中仍占 39.25ms 和 35.45ms，但这部分也包含代码复制和索引操作，尚未单独测量扫描的占比。下一步可以记录每次安装扫描的节点数、需要淘汰的块数、块字节数，以及同一块标识再次编译的次数，再判断是否值得维护空闲 slot 或调整空间管理。

扩大代码池和减少生成代码的体积都可能降低淘汰，但收益未实测。当前常规块在 guest 的 4 字节对齐边界处结束，目的是减少事件产生不同入口时的重叠翻译，见 `components/core/src/gb/jit/sm83_jit.cpp` 的 `Compiler::compile()`。短块也会增加块头和连接逻辑所占的比例。应该先统计块长度、每条 guest 指令对应的机器码字节数和被执行的次数，再比较候选划分；直接加长块可能重新增加重叠代码。分项样本中，JIT 执行结束时片内空闲内存约 117.6KiB，最大连续块为 50KiB，这不是运行期间的最小余量，也不能只凭空闲总量认定可以扩大代码池。

块连接也需要独立计数。当前已经有块间连接，不能再把“加入连接”当作尚未实现的优化。`initialize_gateway()` 在块出口检查执行期限、中断条件、连接 epoch 和目标 PC/EI；`Sm83Jit::execute()` 在淘汰、取指失效或映射改变后更新全局连接 epoch。因此，一次回收可能让没有被回收的目标也需要重新解析连接。这个额外代价有代码依据，但直接连接命中率、因 epoch 变化失效的次数和 `resolve_link()` 的耗时都未实测。需要先把连接命中、解析已有块、返回 C++ 编译和事件退出分开统计，才能判断是否值得细化连接的失效范围。

访存和执行检查是另一组候选。`Compiler::access()` 生成的直接访存仍要检查期限、加载页指针、判断权限并累计周期；IO 和事件附近的访问会进入 `sm83_jit_runtime.cpp` 的 helper，同步时钟并更新期限。块出口还会物化延迟的 Z 标志并更新执行计数。短块可能让这些固定开销占比较高，但当前没有快速路径命中率、helper 调用次数或按退出原因分类的采样。需要把这些数据和实际执行的块长度一起测量，不能只凭 RV32 指令数判断瓶颈，也不能用延后设备事件或省略取指校验来换速度。

渲染与核间等待尚未分项。24 个 Mealybug 用例的合计速度是解释器 1.219×、JIT 1.127×，最慢的 `m3_lcdc_win_en_change_multiple_wx` 分别为 0.756× 和 0.721×。两边都慢，说明值得检查共同的 PPU、事件处理和渲染任务交接，但不能据此认定渲染线程已经占满了 core 0。下一步需要分别测 CPU 核执行、渲染核忙碌、队列等待和帧结束等待的时间；I-cache、D-cache 命中及 PSRAM 访问开销在本轮也未实测。软件代码池淘汰和硬件 cache miss 是不同的指标，不能互相替代。

测量和实验仍需要保持两个后端的工作量、设备行为和判据一致。分项计时只用于定位，确认改动以后要清理临时代码、核对链接地址，再用没有计时探针的固件复测。真实游戏加入音频和板上呈现后的速度未实测，不能从这些测试 ROM 推断最终游戏负载。

## JIT 提速后的结果

上一节的分析之后，JIT 和两个后端共用的设备、渲染代码又做了一轮优化。数据来自 Sila P4，ESP32-P4 v1.3、360MHz、ESP-IDF v6.1，构建 preset 为 `sila_p4-test-release`，不带 `GBX_PROFILER`；`isolated` 调度，JIT 冷缓存，耗时包含编译。基线是改动前的固件。单位为秒。

| ROM | 基线解释器 | 基线 JIT | 现在解释器 | 现在 JIT | 现在 JIT/解释器 |
|---|---:|---:|---:|---:|---:|

同一次全量运行中，125 个 ROM 的执行时间合计为解释器 38.541 秒、JIT 15.883 秒；里程碑 2 验收时同一批 ROM 是 52.967 秒和 57.394 秒。125 个 ROM 都通过，`oam_bug` 仍然只记录结果，每个 ROM 的 JIT 都拿到了代码池，没有回退。SM83 单步全量 50 万条在两个后端上全部通过，JIT 全部原生执行，用时 160.5 秒。固定回归和 `run_jit.py` 都通过。另外两块板子和 Sila P4 的正式固件、测试固件、性能分析版固件，以及 macOS 上 PC 的 GUI 和无窗口构建都能构建。

测试固件在 ROM 任务的 JIT 初始化之前，片内最大的可执行连续块是 335872 至 344064 字节，JIT 代码池需要 192KiB。改动前的测试固件在 `oam_dma/sources-GS` 加载后只有 200704 字节。

用性能分析版固件看 `cpu_instrs`（数字含采样开销）：CPU 所在的 core 1 两个后端都约 98% 忙。core 0 上渲染的实际工作约占解释器运行时间的 11.5%、JIT 运行时间的 45.7%，其余是渲染线程睡前的轮询和空闲。JIT 这时约为原速的 15 倍，按比例折算，原速时渲染约占 core 0 的 3%，未实测。CPU 与渲染分在两个核上的安排暂时不用调整。正式固件接入游戏以后，core 0 上还有 UI 和呈现任务，渲染线程的轮询时长要在实际负载下重新确定。

剩余的开销如下，都还没有处理：

- PPU 每条可见扫描线仍有 5 个调度事件。`cpu_instrs` 的 JIT 运行中，事件派发和 PPU 的各阶段处理合计约占 core 1 的 28%。
- STAT、LY 这类 IO 读取在 JIT 里都经过 C++ helper，每次还可能重算执行期限。`intr_2_mode0_timing_sprites` 的 JIT 运行中，这条路径约占 core 1 的六成。
- Mealybug 的 `m3_*` 用例在 mode 3 中途改寄存器，渲染线程逐像素查找修改记录，core 0 约 85% 忙，两个后端的耗时接近。
