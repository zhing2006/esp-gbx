# 任务 2-5：PC 显示游戏

让 PC 版的图形界面运行 GB ROM：模拟核心用解释器在工作线程上运行，游戏画面作为独立的纹理显示在游戏窗口里，可以用键盘操作。它用来调试 PPU 和整机行为，不代替板上测试。这个任务依赖 2-1，可以和 2-2 至 2-4 同时进行；因为要检查画面，所以要等 2-4 能渲染 BG 以后才能完成。

开工时在[任务状态](status.md)里把这个任务标为“进行中”。

## 先读

- [PC 图形界面方案](../../host-gui.md)全文，以及[架构](../../architecture.md)的“显示和触摸”和“构建”。
- `host/` 下的现有程序，以及 2-1 的系统接口。

## 范围

- 用命令行参数指定 ROM 的路径，程序启动后载入并运行。不给 ROM 时保持现在的界面。
- 模拟在工作线程上运行，按约 59.73Hz 的节奏推进。PPU 的渲染任务在另一个线程上运行，和板上的双核分工走同一条代码路径。还没有音频，所以节奏由宿主的计时器控制。
- 游戏画面作为独立的 SDL 纹理参与合成，不经过 LVGL，保持原机比例，用最近邻缩放，放在 Tab5 布局的游戏窗口里。
- 键盘映射到 GB 的八个按键，映射写进 PC 图形界面方案。

## 不做

- 音频、卡带存档、菜单和选游戏的界面。
- 屏幕上的触摸控件映射到 GB 按键，这和固件一起放在里程碑 3。
- 桌面调试面板和 JIT。PC 版只有解释器。
- 板上构建、烧录、测试和性能优化，也不修改固件共用的 app、UI 或模拟核心。

## 约束

- 模拟线程和 UI 线程按帧交换画面，不在每个像素或每次访存时加锁。
- 无窗口构建不依赖这部分代码，现有的 CTest 检查继续通过。

## 由你决定

线程和帧交换的方式、键盘映射，以及命令行参数的形式。

## 完成标准

- 测量 PC 的线程、帧交换和呈现开销，针对测量结果优化，并核对代码大小和缓冲占用。本任务不适用板上的双后端优化要求，也不为满足优化项而改动共享核心或加入 JIT。
- macOS 上的 GUI debug 构建能载入 `dmg-acid2` 和 blargg 的 `cpu_instrs`，画面与套件的参考图目测一致。这只是手动检查，不作为测试判定。
- 按下映射的键时，ROM 读到的按键寄存器随之变化。
- GUI 和无窗口的 debug、release 构建都能编译，现有的 CTest 检查通过。Windows 上如果没有构建，汇报时写明未验证。

## 收尾

- 满足全部完成标准以后，在[任务状态](status.md)里把这个任务标为“已完成”。
- 更新 PC 图形界面方案中键盘、游戏画面和运行结构的说明。
- 向用户汇报使用方法和已经验证的平台。

## 实现与验证

PC GUI 已经支持从命令行载入 GB ROM，用独立线程运行解释器，并复用 PPU 的渲染线程。游戏画面通过 SDL 纹理显示，键盘映射、线程交接和运行方式见 [PC 图形界面方案](../../host-gui.md)。

macOS 27.0.1 的 GUI debug 构建已经运行 dmg-acid2 和 blargg 的 cpu_instrs，导出的合成画面与套件参考图目测一致。按键事件经过模拟线程后，JOYP 的值符合选择位和按键状态。GUI、无窗口的 debug 和 release 构建及现有 CTest 均通过，Windows 未验证。

mailbox、SDL 事件唤醒和同编号帧像素比较已经在 macOS 27.0.1、Apple M5 Pro 的 debug 和 release 构建上测量，覆盖线程、帧交换与呈现开销。代码大小和缓冲占用也已经核对。
