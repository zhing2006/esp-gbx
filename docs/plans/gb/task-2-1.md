# 任务 2-1：整机框架和 ROM 测试通路

这是[路线图](../../roadmap.md)里程碑 2 的第一个任务：在 `components/core/` 里搭起 DMG 整机的框架，包括调度器和模拟时间线、内存映射、开机状态和系统接口，并且把整机测试 ROM 接进板上的测试通路，在板上测出两个后端的速度。解释器和 JIT 同时实现，JIT 从这里开始翻译多条指令的块。中断和 TIMA 等功能在 2-2，MBC 和 OAM DMA 在 2-3，PPU 在 2-4，它们都在这个框架上增加，并用这里的测试通路验收。

开工时在[任务状态](status.md)里把这个任务标为“进行中”。

## 范围

整机框架：

- 在 `components/core/` 的 `common/` 下实现调度器和模拟时间线。设备不逐个周期推进，在 CPU 访问它们的寄存器，或者它们登记的事件到期时，才追赶到当前时刻。
- 内存映射，包括 ROM、WRAM 和它的 echo 区、HRAM、IO 寄存器和 IE，并给 2-3、2-4 要接入的 VRAM、OAM 和卡带 RAM 留出位置。可以直接访问的区域不经过逐次的函数调用，IO 寄存器和受限的区域经过处理函数。IO 寄存器的读写屏蔽和未使用位按 Pan Docs 实现，声音寄存器也包括在内，声音生成在里程碑 3。
- 不使用 boot ROM，直接设置 DMG-C 开机后的 CPU 寄存器、IO 寄存器和 DIV 内部计数器的相位，依据 Pan Docs “Power Up Sequence”和 mooneye 的 `boot_*` 用例。实现正常运行时的 DIV 计数、读取和写入清零，用开机测试验证它的初值和相位。
- PPU 推进 LY 和模式，在正确的时刻置 VBlank 的中断请求位，并处理 LCD 的打开和关闭，让测试 ROM 能等到 VBlank。
- 无 MBC 的卡带。系统接口接收调用者已经载入内存的整个 ROM，从 SD 卡读取由调用者负责。
- 系统接口：载入 ROM 和复位、运行到指定的模拟时间或者一帧结束、设置按键、取得画面和串口输出、选择执行后端。音频、卡带存档、即时存档和 RTC 以后再加。
- JIT 在真实的内存映射上翻译多条指令的块，并且从这个任务开始采用寄存器常驻、按需计算标志位和快速访存。设备事件必须在准确的模拟时刻生效。如果事件发生在指令中间，可以执行完当前指令再退出块，但不能继续执行下一条指令，也不能因此回退到解释器。事件发生后的访存，包括快速路径，必须使用生效后的设备状态、访问权限和映射，不能执行已经失效的翻译结果。WRAM 和 HRAM 中的代码被改写以后，对应的块失效。
- 定下双核分工的边界：CPU、调度器、设备时序和 JIT 固定在一个核上，PPU 渲染和以后的混音在另一个核上。系统状态的划分要让另一个核只通过任务拿到数据，不读取正在变化的实时状态。工作线程和任务队列在 2-4 随 PPU 渲染一起实现。
- 详细诊断和追踪的运行时开关，见调试设计“采样、告警和开销”一节。打开以后，模拟所在的核上的探针只把定长记录写进固定容量的缓冲，汇总和处理不在这个核上做。SM83 单步测试的总线记录也用换实现的方式接入，但是不用诊断的丢弃规则：测试记录是判定依据，必须完整，记录不全的用例不能判为通过。编译块数、失效次数和按原因分类的回退次数一直统计。

测试通路：

- 测试索引放在电脑上，覆盖路线图里程碑 2 完成标准列出的全部 ROM，以及只记入报告的 `oam_bug`。每项记录套件、稳定的用例 ID、卡上路径、适用机型、模块标签、结束条件、判定方式和模拟时间上限。mooneye 在 `LD B,B` 处检查寄存器，按套件说明以 120 秒模拟时间为上限；blargg 按说明运行规定的模拟时间以后比对画面；dmg-acid2 在 `LD B,B` 处比对画面。依赖的设备还没有实现，或者要比对画面的用例，在对应的任务完成之前标为执行器尚未支持，不下发执行，也不进行测速。
- 测试固件从 SD 卡把整个 ROM 载入 PSRAM，两个后端共用这份只读数据。runner 按数据清单确认板上的 ROM 和本地一致。
- 解释器和 JIT 各用一个系统实例同时运行。每个实例按双核分工使用两个核：CPU 和 JIT 固定在一个核上，2-4 加入的渲染任务交给另一个核。两个实例怎么分配核由你决定，并写进报告。测速时可以只运行一个后端，让它按游戏运行时的方式占用两个核。JIT 的代码生成和执行固定在同一个核上，见架构文档“JIT 后端”一节。
- 回传的结束状态包括结束原因、结束时的模拟时间、CPU 寄存器、串口输出、各块内存的摘要、JIT 的编译、失效和回退计数，以及每个后端的墙钟耗时。串口输出只用于诊断，不参与判定。
- runner 按套件判据分别判定两个后端，再比较两边的结束状态。两个后端都通过、结束状态一致，并且没有未确认的回退，这个 ROM 才算通过。
- 两边结果不一致时，可以对所选 ROM 运行锁步诊断。JIT 每执行一块，解释器就执行同样多的指令，然后比较 CPU 状态、模拟时间和写入的内存，找出第一个出现差异的块。在这个块里，再比较两边的访存序列，每次访存带上所属指令的地址、访问的地址、数据和模拟时间，报告第一处不一致的访存。块里的访存全部一致、只有块结束时的寄存器不同时，报告这个块的入口、指令范围和不同的寄存器。诊断时 JIT 可以生成带探针的代码来记录访存，但是块的划分、寄存器分配和标志位的计算方式要和正常运行相同，不能改用单指令块，否则可能掩盖只在多条指令的块里出现的问题。
- 报告记录具备执行条件的 ROM 在每个后端上的模拟时间、墙钟耗时和速度倍数，以及整次运行的总耗时。测速用的 ROM 和模拟时长写进报告，测试失败时也保留实测数据。未支持的 ROM 只列出缺少的功能和依赖任务，速度记为“未实测”。
- 可以提前结束运行，前提是能证明判定要用的结果以后不会再变，比如 CPU 停在 IME 为 0 的自跳转循环里，没有正在进行的 DMA，并且已经输出了之后的一整帧。条件和依据写进索引；不能证明时，跑满套件规定的时间。
- runner 能按套件、模块标签和单个 ROM 选择，能只重跑失败的 ROM，数据清单不对应时拒绝执行。

## 不做

- 中断分派、HALT、STOP、TIMA/TMA/TAC 的计时行为和溢出中断、按键和串口，以及 DIV 与这些功能的交互，这些在 2-2。
- MBC1、MBC2、MBC3、MBC5、卡带 RAM 和 OAM DMA，这些在 2-3。
- PPU 的画面渲染、精确的 STAT 时序、VRAM 和 OAM 的访问限制，以及画面的回传和比对，这些在 2-4。
- 声音生成、RTC、卡带存档和即时存档。
- 块间链接和跳过忙等，这些在里程碑 3 按游戏的实测安排。
- 固定回归名单，在 2-6 确定。
- 自动重传、断点续跑和根据 Git diff 选择测试。
- 复用解释器基准。ROM 测试每次都按套件判据判定两个后端，不沿用 SM83 的基准机制。
- Debug 界面。

## 约束

- 性能优先，但是不能改变游戏能观察到的行为。CPU 读写 IO 寄存器时，相关设备必须已经推进到这次访问在 M-cycle 内的准确时刻。
- 每条指令、每次访存都会走到的路径上不分配堆内存，不用虚函数，也不检查诊断开关。打开诊断时换用带探针的实现，比如换一套总线函数，或者清空 JIT 代码缓存以后生成带探针的代码。
- 寄存器常驻的值，在退出块之前、调用可能读取或修改 CPU 状态的 helper 之前，要写回 CPU 状态。按需计算标志位时，块外能观察到的 F 必须和逐条计算的结果相同。
- 可以修改里程碑 1 的总线接口和 JIT 前端，但是 SM83 单步测试要继续使用同一个翻译器，测试只替换总线实现、限制块长度。解释器或共用总线改动以后，原来的解释器基准不再适用，要按真机测试计划重新验证。
- JIT 尽量覆盖所有可能执行代码的区域。RAM 中的代码在执行时可能已经被改写，块使用的指令字节必须和执行时实际取到的相同，用失效、取指校验还是别的办法由你决定。回退到解释器的情况要记录次数和原因，里程碑完成时回退清单应该为空，或者已经和用户确认。
- 调度器放在 `common/`，以后 GBC 和 GBA 也要用。现在只实现 GB 需要的功能，但是时间单位要能表示 GBC 倍速时 CPU 和 PPU 的不同时钟。
- 用模板展开专用版本之前，先测代码体积。
- 控制回传大小。通过的 ROM 只回传结束状态和摘要，不回传整块内存；串口输出设上限，超出时报告截断。
- 两个系统实例除了只读的 ROM 以外不共享可变状态，同时运行不能改变任何一边的结果。
- 计时用测试固件的 release 构建，在 Sila P4 上测。报告写明板型、芯片修订、主频、两个后端是否同时运行，以及核的安排。计时运行时诊断开关关闭。
- 超时、达到模拟时间上限、板子重启、通信错误和判定失败分开报告，任何一种都不能算成通过。
- 只维护最新的测试协议，runner 与固件不匹配时明确报错。

## 由你决定

调度器的数据结构和时间单位、内存映射的分页方式、系统接口的形式、JIT 块的标识和失效粒度、寄存器分配、标志位的计算方式，以及 `common/` 和 `gb/` 下的文件划分。测试通路方面，索引的文件格式、结束状态的字段和摘要算法、锁步诊断的实现、检测提前结束的方式，以及 runner 的命令行和报告格式也由你决定。选择的理由写在代码注释里，字段布局写在协议头文件的注释里。如果改变了模块边界，同步更新架构文档。

## 开发期间的验证

- 可以在 PC 上写临时程序，用解释器运行 ROM 来排错。临时程序不提交，也不写进文档。
- JIT 的多条指令块、事件退出和 RAM 中的代码改写，可以先用 `tests/runner/run_jit.py` 的指令序列检查在板上对照解释器。

## 完成标准

- 在 Sila P4 上，全部 SM83 单步用例在两个后端上通过：解释器有新的套件验证基准，JIT 与它的结果全部一致，回退清单为空。
- `run_jit.py` 的检查在板上全部通过，覆盖多条指令的块、按事件退出，以及改写 WRAM 和 HRAM 中已经执行过的代码。
- 在 Sila P4 上，测试索引中只依赖本任务功能的 mooneye 用例在两个后端上通过，结果一致，回退清单为空或者已经和用户确认。哪些用例属于这一类，由索引的模块标签确定；任务结束时列出这些用例，以及其余 ROM 依赖的任务。
- 确认比对和诊断真的能发现错误：临时改错 JIT 在多条指令的块里对一条指令的翻译，runner 能指出 JIT 失败和两边不一致，锁步诊断能报告出错的块和第一处不一致的访存或寄存器，然后改回去。这一步不留下测试代码。
- 报告给出具备执行条件的 ROM 在两个后端上的速度，未支持的 ROM 不参与测速或耗时外推。时间预算估算注明尚未测量的部分。如果已有实测数据表明 ROM 测试或者 SM83 单步全量会超出路线图的时间预算，先找出瓶颈，和用户确认优化方案，再开始 2-2。
- 只重跑失败 ROM 的功能可用，数据清单不对应时 runner 拒绝执行。
- PC 的 debug 构建，以及三块板子的正式固件和测试固件都能构建，没有新的警告。

## 收尾

- 满足全部完成标准以后，在[任务状态](status.md)里把这个任务标为“已完成”。
- 在架构文档中说明调度器、内存映射、系统接口和 JIT 块的模块边界，以及不写下来就容易出错的约束。在真机测试计划中写明 ROM 测试的运行方法和判据，验证结论保存在运行报告中。

## 实现与验证

整机框架、寄存器常驻与延迟标志位的多指令 JIT、快速访存、代码失效和 ROM 测试通路已经实现。模块边界及事件约束见[架构](../../architecture.md#模拟器)。运行方法见[真机测试计划](../../hardware-testing.md#运行整机-rom)，ROM 的支持范围和依赖任务以测试索引为准，板上验证结果和速度保存在运行报告中。未支持的 ROM 不运行，也不参与耗时外推。
