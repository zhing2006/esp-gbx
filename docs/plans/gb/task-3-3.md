# 任务 3-3：主界面、菜单和卡带存档

先设计再实现启动游戏之前的主界面、游戏中的暂停菜单和 SETTINGS 页面，然后按产品设计“存档”一节实现卡带存档的写回，并把 3-1 的 MBC3 RTC 接到板上的 RTC。菜单都画在 480×320 的游戏窗口里，三块板子共用一套布局；设计要先经过用户确认，然后才能实现。写卡在另一个核上进行，不阻塞模拟。这个任务依赖 3-1 和 3-2。

## 范围

界面设计：

- 主界面、ROMS 列表、SETTINGS、暂停菜单，以及存档和 RTC 提示的布局与效果图，风格和现有外壳一致，写进 UI 布局文档，并用 `tools/ui/` 生成和检查。
- 设计里要定下操作方式，比如直接点击游戏窗口里的选项、用屏幕上的方向键和 A、B，或者两者都支持。文件名可能含有中文、日文等字符，界面字体没有对应字形时怎么显示，也在设计里定下来。
- 设计完成以后先交给用户确认，确认以后再开始实现。

菜单和设置：

- 主界面在启动游戏之前进入，有 ROMS、SETTINGS 和 DEBUG 三个入口。入口是可以增加的列表，以后添加入口时不用改结构。本里程碑没有 Debug 界面，DEBUG 入口显示为不可用。
- ROMS 列表递归扫描卡上的 `roms/`，跳过以 `.` 开头的文件和目录。机型按 ROM 头判断，不看扩展名和所在目录。当前不能运行的 ROM，比如 GBC 专用和 GBA 的 ROM，可以列出，但不能启动。选中以后进入 `LOADING`，载入失败时显示原因并回到列表。
- 游戏中按 MENU 键，模拟在帧边界暂停，声音停止，弹出暂停菜单，运行状态变成 `PAUSE`。暂停菜单有 SETTINGS、QUIT 和 DEBUG，显示存档状态和未处理的错误，也要能回到游戏。QUIT 先提交卡带存档，等写入完成再回到主界面。
- SETTINGS 在主界面和暂停菜单里是同一个页面，本里程碑有音量、背光亮度、执行后端和黑白游戏的调色板四项。每一项标明游戏运行中能不能修改，不能修改的在暂停菜单里显示为灰色。当前平台不支持的项也显示为灰色，不隐藏，比如 PC 上的背光亮度和 JIT。音量、亮度和调色板立即生效。切换后端时，在帧边界调用 `select_backend()`，然后从当前状态继续运行。设置在重启以后保留。
- 四块板子的背光都从开关改成 PWM 调光。
- PC 版使用同一套界面。命令行给了 ROM 时直接启动这个 ROM，没有给时进入主界面。
- 菜单操作有提示音，比如移动光标、确认、返回、弹出提示框，以及在不能操作的项上按 A。提示音不是模拟的声音，采样率和位深不受 GB APU 的限制，素材不能带来许可证问题。音量跟随 VOLUME 设置，PC 版也有。

卡带存档：

- 带电池的卡带才有存档文件。文件放在 `saves/` 下与 `roms/` 相同的子目录里，`<ROM 名>.0.sav` 和 `<ROM 名>.1.sav` 轮流写，比如 `roms/gb/rpg/Pokemon Yellow.gb` 的存档是 `saves/gb/rpg/Pokemon Yellow.0.sav` 和 `.1.sav`。每份记录序号、校验、ROM 头的标识和全部卡带 RAM，MBC3 带 RTC 的卡带还记录 RTC 状态和保存时板上 RTC 的时间。
- 启动游戏时读取两份文件，使用校验正确、序号较新的一份。ROM 头的标识和当前 ROM 对不上时，先提示用户，再按用户的选择加载或者不加载。两份都无效时，提示用户以后从空白的卡带 RAM 开始。
- 已有的存档没有载入时，也就是两份都无效，或者用户在标识不符时选择不加载，第一次写回之前先把两份复制成 `<ROM 名>.0.sav.old` 和 `<ROM 名>.1.sav.old`，覆盖上一次的备份，所以每个 ROM 最多有这 4 个文件。备份写完并刷新存储以后才开始写回，复制途中掉电时，原来的两份还没有被改动。
- 卡带 RAM 或 RTC 被改写以后标记为脏，最后一次修改以后延迟一小段时间写回。写入覆盖较旧的那一份，写完以后刷新存储，确认成功才认为这一份已经提交。较新的有效存档在新的一份提交之前一直保留。
- 模拟所在的核只在帧边界复制卡带 RAM 和 RTC 状态。编码、校验、写文件和刷新都在另一个核上进行。
- 存档状态按调试设计在 `CLEAN`、`DIRTY`、`WRITING` 和 `ERROR` 之间切换，SAVE 灯随之显示。写入期间又有修改时，写完仍然是 `DIRTY`。失败状态保留到重试成功或者用户处理，暂停菜单显示 `ERROR` 并提供重试，失败原因在 ERRORS 页面查看。存档失败和内存分配失败这类明确的错误点亮 ERR 灯，直到用户在 ERRORS 页面查看并清除。

RTC：

- 平台接口增加读取板上 RTC 的时间和可信状态。RX8025T 和 RX8130CE 按板子文档检查 VLF 和日期是否合法，没有 RTC 的板子报告不可信。PC 使用系统时钟，视为可信。
- 启动游戏时，如果存档里保存时的时间和当前板上 RTC 的时间都可信，就把这段时间用 3-1 的接口加到 RTC 上。板上 RTC 不可信或者时间倒退时不补算，并在界面上提示。
- 游戏暂停期间经过的时间用宿主的单调时钟计算，恢复运行时补算。

## 不做

- Debug 界面，本任务只放入口。
- 即时存档和读档，这些在里程碑 4。
- 设置板上 RTC 时间的界面，以及上面四项以外的设置项。
- 2 倍速运行，这在 4-3。
- GBA 的存档类型。

## 约束

- 菜单、列表扫描、设置的读写和存档的工作都不在模拟所在的核上运行，除了在帧边界复制存档状态。扫描大目录和写卡时，界面不能卡住，模拟也不能等待。
- 暂停以后从同一个状态继续运行，暂停不能改变模拟结果。
- 菜单画在游戏窗口里时，呈现任务不再向这个窗口写游戏帧；回到游戏以后再恢复。UI 和游戏画面不能同时写同一块区域。LVGL 对象只能在 LVGL 任务里，或者持有 `display::lock()` 时操作。
- 每条指令、每次访存的路径上不为脏标记增加检查。JIT 的快速访存会直接写卡带 RAM，检测脏数据的方式不能漏掉这些写入。
- FAT 上的一次 rename 不能当作掉电安全的保证。
- 界面上的文字是英文。文件名按 UTF-8 处理，FatFs 的长文件名和编码配置要和这一点一致。
- 存档文件的格式写在代码注释里，文档只写约定。

## 由你决定

操作方式和字形缺失时的显示办法在设计阶段提出，由用户确认。设置的存储位置和格式、存档的文件格式和校验算法、写回的延迟时长、检测脏数据的方式、RTC 驱动放在 `drivers/` 还是 `boards/`，以及菜单状态在 app 和 ui 之间的划分由你决定，理由写在代码注释里。

## 完成标准

- 设计已经由用户确认。UI 布局文档有新界面的说明和效果图，`render_previews.py --check` 通过。
- 在 Sila P4 上，正式固件开机进入主界面，可以从 ROMS 启动 ROM。游戏中按 MENU 暂停，在 SETTINGS 里调音量、亮度和调色板，切换后端，然后回到游戏，画面、亮度、声音和后端灯都正常；QUIT 回到主界面以后，可以再启动另一个 ROM。子目录、`._` 开头的文件、不能运行的 ROM 和中文、日文文件名都按设计显示和处理。设置在重启以后仍然保留。
- 在 Sila P4 上，用 3-2 列出的本地 Pokémon Gold 或 Pokémon Yellow 检查存档的正常流程：存档从 `DIRTY` 经过 `WRITING` 回到 `CLEAN`，QUIT 时立即提交，写入期间又有修改时保持 `DIRTY`。拔掉 SD 卡或卡满时显示 `ERROR` 并点亮 ERR 灯，恢复以后重试成功，回到 `CLEAN`。ROM 头的标识不符时提示用户，按用户的选择加载或者不加载。
- 在 Sila P4 上做写入中断测试：在写卡带存档的不同阶段用 CH340 的 RTS 复位芯片，重复 10 次，覆盖写数据和刷新存储这两个阶段。芯片复位不切断 SD 卡的供电，所以这项测试检查的是存档协议能不能在写到一半时保住上一份存档，不包括卡本身在掉电时写坏的情况。为了容易切在写入过程中，可以在开发构建里临时让存档反复写回，并通过串口输出每次提交的序号。每次重启以后都要能读到一份有效存档，它的内容和复位前最后一次提交的那份相同；如果复位时正在写的那份已经完整写好，也可以是这一份。
- 用这两个游戏检查 32KiB、4 个 bank 的卡带 RAM：在游戏里存档以后 QUIT，再启动这个游戏，读到的存档和退出前一致。这是人工检查。
- Tab5 有带后备电源的 RTC，在 Tab5 上检查：运行 MBC3 带 RTC 的 ROM，比如本地的 Pokémon Gold，退出、关机一段时间再开机，RTC 补算了关机期间的时间，并且和板上 RTC 经过的时间一致。Sila P4 上确认会提示 RTC 不可信。
- 在 Sila P4 上测量写回期间模拟所在的核的帧耗时，确认没有因为写卡而等待。
- PC 版的主界面、菜单、设置、卡带存档和 RTC 补算都能用，存档写在本地目录里。GUI 和无窗口的构建都能编译，现有的 CTest 检查通过。
