# 任务 2-4：PPU

实现 DMG 的 PPU：模式时序、STAT 中断、VRAM 和 OAM 的访问限制，以及 BG、窗口和 OBJ 的渲染，按原机分辨率输出画面。解释器和 JIT 同时实现，画面渲染按双核分工放在另一个核上。测试通路加入画面回传和参考图比对，用比对画面的 ROM 验收。这个任务依赖 2-3，2-5 的 PC 图形界面可以用来调试画面。

开工时在[任务状态](status.md)里把这个任务标为“进行中”。

- dmg-acid2、mooneye 和 blargg 的 `game-boy-test-roms-howto.md`，以及 Mealybug 的说明。
- [真机测试计划](../../hardware-testing.md)“通过判据”一节中比对画面的规定。

## 范围

- 模式切换和各模式的时长，mode 3 的长度随 SCX、窗口和 OBJ 变化。LCD 打开以后第一行的时序按 Pan Docs 和 mooneye 的 `lcdon_*` 用例实现。
- STAT、LYC 比较和 STAT 中断，包括几个中断条件先后满足时的阻塞。
- VRAM 和 OAM 在各模式下对 CPU 的访问限制。
- BG、窗口和 OBJ 的渲染，DMG 的 OBJ 优先级、每行最多 10 个 OBJ 的限制，以及 BGP、OBP0 和 OBP1 调色板。
- 画面渲染在另一个核上。CPU 所在的核计算模式时序、STAT 和中断，按扫描线把渲染任务交给另一个核。任务带上这一行用到的寄存器状态，以及这一行期间寄存器、VRAM 和 OAM 的修改和发生的位置。mode 3 期间的修改按写入的时刻分段生效，本里程碑不保证生效的像素位置和原机完全相同，Mealybug 的结果作为参考记入报告。
- 平台接口加入固定在指定核上的工作线程和核间通知，ESP 上用 FreeRTOS 实现，PC 上用线程实现。任务队列的容量固定，队列满了时 CPU 所在的核等待，不丢弃任务。
- 按原机分辨率输出 BGR555 帧，黑白游戏使用固定的灰阶调色板。测试直接取得每个像素的灰阶等级，不从 BGR555 反推。
- JIT 读写 PPU 寄存器时经过处理函数，先把 PPU 推进到访问的时刻。VRAM 和 OAM 在受限期间不能走快速访存。
- 测试通路回传最终帧，每像素 2 位，一帧 5,760 字节。取最终帧之前，先等渲染所在的核处理完已经提交的任务。两个后端的帧摘要相同时只回传一份。runner 按套件规定的四级灰阶读取参考图并逐像素比对，失败时在报告里保存实际帧和差异图。
- 测试索引中比对画面的 ROM 改为已支持，blargg 的提前结束条件按 2-1 的规则逐个确认。
- `tools/prepare_gb_tests.py` 和测试索引加入 Mealybug 中带 DMG 参考图（文件名以 `_dmg_blob` 结尾）的用例。它们的结果记入报告，不作为完成条件。这些参考图对应哪个 DMG 修订，要先按 Mealybug 的资料确认，确认不了时在报告中注明。

## 不做

- GBC 的调色板、VRAM bank 和 HDMA。
- 在板子的屏幕上显示游戏画面，这在里程碑 3。
- 把 `oam_bug` 和 Mealybug 作为完成条件。

## 约束

- 性能优先，不逐点运行像素 FIFO。没有中途写入的行一次渲染完，mode 3 中途有写入的行按写入的位置分段渲染。mode 3 的长度在 CPU 所在的核上计算，不等渲染结果。
- 渲染所在的核只使用任务里的数据，不读取 CPU 所在的核正在修改的状态。如果也支持在同一个核上渲染，比如负载轻的时候，两种方式渲染出的画面必须相同，测试要覆盖实际使用的方式。
- 画面只和套件提供的参考图比较，不把模拟器自己的输出存成标准答案。
- 回退、测试时间和回传大小沿用 2-1 的规则。

## 由你决定

渲染任务的格式、VRAM 和 OAM 修改的传递方式、分段渲染的实现、mode 3 长度的计算方式，以及帧缓冲的格式和交换方式。

## 完成标准

- 按[双后端优化要求](../../hardware-testing.md#每个任务的双后端优化)，分别分析和优化解释器、JIT 下的 PPU 同步、受限访存及渲染任务开销，提交两边各自的优化前后数据和剩余瓶颈。共用渲染路径的收益也要在两个后端下核对，不能只测一边。完成优化并清理临时计时后，再做最终验证。
- 在 Sila P4 上，两个后端都通过 `dmg-acid2`、mooneye `acceptance` 下 PPU 相关的用例，以及 blargg 的 `cpu_instrs`、`instr_timing`、`mem_timing`、`mem_timing-2` 和 `halt_bug`，结果一致，回退清单为空或者已经和用户确认。之前通过且受本任务影响的 ROM 仍然通过。
- SM83 单步只在实际改动影响 CPU 执行时运行，按[真机测试计划](../../hardware-testing.md#选择本次运行的测试)选择受影响的操作码组；通用路径的影响无法缩小时才跑全量，不因任务收尾自动跑全量。
- 确认画面比对真的能发现错误：临时改错一个调色板的映射，runner 能指出受影响的 ROM 并保存差异图，然后改回去。这一步不留下测试代码。
- 报告给出这些 ROM 的速度和核的安排，按实测速度估算的全量耗时仍在路线图的预算以内；超出时先和用户确认优化方案。
- 另外两块板子的正式固件和测试固件都还能构建。

## 实现与验证

DMG PPU、双核渲染、帧回传和参考图比较已经实现，模块边界见[架构](../../architecture.md#模拟器)。行中修改按照取图和像素输出阶段采样，处理 SCX 锁存、调色板写入、OBJ 取图和窗口重触发。

本任务要求的 ROM 和受影响的回归已经在 Sila P4 的解释器与 JIT 上通过，两个后端的结果一致，没有回退。Mealybug 带 DMG 参考图的 24 个用例也已经逐像素通过。`oam_bug` 在两个后端上都显示“Failed #2”，OAM corruption 仍未实现。它的参考图还包含套件规定以外的灰阶值，因此自动画面比较无法判定。该项按计划记录，没有计为通过。

解释器和 JIT 的优化数据、片内代码缓存实验、全量 ROM 耗时估算及验证记录保存在本地运行报告中。测试选择和判据见[真机测试计划](../../hardware-testing.md)。本次没有修改平坦总线的指令语义，因此没有运行全量 SM83 单步；整机 JIT 的划分、追踪、代码改写和 bank 访问由板上的针对性检查与所选 ROM 验证。PC 检查及另外两块板子的正式固件、测试固件构建已经通过。

解释器、设备执行代码和 JIT 运行时 helper 的布局已经固定，说明见[架构文档](../../architecture.md)。实验和数据保存在本地运行报告中。
