# 任务 4-3：2 倍速和双核负载均衡

让速度拨杆的 2X 位置生效，游戏按 2 倍原速运行；同时按两个核的实测负载重新分配工作。4-1 和 4-2 做完以后，可以用即时存档直接回到负载重的位置，在同一个状态上反复测量和比较，所以这个任务放在即时存档之后。这个任务依赖 4-2。

开工时在[任务状态](status.md)里把这个任务标为“进行中”。

## 先读

- [路线图](../../roadmap.md)的里程碑 4 和“后续优化”，[产品设计](../../product-design.md)的“音画同步”和“双核分工”。
- [架构](../../architecture.md)的“模拟器”全文，尤其是 PPU 和 APU 在两个核之间的划分、任务队列的交接，以及呈现任务和 LVGL 所在的核。
- [调试设计](../../debug-design.md)中 `SPEED` 的统计口径和 `FAST` 状态，[UI 布局](../../ui-layouts/index.md)中的速度拨杆。
- [真机测试计划](../../hardware-testing.md)的“每个任务的双后端优化”，以及 3-2 报告中两个核的负载测量。
- 4-1 的状态接口和 4-2 的存档文件。

## 范围

- 速度拨杆拨到 2X 时，模拟按 2 倍原速运行，拨回 1X 时恢复原速。两个后端都支持。串口控制台的 `speed 1|2` 和拨杆的作用相同。
- 2 倍速时 `SPEED` 格的单位显示 `FAST`，速度按调试设计的要求和原速运行分开统计。`AUDIO` 格的主值显示 `OFF`，欠载次数和最低水位显示 `--`。`FRAME`、`AUDIO` 等指标在 2 倍速下的含义写进调试设计。
- 暂停和切换速度时，VFD 不变成 `--` 或 `WARMUP`：暂停期间读数停在暂停前的值，`MEM` 照常刷新；继续运行或切换速度以后，新窗口攒够数据之前保持原来的读数。载入新游戏时读数清空。
- 2 倍速时关闭声音：APU 的采样率设成 0，混音器只处理寄存器写入，不生成 PCM；节奏改由墙钟控制，按 2 倍原速运行。拨回 1X 时恢复采样率和按音频水位控制的节奏，重新预填充，预填充期间不计欠载。
- 2 倍速时模拟每秒产出约 120 帧，屏幕最多显示约 60 帧，所以只画会显示的帧。每帧开始运行时，按 1X 的帧间隔排出显示时刻，挑离显示时刻最近的帧来画：跑满 2 倍时就是隔一帧画一帧，跑不满时补到约每秒 60 帧。不画的帧，CPU 所在的核不交出扫描线任务，显存和 OAM 的修改跟着下一个要画的帧交给渲染线程；工作线程不渲染、不转格式。模拟结果不变。
- 2X 时 core 1 只运行模拟，保持现在的分工。1X 时工作线程做完任务以后不再空转等下一行，没有任务就睡眠，由 CPU 所在的核成批唤醒，把 core 0 的时间留给呈现任务和 LVGL。
- 执行核心的热代码和机器状态放进片内 RAM，`app.cpp` 的全局对象移到 PSRAM，给 JIT 代码池留出连续的片内空间。
- 负载用 V-Rally Championship Edition 的两个即时存档测量，槽位 1 和 2 由用户存在卡上。每次测量都载入同一个存档，载入后不按键，统计 10 秒。

## 不做

- 2 倍以外的速度和不限速的快进。
- GBC 的 CPU 倍速模式（KEY1），这属于 GBC。
- JIT 的块间连接和跳过忙等，这些在 3-4。

## 约束

- 1X 原速时仍然由音频缓冲的水位控制节奏，行为、测试结果和速度不能因为本任务变差。
- 重新分配工作不能改变模拟结果。另一个核上的渲染和混音仍然只读取任务里复制的寄存器和显存，不读实时状态。
- 改动解释器、设备执行代码或 JIT 运行时 helper 时，按 `cmake/core_layout.cmake` 的规则放置，检查 map 中的地址。
- 每条指令、每次访存的路径上不为 2 倍速增加检查。

## 由你决定

工作在两个核之间的划分方式、2 倍速时节奏控制的实现，以及测量位置的选择。选择的理由写在代码注释里。

## 完成标准

- 在 Sila P4 上，两个后端都能用速度拨杆在 1X 和 2X 之间切换。用户按测试点在板上试玩 Dangan GB、Pokémon Gold、Pokémon Yellow 和 V-Rally，确认能跑满 2 倍，画面和声音正常。
- 用 V-Rally 的两个存档，在两个后端的 1X 和 2X 下记录 `SPEED`、`FRAME` p95、两个核的 `IDLE`、欠载次数和各任务占核的比例，以及板型、芯片修订和主频。1X 下比较工作线程改动前后的数据，两个核各自的得失由用户确认取舍。
- 改动影响了哪些模块，就按[真机测试计划](../../hardware-testing.md#选择本次运行的测试)运行这些模块的 ROM，开发完就运行。两个后端全部通过，结果一致。
- PC 的 debug 构建，以及全部板子的正式固件和测试固件都能构建，没有新的警告。全部板子的构建在用户确认可以提交时做一次，开发过程中只构建要刷进板子的固件和 PC 的 debug 版。

## 收尾

- 满足全部完成标准以后，在[任务状态](status.md)里把这个任务标为“已完成”。
- 在架构文档中更新两个核之间的工作划分和 2 倍速的节奏，在调试设计中写明 2 倍速时各指标的含义和 `speed` 命令，在 UI 布局中写明 2X 时的显示。
- 向用户汇报使用方法、2 倍速的实测结果、两个核负载的前后对比和剩余瓶颈。

## 实现与验证

### 已经完成

- 拨杆和 `speed` 命令通过 `Game::set_fast()` 在帧边界切换速度，见 `components/app/src/game.cpp` 的 `change_speed()`。载入新游戏时沿用拨杆的位置。
- 画哪一帧由 `Game::draw_now()` 决定，`gb::System::set_drawing()` 让 PPU 跳过不画的帧。绘制开关只在帧之间改变：一次运行如果停在帧中间（STOP，或者 LCD 在运行中途打开），下一次运行沿用原来的决定，免得把前半帧的旧扫描线和后半帧拼在一起发布。LY 进入 144 以后还要过 16 tick，到 VBlank 事件才交付这一帧，这段时间也算在帧内。`EMU` 按交付的帧编号之差累加，所以没画的帧也计入；2X 时 `FRAME` 只有画出来的帧有样本，样本从切速以后开始运行的第一帧算起，切速时还在工作线程里的帧算旧速度的。
- mode 3 开头 20 tick 内写 SCX 会重新计算传输长度和 HBlank 时刻。这段时序不依赖扫描线任务，PPU 自己保存这一行选出的精灵，不画的帧也照常计算。即时存档的格式升到版本 2，状态里加了这一行选出的精灵和这一帧画不画，从帧中间读档时这一帧按存档时的决定继续。版本 1 的存档不能再读。
- VFD 读数的保持在 `components/app/src/app.cpp` 的 `status()` 里。
- 模拟核心只在 `Ppu::begin_line` 和 `Ppu::begin_transfer` 各加了一个判断，从 `Ppu::advance` 开始的热代码整体后移 8 字节。不测量这次移动的影响。
- 用户在 Sila P4 上按测试点试玩了两个后端，Dangan GB、Pokémon Gold、Pokémon Yellow 和 V-Rally 都能跑满 2 倍，画面、声音和 VFD 正常。
- 用测试固件运行 PPU 模块（`run_roms.py --module ppu`）的 43 个 ROM：42 个通过，两个后端结果一致；`blargg/oam_bug` 只记入报告，套件没有可用的参考，结果为 `UNJUDGEABLE_REFERENCE`。存档升到版本 2 以后，带存档点的 8 个 ROM（`run_roms.py --states`）全部通过。
- 在 PC 上临时比较了 168 个 ROM（mooneye acceptance、mealybug、blargg）在全画、全跳和隔帧画三种情况下的运行，每次访存的地址、数据和时刻都一致。这些 ROM 都没有在不画的帧里于 mode 3 开头写 SCX 并观察 HBlank 时刻，所以修正 SCX 时序之前也一致，现有套件覆盖不到这条路径。
- 在 PC 上临时检查了存档读档：51 个 ROM（mealybug、mooneye 的 ppu 和 oam_dma、dmg-acid2）在全画和全跳两种情况下，各在约 30 个时刻存档，其中一部分落在 LY=144、帧事件之前；再读进绘制开关相反的机器接着运行。2982 次续跑的每次访存，以及交付的每一帧的编号和像素，都和不中断的运行一致。临时去掉读档时对“画不画”的恢复，有 98/124 次不一致，说明这个检查能发现画面拼接。

- 1X 时工作线程不轮询：`Offload::set_polling()` 开关轮询，`Game` 在载入和切速时按速度设置，2X 轮询，1X 不轮询，理由写在 `components/app/src/game.h`。默认轮询，测试固件不变。
- 执行核心放进片内：`tools/link_core_layout.py` 把原来排在 flash 代码开头的那组对象放进 IRAM，只读数据放进片内数据段，共 68 KB；`gb::System`（23.6 KB）用 `platform::allocate_internal()` 分配在片内；`components/app/linker.lf` 把 `app.cpp` 的 BSS（44 KB，主要是 `game` 和 `page`）放进 PSRAM。只搬代码时，片内低端区装不下 `game` 和 `page`，它们被放到高端区开头，JIT 的 224 KB 代码池凑不出连续空间，JIT 无法启动。游戏运行时片内剩余从 146 KB 降到 98 KB（JIT 代码池已经分配）。
- 搬迁以后用测试固件运行固定回归（`run_roms.py --regression`）和带存档点的 ROM（`--states`），10 个和 8 个全部通过，两个后端结果一致，测试固件同时创建两个 `System` 时片内内存也够用。

### 负载测量

都在 Sila P4 上测量，芯片 ESP32-P4 v1.3，主频 360 MHz，构建 preset 为 `sila_p4-profile`，数字包含 profile 版计数的开销。用 V-Rally 槽位 1 和 2 的版本 2 存档：用串口控制台载入 ROM，通过 `keys` 操作暂停菜单载入槽位，用 `speed` 设定速度后继续运行，4 秒后用 `stat 2` 和 `tasks 10000` 采集 10 秒。所有组的 `SPEED` 都是 100% 或 200%，欠载都是 0，`DRW` 在 58.5 到 60.5 之间。`FRAME` 取 10 秒里 5 个窗口的平均值。

| 后端 | 槽位 | core 0 空闲 % | core 1 空闲 % | 工作线程 % | 模拟任务 % | `FRAME` p95 / 平均 ms |
|---|---|---|---|---|---|---|
| JIT | 1 | 54.4 | 78.9 | 30.0 | 21.1 | 6.7 / 5.9 |
| JIT | 2 | 56.6 | 75.5 | 27.6 | 24.5 | 5.5 / 5.4 |
| 解释器 | 1 | 41.5 | 63.3 | 43.3 | 36.7 | 9.3 / 8.4 |
| 解释器 | 2 | 45.2 | 61.0 | 38.2 | 39.1 | 7.8 / 7.7 |

不轮询时 core 0 多出 5 到 17 个点的空闲，但 core 1 的模拟任务多花 0.3 到 4.5 个点，`FRAME` 的最大值在 JIT 下多 1.4 到 2.5 ms，在解释器下多 3 到 4 ms。CPU 所在的核每帧唤醒工作线程约 12 次，每次约 5.6 µs，只占 core 1 约 0.3 个点。`prof` 采样显示，多出来的时间均匀地分布在全部模拟代码上，执行的指令相同，每条指令变慢了 10% 到 15%。让 core 0 不进入 WFI，结果在噪声范围内，不能确定有改善。在 core 0 上放一个和工作线程同优先级的任务，只在模拟一帧期间占住 core 0，让工作线程照常睡眠和被唤醒，解释器槽位 2 的模拟任务回到 39.1 和 39.2，同一轮里开轮询是 39.0 和 40.3，不轮询是 41.9 和 41.2。所以 core 1 变慢，是因为呈现任务、LVGL 和 `main` 在模拟期间也在 core 0 上运行；P4 的代码和大块数据都在 PSRAM，两个核共用 L2 缓存和 PSRAM。开轮询时，空转的工作线程让这些任务等到模拟结束以后才运行。

### 收尾

- 架构文档写了两个核的分工、2 倍速的节奏和跳帧，以及执行核心在片内 RAM 的位置；调试设计写了 2 倍速时各指标的含义、VFD 读数的保持和 `speed` 命令；UI 布局写了 2X 时的显示。
- 片内 RAM 的整理放在路线图“后续优化”里，没有在本任务里做。
