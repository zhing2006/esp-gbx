# 任务 5-1：片内 RAM 整理

这是[路线图](../../roadmap.md)里程碑 5 的第一个任务：列出片内 RAM 被哪些代码、数据和分配占用，把访问不频繁的部分移到 PSRAM，腾出的空间留作余量。L2 cache 的大小和 JIT 代码池保持现在的配置，它们怎样调整在 5-2 里和代码池的位置一起决定。这个任务依赖 4-3。

开工时在[任务状态](status.md)里把这个任务标为“进行中”。

## 先读

- [路线图](../../roadmap.md)的里程碑 5，[产品设计](../../product-design.md)的“目标平台”和“内存布局”。
- [架构](../../architecture.md)的“JIT 后端”“构建”和“代码规则”，尤其是热代码的链接规则、`gb::System` 的分配和 `components/app/linker.lf`。
- [调试设计](../../debug-design.md)“宿主 CPU 和内存”一节中片内内存的口径，以及游戏页的 `MEM` 格。
- [真机测试计划](../../hardware-testing.md)的“每个任务的双后端优化”和“选择本次运行的测试”。
- [4-3](task-4-3.md) 的负载测量方法，以及执行核心放进片内的做法和测量数据。

## 范围

- 列出片内 RAM 的占用。静态部分按组件和对象列出 IRAM 代码、片内的 `.data` 和 `.bss`。动态部分按来源列出：任务栈、驱动和 DMA 缓冲、显示和 LVGL、`gb::System`、JIT 的代码池、gateway 和槽数组，以及 IDF 自己的分配。在启动以后、主界面、用两个后端运行游戏时，分别记录片内空闲和最大可分配块。正式固件和测试固件各记一份，测试固件同时创建两个 `System`。
- 按访问频率区分冷热。每条指令、每次访存、每条扫描线、每个音频样本都会用到的算热；只在启动、载入 ROM、菜单、存档、串口命令或测试单步时用到的算冷。release 镜像里已经能看到几项冷的：平坦总线版的 `sm83_step` 约 8KB 在 IRAM 里，它只给单步测试用；`menus` 约 2.4KB 在片内数据段；串口控制台 `send_pixels` 的行缓冲约 2KB 在片内 `.bss`。
- 冷的代码通过链接配置放回 flash 段，运行时从 PSRAM 执行。冷的数据和静态缓冲用链接配置或 `EXT_RAM_BSS_ATTR` 放进 PSRAM，动态分配改用 PSRAM 的能力。IDF 自己放进 IRAM 的函数，如果有配置项可以移到 flash，先按配置项的说明核对约束再用。
- 腾出多少不设目标。报告给出每一项搬迁的内容和大小，以及搬迁前后的片内空闲和最大可分配块。
- 性能用 V-Rally Championship Edition 的两个即时存档测量，做法和 4-3 相同：构建 preset 为 `sila_p4-profile`，载入同一个槽位以后不按键，用 `stat` 和 `tasks` 统计 10 秒。两个后端各测 1X 和 2X。基线在开工时用同一版代码重新测一次，不直接用 4-3 的数据。

## 不做

- 改变 L2 cache 的大小、JIT 代码池的大小和位置，这些在 5-2。
- 为了腾空间缩小缓冲、减少任务栈到没有余量，或者去掉功能。
- 改动模拟核心和 JIT 的数据结构。

## 约束

- ISR 和它调用的代码与数据、flash 操作期间要运行的代码、硬件要求放在片内的 DMA 缓冲，都不能移到 PSRAM。每一项都按 IDF 文档核对，依据写在链接配置或代码注释里。
- 执行核心的热代码和机器状态留在片内。改动它们的位置时，按 `cmake/core_layout.cmake` 的规则放置，检查 map 中的地址；布局变化对性能的影响要上板测量。
- 正式固件和测试固件使用同一套布局规则。
- 不改变模拟结果，也不改变界面、声音和存档的行为。
- 每条指令、每次访存的路径上不增加检查。

## 由你决定

清单的分组方式、哪些项搬到 PSRAM，以及用哪种方式搬。不能搬或者搬了变慢的项，原因写在链接配置或代码注释里。

## 完成标准

- 报告给出片内 RAM 的清单和每项搬迁的内容、大小，以及搬迁前后的静态段大小、各时刻的片内空闲和最大可分配块，正式固件和测试固件各一份。
- 在 Sila P4 上用 V-Rally 的两个存档，在两个后端的 1X 和 2X 下比较搬迁前后的 `SPEED`、模拟任务的比例、两个核的 `IDLE`、`FRAME` p95 和平均值、欠载次数，记录板型、芯片修订和主频。超出测量波动的变差要撤销对应的搬迁，或者由用户确认取舍。
- 两个后端都通过固定回归（`run_roms.py --regression`）和带存档点的 ROM（`--states`），结果一致。
- 用户在板上检查菜单、卡带存档、即时存档、声音和画面，确认正常。
- PC 的 debug 构建，以及全部板子的正式固件和测试固件都能构建，没有新的警告。全部板子的构建在用户确认可以提交时做一次，开发过程中只构建要刷进板子的固件和 PC 的 debug 版。

## 收尾

- 满足全部完成标准以后，在[任务状态](status.md)里把这个任务标为“已完成”。
- 在架构文档的“代码规则”中写明哪些代码和数据必须在片内、哪些放进 PSRAM，以及分别由哪个链接配置或分配接口控制。清单和测量数据只写在本文件和运行报告里。
- 向用户汇报片内 RAM 的清单、腾出的空间和搬迁前后的性能对比。

## 实现与验证

都在 Sila P4 上测量，芯片 ESP32-P4 v1.3，主频 360 MHz，L2 cache 128 KB。

### 片内 RAM 清单

静态部分按 map 统计，正式固件为 `sila_p4-release`，测试固件为 `sila_p4-test-release`。片内低端区从 `0x4ff00000` 起依次放 IRAM 代码、`.data` 和 `.bss`，后面才是堆。

| 段 | 正式固件 | 主要内容 |
|---|---|---|
| IRAM 代码 | 136.4 KB | 执行核心 66.0 KB；IDF 的 esp_hw_support 16.7 KB、spi_flash 9.6 KB、heap 6.4 KB、FreeRTOS 5.7 KB、MSPI HAL 4.6 KB、esp_system 4.3 KB、PSRAM 3.7 KB、DMA 3.0 KB、C 库 2.9 KB、ring buffer 2.0 KB、I2C 0.8 KB |
| `.data` | 14.8 KB | IDF 约 11 KB，比如 sleep_retention 2.7 KB、spi_flash_chip_generic 2.6 KB；`app.cpp` 的 `menus` 2.4 KB；执行核心的只读数据 1.4 KB |
| `.bss` | 15.2 KB | FreeRTOS 5.2 KB，其中中断栈 4 KB；coredump 栈 1.8 KB；串口控制台截图的行缓冲 2 KB；音频的混音缓冲 1 KB |

测试固件的静态部分共 157.2 KB，构成相同，没有 app 和串口控制台。

动态部分用一个临时的诊断固件统计：打开帧指针和 heap tracing，从 `app_main` 开始记录，在主界面和游戏中按调用者列出还活着的片内分配。`app_main` 之前 IDF 自己建了 main 任务的栈 8 KB、esp_timer 3.5 KB、两个 IDLE 各 1.5 KB、两个 ipc 各 1 KB 和 FreeRTOS 定时器任务 2 KB，还从片内留出 32 KB 给只能放在片内的分配（`CONFIG_SPIRAM_MALLOC_RESERVE_INTERNAL`）。LP RAM 32 KB 和 TCM 8 KB 也在片内的堆里。

| 来源 | 大小 | 冷热 |
|---|---|---|
| 任务栈和 TCB | 约 51 KB | library、saves、slots 各 6 KB，串口控制台 4 KB，是冷的；emulate 8 KB、LVGL 8 KB、audio 4 KB、present 4 KB、frame-step 3 KB 是热的 |
| LVGL 的对象、样式和定时器 | 6.6 KB | 冷 |
| I2S 的 DMA 缓冲 | 4.1 KB | 热，驱动要求在片内 |
| 锁、信号量，DMA2D、PPA、LCD 等驱动的描述符 | 约 4 KB | 由驱动分配 |
| 载入游戏后：`gb::System`，渲染工作线程的栈 | 23.6 KB、4 KB | 热 |
| 第一次用 JIT 以后：代码池、块索引和槽数组、gateway、`Sm83Jit` | 224 KB、40 KB、9.8 KB、8 KB | 热，退出游戏以后保留 |

JIT 运行时，片内高端区在诊断固件上只剩 2.7 KB，块索引的数组有 24 KB 分配在了留给只能放在片内的分配的那 32 KB 里。

### 搬迁的内容

| 内容 | 大小 | 方式 |
|---|---|---|
| 执行核心里的冷函数：平坦总线版 `sm83_step`，各设备的构造函数、析构函数、`initialize()`、`reset()`、载入，APU 的 `set_rate()`，测试用的总线追踪 | 14.4 KB | `components/core/linker.lf` |
| IDF 的 heap、ring buffer 的中断函数、C 库的锁、I2C 的中断处理函数 | 10.8 KB | `sdkconfig.defaults` |
| `menus` | 2.4 KB | 初始化时用 `platform::allocate_external()` 分配 |
| 串口控制台截图的行缓冲 | 2 KB | `EXT_RAM_BSS_ATTR` |
| library、saves、slots 和串口控制台的任务栈 | 22 KB | `platform::StackMemory::external`、`xTaskCreatePinnedToCoreWithCaps()` |
| LVGL 的堆 | 约 6.6 KB | `CONFIG_LV_USE_CUSTOM_MALLOC`，`components/platform/src/esp/lvgl_memory.cpp` |

执行核心原来按对象整个放进片内，冷函数改成在 `linker.lf` 里逐个标出，由 ldgen 列出每个对象剩下的段，`tools/link_core_layout.py` 再把这些段按原来的顺序移到片内代码段开头。一个对象里某一类段全是冷函数时，ldgen 只写文件名、不写段，这一行会把对象里剩下的所有段都放进片内数据段，调试信息也在内，脚本会去掉这样的行。

IDF 里其余放进 IRAM 的函数，比如 esp_system、日志、esp_timer、spi_flash 和 C 库的其他函数，只有打开 `CONFIG_SPI_FLASH_AUTO_SUSPEND` 才能改放 flash，这项功能只支持部分 flash 芯片，没有使用。GDMA 的控制函数被 PARLIO 的配置选进 IRAM，只有 0.7 KB，没有改。

### 内存测量

正式固件的数字来自 `sila_p4-profile` 的 `pstat` 输出，单位 KB，空闲为 `MALLOC_CAP_INTERNAL | MALLOC_CAP_8BIT`。主界面是开机以后，游戏中是 V-Rally 载入槽位以后。JIT 第一次运行以后代码池一直保留，所以退出到主界面的数字和 JIT 游戏中相同。测试固件的数字来自一个临时加了日志的测试固件，在会话开始时和 `--schedule concurrent` 下两个 worker 都建好 `System` 以后记录，ROM 是 dmg-acid2。

| | 搬迁前 空闲 / 最大块 | 搬迁后 空闲 / 最大块 |
|---|---|---|
| 正式固件静态段 | 166.5 | 136.7 |
| 正式固件主界面 | 404.2 / 288 | 463.6 / 320 |
| 正式固件解释器游戏中 | 376.2 / 256 至 264 | 435.6 / 296 |
| 正式固件 JIT 游戏中，退出后相同 | 94.3 / 31 | 153.7 / 64 |
| 测试固件静态段 | 157.2 | 132.5 |
| 测试固件启动后 | 485.4 / 344 | 510.1 / 344 |
| 测试固件两个 `System` 同时运行 | 129.1 / 52 | 153.7 / 76 |

### 负载测量

构建 preset 为 `sila_p4-profile`，数字包含 profile 版计数的开销。V-Rally 槽位 1 和 2 的存档，做法和 4-3 相同：用串口控制台载入 ROM，通过 `keys` 操作暂停菜单载入槽位，用 `speed` 设定速度，4 秒后用 `stat 2` 和 `tasks 10000` 采集 10 秒，`FRAME` 取 5 个窗口的平均值。搬迁前测了 3 轮，第 1 轮先测 JIT，后两轮每轮先复位板子，再先测解释器；搬迁后测了 2 轮，做法和后两轮相同。下表是各轮的平均值。所有组的 `SPEED` 都在 99.6% 到 100.3% 或 199.7% 到 200.2% 之间，欠载都是 0。

| 后端 | 槽位 | 速度 | 模拟任务 % 前 / 后 | core 0 空闲 % 前 / 后 | core 1 空闲 % 前 / 后 | `FRAME` p95 / 平均 ms 前 | 后 |
|---|---|---|---|---|---|---|---|
| JIT | 1 | 1X | 14.7 / 14.9 | 70.2 / 70.0 | 78.0 / 78.1 | 5.68 / 4.60 | 5.84 / 4.67 |
| JIT | 1 | 2X | 24.7 / 24.8 | 68.2 / 68.5 | 75.3 / 75.2 | 3.96 / 3.28 | 3.94 / 3.23 |
| JIT | 2 | 1X | 22.8 / 23.2 | 68.7 / 67.6 | 69.2 / 67.4 | 5.38 / 5.09 | 5.55 / 5.37 |
| JIT | 2 | 2X | 39.5 / 40.3 | 59.8 / 59.0 | 60.5 / 59.6 | 4.67 / 4.60 | 4.75 / 4.71 |
| 解释器 | 1 | 1X | 33.1 / 33.5 | 62.6 / 62.0 | 66.9 / 66.5 | 8.60 / 7.59 | 8.78 / 7.67 |
| 解释器 | 1 | 2X | 61.6 / 61.7 | 52.0 / 52.2 | 38.4 / 38.3 | 6.50 / 6.17 | 6.53 / 6.18 |
| 解释器 | 2 | 1X | 39.2 / 40.0 | 60.8 / 60.0 | 60.8 / 60.0 | 7.93 / 7.71 | 8.25 / 7.90 |
| 解释器 | 2 | 2X | 70.2 / 71.8 | 48.0 / 46.9 | 29.8 / 28.1 | 6.96 / 6.91 | 7.43 / 7.34 |

搬迁前同一组在各轮之间的差别，最大的是解释器槽位 2 的 1X，模拟任务在 38.2 到 40.8 之间。只有解释器槽位 2 的 2X 两轮都超出了搬迁前的范围：模拟任务从 70.1 到 70.3 变成 71.8 和 71.9，`FRAME` 平均从 6.76 到 7.10 ms 变成 7.33 和 7.34 ms。把改动分成两半分别测这一组：只搬执行核心的冷函数，两轮是 70.4 和 70.2；只做其余的搬迁，一轮是 70.2。两半单独都没有复现，原因没有查明。接受这项变差，保留全部搬迁。

上面的负载和内存数据测完以后，代码审查指出 `Apu::open()` 不是冷函数：`append()` 每开一个新的音频 batch 都要调用它，2X 关闭声音时也一样。所以把它从 `linker.lf` 里去掉，留在片内。片内代码因此多了 96 B，两种固件的静态段总数不变。放回以后没有重新测量负载。解释器槽位 2 的 2X 变慢是否和它有关，未实测。

### 测试

用测试固件运行固定回归（`run_roms.py --regression`）和带存档点的 ROM（`--states`），10 个和 8 个全部通过，两个后端结果一致。
