# 任务 6-3：逆转裁判和超级机器人大战 OG2 的速度

里程碑 6 完成以后，用户在 Sila P4 的正式固件上试玩，发现两款游戏的场景达不到原速，音频频繁欠载：逆转裁判的槽位 1 和超级机器人大战 OG2 的槽位 2。这两款游戏都要能流畅运行，做完以后再测一次 6-1 的 4 个场景，速度不能回退。这个任务依赖 6-2。

## 范围

- 找出两个场景的瓶颈并优化，目标是 1X 下 `SPEED` 稳定在原速、不再频繁欠载。
- 优化不改变模拟结果：渲染器的改动用 PC 上的槽位帧 hash 核对，JIT 和设备的改动跑相关的测试 ROM。
- 最后用 6-1 的 4 个场景复测速度。

## 原则

只要不影响游戏运行，可以降低模拟精度，但这是最后的手段，先做不改变结果的优化，不够时再考虑。降低精度的改动放进 `GBX_GBA_RELAXED_TIMING` 宏，宏关闭时的行为不变。慢的部分可以借鉴对照模拟器的做法，但是按项目规则不搬它的代码，自己实现。

## 测量方法

- 板子是 Sila P4（ESP32-P4 v1.3、360MHz），固件是 `sila_p4-profile`，后端是 JIT。
- 两个游戏的 ROM 和槽位文件用控制台的 `file` 命令从卡上取回，放在本地的 `roms/gba/` 和 `build/m6/states/`，不入库。
- 场景的内容随帧变化，按墙钟统计的窗口每次落在不同的帧上，结果不能直接比较。`bench <skip> <n>` 从下一次读槽位开始数帧，统计第 `skip` 到 `skip + n` 帧：CPU 所在的核每帧的周期，以及 JIT 运行中各部分（原生代码、经过 C++ 的读写、块边界和访存的 catch-up、HALT、进中断、查块和编译、PPU 的行事件）占的比例。OG2 用 `bench 120 600`。
- 和对照模拟器对比用 OG2 开机以后的演示动画：在 StarTeam 的菜单上选简体版（第 300 帧左右按 A），以后不再按键，第 4200 到 4800 帧是艾克塞琳在宇宙背景前的对话，和槽位 2 是同一类场景。对照模拟器用它在仓库外的场景 `og2`，我们用 `bench @4200 600`。我们按 A 的时刻由控制台发出，和对照模拟器可能差几帧。
- 渲染器的改动在 PC 上用 `gbx_gba_frames` 从 8 个槽位各跑 300 帧，和改动前的构建比较每帧的 hash 和结束时的机器状态，宏打开和关闭各一次。

## 记录

### 两个场景的瓶颈

逆转裁判槽位 1（法庭休息室的对话框，画面静止）：release 固件 `SPEED` 约 97%，核 0 空闲 0%，核 1 空闲 77%。CPU 所在的核在等渲染器：渲染每帧 14.4ms，其中通用合成 `compose_run` 占核 0 的 39%，`text_bg` 占 25%。这个画面打开了 4 个 BG：BG0 和 BG2 整行透明，BG3 是不透明的 256 色背景，BG1 的对话框（约占 30% 的像素）以 alpha 混合叠在 BG3 上。每个像素都走通用合成，平均约 60 个周期。

OG2 槽位 2（宇宙背景前的对话）：`SPEED` 约 67%，两个核都接近占满，主要是核 1。这个游戏每一行都有 HBlank 中断（每帧 228 次），中断处理程序每行改约 10 个显示寄存器（滚动、WIN0H、BLDCNT、BLDALPHA、BG1CNT），主循环用 IntrWait 等 VBlank，等待期间每次 HBlank 中断都把 CPU 从 HALT 唤醒。PC 上统计，每帧只执行约 6 万条 GBA 指令，GBA 的时间里 43% 停在 IntrWait 的 HALT 里。

### OG2 核 1 的构成

`bench 120 600`，改动之前核 1 每帧约 818 万个周期，1X 需要不超过 600 万。JIT 运行中各部分的占比：

| 部分 | 占比 |
|---|---|
| 原生代码和 stub | 约 46%，每条 GBA 指令约 55 个周期 |
| 经过 C++ 的写入 | 12.9%，每帧 2468 次 |
| 访存的 catch-up 和块边界 | 约 19%，其中 PPU 的行事件约 8% |
| 查块、编译和装块 | 6.3%，其中编译、装块和存块约 5% |
| HALT 和进中断 | 约 5% |

每帧原生代码因为停止退回 C++ 约 335 次：约 200 次是中断，约 135 次是 HALT。从中断返回到块中间时，还要经过 C++ 查找块中间的入口，每帧约 130 次。代码池每帧编译约 5 个块，淘汰约 9 个；把块数上限从 1024 改成 2048，速度不变。缓存控制器的计数显示核 1 约 32% 的周期在等指令缓存缺失：每一行都要走一遍很长的代码路径，16KB 的指令缓存装不下。

### 和对照模拟器对比

OG2 演示动画的第 4200 到 4800 帧，Sila P4：

| | 对照模拟器（一个核跑 CPU 和渲染） | 我们（显示寄存器的写入改完以后） |
|---|---|---|
| 速度 | 160% | 83% |
| CPU 和设备，每帧 | 约 235 万周期（6.5ms） | 核 1 707 万周期 |
| 渲染，每帧 | 约 3.9ms | 核 0 13.9ms |

我们核 1 的 707 万周期里，原生代码和 stub 约一半；另一半是设备事件、经过 C++ 的读写、中断和 HALT 进出 C++ 的来回。所以这个游戏在这块板子上可以跑到原速，差距在实现。

### 不改变结果的改动

- 渲染器：带颜色特效的行也从后往前画，不再先把每个 BG 画进各自的行缓冲、再逐像素合成。亮度效果、只有一个第一目标的行，以及第一目标和半透明 OBJ 都不是第二目标的行，画的时候就直接算出颜色；只有 OBJ 窗口逐像素决定效果的行还要记下最上面两层。没有可见效果的特效，以及不会混合的半透明 OBJ（GBATEK “LCD I/O Color Special Effects”），按不带特效的画。
- 渲染器的窗口和 OBJ：按窗口边界切出的区段画；OBJ 一行只画一次，仿射 OBJ 先算出落在纹理内的列区间，马赛克时一块只取一次颜色；OBJ 的优先级、半透明和 OBJ 窗口按行记成位图。
- 画第 N 行时，预取第 N+1 行在 PSRAM 帧缓冲里的位置。
- 显示寄存器 08h-57h 的写入只改 I/O 的副本和这一行的定时写入，不再经过 `write_slow()`；HBlank 和 VBlank 里，JIT 的写 stub 直接写 I/O，不进 C++。经过 C++ 的写入从每帧 2468 次降到 1150 次。
- JIT 的读 stub 直接读不需要计算的 I/O 寄存器，经过 C++ 的读从每帧 744 次降到 61 次。
- IE&IF 或 IME 改变以后，只在 CPU 的 stage 可能变化的那个周期进 C++ 采样中断线。
- PPU 的行事件不再通过函数指针判断每行的边沿。

PC 上宏关闭时，8 个槽位的帧 hash 和结束状态都和改动前相同。渲染器的最后一组改动另外比较了 OG2 的 1100 帧（覆盖仿射加马赛克 OBJ 的那一段）和 168 个 GBA 测试 ROM 各 120 帧，也都相同。

### 宏打开时的改动

照对照模拟器的做法，放在 `GBX_GBA_RELAXED_TIMING` 里：

- 中断线不模拟 2、3 个周期的延迟，IE&IF 或 IME 一改就决定，CPU 在下一个指令边界进入中断。HALT 期间请求的中断在唤醒后进入。
- JIT 按块计时：块里只在写内存的指令之后检查事件，其余的事件推迟到下一次访存或块尾。每帧编译的块从 5.1 个降到 2.8 个。
- 读 IF 直接读 I/O 的副本，比 CPU 早一个周期读到刚请求的位（nba-hw-test `ppu/status-irq-dma#irq`）。
- 混音的采样点固定为 32768Hz，振幅分辨率仍按 SOUNDBIAS。

PC 上 7 个槽位 300 帧的画面和改动前相同。OG2 有 127 帧不同，差在左边 0-5 列、第 68-113 行的几个像素：中断提前了几个周期，行中写入的落点随之移动，肉眼看不出。

### 缓存和音频

- ROM 缓存在 PSRAM 够用时是 14MB，超出的部分按 32KB 一页从卡上读。OG2 的 ROM 有 18MB。缓存是 8MB 时，槽位 2 的 600 帧里缺页 17 次，每页约 5.5ms 到 9.7ms，看 SD 卡；改成 14MB 以后，读档后的头一个 5 秒窗口缺 4 页，之后 75 秒没有再缺页。
- JIT 的第二级是 4MB，和对照模拟器在 ESP32-P4 上 ROM 代码缓存加 RAM 代码缓存的大小相同，方便对比。OG2 读档后运行约 35 秒，第二级用了 2.1MB，没有丢弃过块。
- GBA 的音频缓冲目标是 64ms，GB 和 GBC 仍是 40ms。目标是 40ms 时，一帧超过约 40ms 就会欠载；改成 64ms 以后，OG2 槽位 2 的正式版 90 秒只欠载 1 次，在读档后的头一个窗口里。声音因此多延迟约 24ms。

### 片内内存

GB 的 JIT 要一整块 192KB 的代码池加 16KB 的 gateway。这个任务的渲染器改动让 GBA 的执行代码从 118.0KB 变成 135.6KB，GB 游戏启动时高段 SRAM 就分不出这么大的块了。用户选了下面几项，现在的布局是：

- IDF 开机时预留的 32KB 内部 DMA 池关掉了。它从最大的块里切出来，正好在高段的开头，但是只有别处都分不到时才会用它。
- 留在片内的任务栈（模拟、音频、呈现、帧转换、GB 渲染、GBA 读页）放在低段 SRAM。P4 v1.x 上 IDF 先从高段分配所有片内内存，低段要等高段满了才用。
- GB 的整个执行核心放在 flash，从 PSRAM 运行，原来在低段占约 67KB。片内只留两个系统共用的块查找和工作线程队列，共 674 字节。
- P4 v1.x 上，核 0 上跑的渲染器和混音器（约 38.6KB）放在低段，CPU 和设备的代码在高段。
- GBA 的代码池是 192KB，BIOS 放在 PSRAM，这样 `Arm7Jit::Tables` 才留在片内。JIT 只在编译 BIOS 的代码时整段读 BIOS；解释器执行 BIOS 时每次取指令都要读，这部分的影响未实测。

正式固件载入精灵宝可梦 水晶，GB 的 JIT 正常启动。profile 固件载入水晶和 OG2 以后，两种 JIT 的块表都在片内；OG2 载入以后片内还剩 62824 字节，其中最大的可执行块 31744 字节，推测是堆里的 LP SRAM（见 [6-1](task-6-1.md) 的“片内内存落到 LP SRAM”），`allocate_internal()` 不用它。用户在正式固件上玩 GB 游戏，觉得仍然流畅，速度未实测。

|---|---|---|---|
| 改动前 | 818 万 | | |
| 显示寄存器的写入 | 781 万 | | |
| 中断线的采样、I/O 读 | 754 万 | | |
| 宏打开：中断立即生效 | 725 万 | 16.3ms | 94 次，1.3 秒 |

|---|---|

### 6-1 的 4 个场景

分析版固件，宏打开，`build/m6/scenes.sh` 和 6-1 收尾时相同，`stat` 统计 10 秒：

| 场景 | JIT 2X 档，6-1 收尾 | JIT 2X 档，现在 | 解释器 1X，6-1 收尾 | 解释器 1X，现在 |
|---|---|---|---|---|
| 马里奥高尔夫，球场上 | 192.7% | 199.4% | 100.0% | 100.0% |
| 黄金太阳 2，按 A 开始以后 | 180.0% | 186.0% | 67.1% | 67.2% |
| V-Rally 3，赛道上 | 109.7% | 124.6% | 41.9% | 41.1% |
| Mother 3，输入名字 | 197.6% | 200.1% | 99.1% | 85.6% |

JIT 的 4 个场景都没有回退，Mother 3 已经到 2X 档的上限。解释器的 Mother 3 重复测了两次，都是 85.5% 左右，核 1 没有空闲；用开工时的代码编的分析版固件测同一个场景是 91.1%，和 6-1 记录的 99.1% 也对不上。PC 上开工时的代码和现在的构建跑这个槽位 1200 帧，耗时相同（约 277ms），所以模拟的工作量没有变，板上的差别可能来自片内 RAM 里代码位置的变化，没有核实。不再追，因为解释器本来就不用来玩游戏。

### 板上的测试

Sila P4，测试固件 `sila_p4-test-release`，宏关闭：

- GBA 固定回归 25 项、`--small-pool` 25 项、`--states` 8 项、`gbx` 套件 31 项都通过，两个后端一致。
- PPU 模块 46 项：36 项通过，9 项是原本就只记入报告的失败，1 项要人工判断。其中 `nba-hw-test/ppu/status-irq-dma#irq` 是 IF 的读改成宏关闭时经过 C++ 以后单独重跑的。
- 片内内存的改动以后：`run_jit.py` 179 项全部通过；GB 固定回归 22 项不加 `--small-pool`，两个后端都通过，结果一致；GBA 固定回归加 `--tiny-cache` 25 项通过。

宏打开的测试构建在 6-3 收尾时没有跑，6-4 收尾时用 6-4 开工时的代码（包括 6-3 和它之后几项片内内存的改动）补跑了 GBA 全部 ROM 171 个。和 6-2 宏打开的那次比：

- 解释器新失败 14 个，都是测中断时机的：alyosha `Interactions` 的 `Halt_DMA_IRQ`、`Halt_IRQ` 和 `Internal_Cycle_DMA_IRQ` 系列 8 个，nba-hw-test 的 `irq/irq-delay` 和 `ppu/status-irq-dma` 的三项。
- JIT 新失败 8 个，其中 alyosha 的 `Bus/Unused_location_update_bus` 和 nba-hw-test 的 `dma/latch` 解释器通过。
- 另有 3 个两个后端都通过，但是周期数不一致。
