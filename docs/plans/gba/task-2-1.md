# 任务 2-1：整机框架、内存和 ROM 测试通路

这是[路线图](../../roadmap.md#gba) GBA 段里程碑 2 的第一个任务：在 `gba/` 下搭起整机的框架，包括内存映射、等待周期、预取缓冲、BIOS、开机状态、ROM 的 SD 分页缓存和系统接口，并把 GBA 的测试 ROM 接进板上的测试通路。解释器和 JIT 同时实现，JIT 从这里开始翻译多条指令的块。中断、定时器和 DMA 在 2-2，PPU 在 2-3，卡带存档芯片在 2-4，它们都在这个框架上增加，并用这里的测试通路验收。这个任务依赖 1-5。

开工时在[任务状态](status.md)里把这个任务标为“进行中”。

## 范围

整机框架：

- 内存映射：BIOS、EWRAM、IWRAM、IO、调色板 RAM、VRAM、OAM、卡带 ROM 的三个等待区和卡带存档区，以及各区域的镜像。各区域的总线宽度、16 位总线上的 32 位访问、未对齐访问、没有映射的地址和 open bus，以及 BIOS 的读保护，按 GBATEK “GBA Memory Map” 和 “GBA Unpredictable Things”。IO 寄存器的读写屏蔽和未使用位按 GBATEK 实现，声音寄存器也包括在内。2-2、2-3 和 2-4 要接入的设备在内存映射里留出位置。
- 等待周期：WAITCNT 的各个字段、N/S 访问、每 128KiB 边界上的访问强制为 N（nba-hw-test `bus/128kb-boundary`），以及卡带的预取缓冲（GBATEK “GBA GamePak Prefetch”）。内部周期按 “ARM CPU Instruction Cycle Times”。
- BIOS 从卡上的文件读取，按 1-1 记下的校验值核对。开机不运行 BIOS 的开机流程，直接设置 BIOS 交出控制时的 CPU 寄存器、各模式的栈指针、IO 寄存器和 BIOS 读保护看到的值，每一项的来源写在注释里。
- 沿用 `common/` 的调度器和模拟时间线，时间单位要能表示 GBA 的 16.78MHz 周期，不能让 GB 和 GBC 的路径变慢。
- ROM 经过 SD 分页缓存读取，`common/rom.h` 的窗口在取得时处理缺页。CPU 取指、数据读取、DMA 和 JIT 的 ROM 快速路径都经过同一个访问层，ROM 最大 32MiB。缓存放在 PSRAM，大小按 PSRAM 的预算定；ROM 比缓存小时整个留在缓存里，不会缺页。系统接口另外可以把缓存设得很小，测试用它让页面不断换进换出。
- PPU 按 GBATEK “LCD Dimensions and Timings” 推进 VCOUNT 和 DISPSTAT 的 HBlank、VBlank 标志，在对应的时刻置中断请求位，让测试 ROM 能等到 VBlank。画面渲染在 2-3。
- 系统接口：载入 ROM 和 BIOS、复位、运行到指定的模拟时间或者一帧结束、设置按键、选择执行后端、设置分页缓存的大小。画面、卡带存档、即时存档和声音以后再加。
- 双核分工的边界：CPU、调度器、设备时序和 JIT 固定在一个核上，PPU 渲染和以后的混音在另一个核上，另一个核只通过任务拿到数据。读卡和预读放在哪个核上由你决定，但是缺页只能改变墙钟时间，不能改变模拟的结果。

JIT：

- JIT 在真实的内存映射上翻译多条指令的块，块标识区分 ARM 和 Thumb、代码所在的区域和影响翻译结果的等待周期设置。程序改写 WAITCNT 以后，依赖旧值的翻译不能再执行。
- BIOS 和 ROM 中的代码是常量。IWRAM 和 EWRAM 中的代码被 CPU 或 DMA 改写以后，对应的块失效，用失效、取指核对还是别的办法由你决定。程序也可能在 VRAM、调色板 RAM 或 OAM 里执行代码，JIT 不翻译的区域交给解释器执行，并记录原因。
- 设备事件在准确的模拟时刻生效。事件发生在指令中间时，可以执行完当前指令再退出块，但不能继续执行下一条指令，也不能因此回退到解释器。事件发生以后的访存，包括快速路径，必须使用生效以后的设备状态。
- 可以安全直接访问的内存生成宿主读写指令，其余访问经过总线处理。快速路径也要计入等待周期和预取，不能绕过 open bus、未对齐访问、BIOS 读保护和代码失效所需的处理。ROM 的快速路径在页面不在缓存里时退回慢路径。
- 运行时的结构照搬 SM83 JIT：成批运行、块间连接、分发表、PSRAM 的第二级代码缓存、重装退避和块中入口，开工时和用户商定。
- 编译块数、失效次数和按原因分类的回退次数一直统计，详细诊断沿用 GB 段的运行时开关。

测试通路：

- 测试索引登记 1-1 名单中的全部 ROM，以及 1-2 自写的 ROM，记录稳定的用例 ID、卡上路径、模块标签、依赖任务、结束条件、判据和模拟时间上限。依赖的设备还没有实现的 ROM 标为执行器尚未支持，不下发执行，也不测速。
- 判据：jsmolka、alyosha 和自写的 ROM 运行到 idle 循环时，检查 1-1 名单为这个 ROM 记下的结果寄存器；nba-hw-test 按 1-1 定下的办法认出屏幕上打印的结果。和参考帧比较画面在 2-3 实现。
- 握手报告 BIOS 的校验值，runner 在 BIOS 无效时拒绝运行 GBA 的 ROM。测试固件流式读取整个 ROM 文件计算 SHA-256，和清单核对以后才执行。
- 两个后端各用一个系统实例，比较结束状态，两边都通过、结束状态一致、没有未确认的回退，这个 ROM 才算通过。回传的结束状态包括结束原因、模拟时间、CPU 寄存器、各块内存的摘要、JIT 计数和每个后端的墙钟耗时。
- runner 能按模块、套件和单个 ROM 选择，能只重跑失败的 ROM，加一个选项用很小的分页缓存运行所选的 ROM。
- 两边结果不一致时，对所选 ROM 运行锁步诊断，找出第一个出现差异的块，再报告块里第一处不一致的访存，或者不同的寄存器。诊断时 JIT 的块划分、寄存器分配和标志位的计算方式要和正常运行相同。
- 报告记录具备执行条件的 ROM 在每个后端上的模拟时间、墙钟耗时和速度倍数，缺页次数和读卡时间分开列出。

## 不做

- 中断分派、HALT、定时器、DMA、按键、串口和 Direct Sound 的 FIFO，这些在 2-2。
- PPU 的画面渲染和画面的比较，这些在 2-3。
- SRAM、Flash 和 EEPROM，这些在 2-4。卡带存档区在这里只读出 open bus 规定的值。
- 固定回归的名单，在 2-6 确定。

## 约束

- 写代码时就要注意性能，解释器和 JIT 都一样。在满足功能的前提下选性能最好的实现，不写明显低效的代码，也不留给以后的优化任务再改。
- 性能优先，但是不能改变游戏能观察到的行为。CPU 读写 IO 寄存器时，相关设备必须已经推进到这次访问的准确时刻。
- 每条指令、每次访存都会走到的路径上不分配堆内存，不用虚函数，也不检查诊断开关。
- 改动共用的调度器、JIT 后端或测试通路时，GB 和 GBC 的结果不能变，GB 不能变慢。开发期间不运行 GB 和 GBC 的测试，在 2-6 收尾时检查。
- 解释器的总线接口改动以后，1-5 的解释器基准不再适用。按真机测试计划的规则，影响范围界定不了时，重新验证一次单步全量，不在每轮修改以后重复。
- 两个系统实例除了只读的 BIOS 和 ROM 以外不共享可变状态，同时运行不能改变任何一边的结果。分页缓存由两个实例共用时，也只能影响墙钟时间。
- 改动解释器、设备执行代码或 JIT 运行时 helper 时，按 `cmake/core_layout.cmake` 的规则放置，检查 map 中的地址，不能移动 GB 的热代码。
- 计时用 `sila_p4-test-release`，诊断开关关闭，报告写明板型、芯片修订、主频和核的安排。超时、达到模拟时间上限、板子重启、通信错误和判定失败分开报告。
- 开发期间只构建要刷进板子的测试固件和 PC 的 debug 版。做完一段开发，或者调研需要上板的探针时才上板，只运行改动影响到的 ROM 和用例。

## 由你决定

内存映射的分页方式、等待周期和预取缓冲的实现、分页缓存的页大小和替换策略、系统接口的形式、JIT 块的标识和失效粒度，以及 `gba/` 下的文件划分。测试通路方面，索引的格式、结束状态的字段、锁步诊断的实现和 runner 的命令行也由你决定。选择的理由写在代码注释里，字段布局写在协议头文件的注释里。

## 完成标准

- 按[双后端优化要求](../../hardware-testing.md#每个任务的双后端优化)，用具备执行条件的 ROM 分析两个后端在等待周期、预取和分页上的开销，提交两边各自的优化前后数据和剩余瓶颈。
- 在 Sila P4 上，索引中只依赖本任务功能的 ROM 在两个后端上通过，结果一致，回退清单为空或者已经和用户确认；用很小的分页缓存再运行一次，仍然通过。哪些 ROM 属于这一类由索引的模块标签确定，任务结束时列出它们，以及其余 ROM 依赖的任务。
- 1-2 自写的 32MiB ROM 的 CPU 读取测试在两个后端上通过，用很小的分页缓存时也通过。DMA 读取的测试在 2-2 验收。
- `run_jit.py` 加入的检查在板上通过，覆盖多条指令的块、按事件退出，以及改写 IWRAM 和 EWRAM 中已经执行过的代码。
- 确认比对和诊断真的能发现错误：临时改错 JIT 在多条指令的块里对一条指令的翻译，runner 能指出 JIT 失败和两边不一致，锁步诊断能报告出错的块和第一处不一致，然后改回去。这一步不留下测试代码。
- PC 的 debug 构建和 `sila_p4-test-release` 构建通过，没有新的警告。全部板子的构建在 2-6 做。

## 收尾

- 满足全部完成标准以后，在[任务状态](status.md)里把这个任务标为“已完成”。
- 在架构文档中写明 GBA 的内存映射、等待周期、分页缓存、系统接口和 JIT 块的模块边界，以及不写下来就容易出错的约束。在真机测试计划中写明 GBA ROM 测试的运行方法和判据，验证结论保存在运行报告中。
- 向用户汇报设计选择、测试结果、各 ROM 的速度、缺页的开销，以及对时间预算的估算。
