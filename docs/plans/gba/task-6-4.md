# 任务 6-4：CPU 所在的核向对照模拟器看齐

6-3 以后，渲染器所在的核 0 在 OG2 的战斗里已经有余量，剩下的差距主要在 CPU 所在的核 1：同一个场景里，对照模拟器模拟 CPU 和设备每帧用的周期比我们少得多。这部分单独作为一个任务。这个任务依赖 6-3。

## 已知的数据

- OG2 开机演示动画第 4200 到 4800 帧（Sila P4，见 [6-3](task-6-3.md) 的“和对照模拟器对比”）：对照模拟器的 CPU 和设备每帧约 235 万周期（6.5ms），渲染约 3.9ms，两部分在同一个核上；我们在 6-3 的显示寄存器改完时，核 1 每帧 707 万周期。
- V-Rally 3 赛道上（见 [6-1](task-6-1.md) 的“对照模拟器的速度”）：对照模拟器模拟一帧的 CPU 和设备约 7.3ms，渲染 4.8ms；我们当时核 1 一帧约 20ms。
- 开工时的两个 OG2 槽位，Sila P4 分析版 `bench 120 600`，原速 600 帧是 10046ms：
  - 槽位 2：核 1 每帧 564 万周期，600 帧 10032ms，CPU 等渲染线程 1 次，21.4ms。
  - 槽位 1（用户 SD 卡上的即时存档）：核 1 每帧 568 万周期，600 帧 10085ms，CPU 等渲染线程 5 次，共 132.7ms；渲染平均每帧 11.71ms，最长的一帧画了 40.0ms。用户在这个场景里看到核 1 的占用很高，容易跑满。

两边的测试条件不同，比较时要考虑进去：

- 对照模拟器的场景测试没有显示和声音，另一个核空闲。6-1 测过，我们的核 0 渲染和呈现时，核 1 慢约 19%，因为两个核共用 L1 数据缓存、L2 缓存和 PSRAM。
- 我们的 PPU 在核 1 上把每一行交给核 0，要复制这一行以前写过的页，记录行中的写入；对照模拟器在同一个核上直接从内存画一行，没有这部分开销，但是要付渲染的 3.9ms。
- 对照模拟器按游戏记录了等待循环的地址：V-Rally 3 欧版、马里奥高尔夫和黄金太阳 2 有，OG2 和 Mother 3 没有。所以 OG2 上的比较不受这一项影响。

## 对照模拟器有、我们没有的做法

下面是用子代理阅读对照模拟器的源码整理出来的不改变结果的做法，结果见“记录”里的各节。

| # | 做法 | 结果 |
|---|---|---|
| A1 | ROM 代码里 PC 相对的 `LDR` 在编译时取出常数，访存的等待周期在编译时算好。避开 GPIO 的 0xC4 到 0xCB，要求常数和指令在同一个 32KB 页里 | 保留，只在宏打开时 |
| A2 | 写 IE、IF、IME 在 stub 里完成，只在中断变得可以进入时才回 C；只是按掩码存值的 I/O 寄存器按一张写掩码表直接写 | 保留 |
| A3 | ARM 的单个写入在块里直接写 VRAM 和 OAM 的字；写调色板的字经过一个很短的汇编函数，同时转换颜色 | 保留 |
| A4 | LDM、STM、PUSH、POP 整段只查一次范围和代码标记，然后原生读写 | 保留 |
| A5 | 块跨过条件跳转：只有无条件跳转结束块，前面的出口跳过它时也不结束；一个块最多 1024 条指令、32 个出口，跳到块内的目标留在块里 | 第一步试过，槽位 1 变慢，没有保留 |
| A6 | 已链接的出口就是一条 `jal`，写在出口的位置上；目标块入口检查周期预算 | 保留，只在宏打开时 |
| A7 | ROM 块的每个指令边界都可以进入，加一个只在用到时才填的分支缓存：BX、POP {PC} 和异常返回先查片内 RAM 里 8KB、1024 项直接映射的表 | 保留 |
| A8 | 块的出口往后看最多 8 条 BIOS 或 ROM 的指令，只算还会用到的标志位 | 保留，只在宏打开时 |

### 核 0 和外围（没有做）

- 渲染器：对照模拟器写调色板时就转成 RGB565 和一种展开的格式，alpha 混合只要一次乘法；仿射 BG 的地址用 PIE 扩展的向量指令生成。都不改变结果。
- 自动跳帧：按音频队列的水位决定不画哪些帧，模拟结果不变，但是画面会少帧。对照模拟器的场景测试关着它，所以它不是上面那些差距的来源。

### 已经试过的

对照模拟器把 IWRAM、EWRAM、VRAM 和生成的代码都放在 PSRAM，L2 缓存 256KB。6-1 试过把生成的代码放在 PSRAM，结果更慢，见 6-1 的记录。

## 约束

- JIT 优先：保护 JIT 的速度、片内 RAM 和热代码的布局。解释器的收益要和 JIT 的损失一起权衡。
- 热代码的位置由构建和链接配置控制，用链接映射核对地址，影响缓存的布局改动要在板上实测。
- 宏关闭时，解释器和 JIT 的结果必须相同。

## 完成标准

  - 槽位 1 的 `bench 120 600` 跑 600 帧不超过原速的 10046ms。
- 达到目标以后，A 类的各项仍然都要做完。每一项都在板上实测，没有收益的不保留，数据写进记录。

### 游戏运行时 JIT 的代码池

开工测基线时发现，同一次开机里跑过 OG2、执行过控制台的 `stat` 以后，再载入游戏就报“the JIT cannot start: not enough memory for its code”。IDF 第一次初始化函数内的静态变量时（`__cxa_guard_acquire`）会建信号量，以后不再释放；游戏运行时高段只剩零碎的空隙，它们正好落在代码池要用的地方。任何任务在游戏中第一次创建、以后一直保留的对象都会造成同样的问题。

所以 `Game` 初始化时就占住 JIT 代码池要的那块片内 RAM，大小取 GB 和 GBA 两种 JIT 里大的一种，以后不再释放。GB 的 gateway 比 GBA 的大，所以 GBA 的代码池多了约 4.6KB，游戏运行时片内的空闲也少了这么多（OG2 载入后 58408 字节）。OG2 载入、`stat`、换成精灵宝可梦 水晶、再换回 OG2，JIT 都能启动。

### 和对照模拟器并排比较

OG2 演示动画，按 A 的帧号对齐对照模拟器场景的第 300 帧。我们 `GBX_GBA_RELAXED_TIMING` 打开（正式固件的默认）；对照模拟器用它的场景 `og2`（PIE 仿射渲染打开），在它的场景测试里加了整个窗口和渲染部分的 `mcycle`、`minstret` 计数。按 A 的帧号由 `stat` 打印的模拟时间推算，可能差几帧。下表是 A 类开始之前：

| 每帧 | 对照模拟器 CPU 和设备 | 对照模拟器渲染 | 我们的核 1 |
|---|---|---|---|
| 宿主周期 | 236.9 万 | 141.6 万 | 546 万 |
| 宿主指令 | 142.5 万 | 106.2 万 | 269 万 |
| IPC | 0.60 | 0.75 | 0.49 |

我们每帧执行 60191 条 GBA 指令，平均每条 44.7 条宿主指令（包括设备和 C++）；对照模拟器的 GBA 指令数没有计数，如果和我们相同，约 23.7 条。按 `bench` 的分类，扣掉经过 C++ 的部分以后，我们的原生代码平均每条 GBA 指令 49.6 个周期，合计约 298 万周期，已经比对照模拟器的 CPU 和设备合计还多。所以差距一半在指令数，一半在原生代码的周期上，A 类里减少回 C++ 的几项只能解决一部分。

`bench` 的分类（占核 1 运行时间）：原生代码 87.3%，其中经过 C++ 的写 9.6%、读 0.7%、边界 1.6%、catch-up 6.8%、内部周期 11.5%、refill 2.3%；HALT 4.3%，进入中断 2.0%，查找 1.7%；PPU 事件 12.9%（包含在前面经过 C++ 的各项里）。经过 C++ 的写每帧 1134 次：IME 264、IF 201、BLDALPHA 159、BLDCNT 154、IWRAM 170。

开机时 StarTeam 的语言菜单每帧 1056 万周期，只有 57% 的速度，83% 的时间在 catch-up 里，每帧有 262 次 DMA3。

### A2：IE、IF、IME 和只存值的 I/O 寄存器

JIT 的写 stub 直接完成两类 I/O 写，其余的仍然经过 C++。一类是 `Memory::io_write16()` 只存值的寄存器，比如 DMA 通道的地址和计数、串口数据。另一类是 IE、IF、IME，包括 IME 低字节的字节写（OG2 在主循环的临界区前后用 `strb` 清零、置位 IME，每帧约 260 次）：宏打开时，只要写入不会让运行停下就在 stub 里完成；宏关闭时，只有中断线和观察期都不受影响的写才在 stub 里完成。

演示动画：核 1 每帧 546 万降到 528 万，经过 C++ 的写从每帧 1134 次降到 639 次。剩下的主要是 IWRAM 代码行的写 170 次，以及行中带时刻的 BLDALPHA 和 BLDCNT 共 312 次。

### A4：IWRAM 和 EWRAM 的 LDM、STM、PUSH、POP

基址寄存器在块入口的区域提示是 IWRAM 或 EWRAM 时，块传送先检查一次范围、剩余周期和代码标记，条件满足就在块里一次读写所有的字，否则逐字调用 stub。

演示动画：核 1 每帧 528 万降到 511 万；IWRAM 的 stub 读从每帧 4863 次降到 2337 次，写从 3029 次降到 498 次。块传送里几乎没有 EWRAM，EWRAM 的 stub 读仍然是每帧 2334 次。

### A1：ROM 里的 PC 相对 LDR

宏打开时，ROM 块里 Thumb 和 ARM 的 PC 相对 `LDR` 在编译时取出常数，周期和 stub 的 ROM 路径相同；常数在区域 13（可能是 EEPROM）或第一页的 GPIO 寄存器上时仍然经过 stub。宏关闭时预取缓冲区可能在跑，也经过 stub。PC 相对 LDR 读到的常数同时当作 Rd 的区域提示，任何区域的代码都这样做，后面用 Rd 做基址的访存就不必调用 stub。

演示动画两次：核 1 每帧 513 万、506 万，主机指令每帧 251 万降到 244 万。stub 读 ROM 从每帧 1326 次降到 749 次，读 IWRAM 从 2337 次降到 363 次。

槽位 1：核 1 每帧 538 万周期，600 帧 10070ms，比原速多 24ms。这段时间里 CPU 等渲染线程 8 次，共 192.9ms；去掉等待，600 帧约 9877ms，在原速以内。所以下一步先看渲染线程。

### 渲染线程

渲染线程跟不上时，要分清是读 SD 卡换页造成的，还是我们的渲染算法比对照模拟器差；是算法差，就向对照模拟器看齐。

读卡不是原因。`tasks 8000` 统计的 8 秒里，演示动画没有缺页，渲染每帧仍然要 9.67ms；槽位 1 缺了 3 页，在核 1 上同步读卡，共 26.6ms。槽位 1 的等待来自很重的帧：渲染平均每帧 11.76ms，核 0 还有 19.5% 空闲，但是最长一帧画了 40.0ms，环形缓冲只能放下一帧多的行。

`bench` 加了渲染器的计数，在工作线程所在的核上读 `mcycle` 和 `minstret`，包括中途被中断和其他任务占去的部分。演示动画同一段 600 帧：

| 每帧 | 对照模拟器渲染 | 我们的渲染器，改动前 | 我们的渲染器，改动后 |
|---|---|---|---|
| 宿主周期 | 141.6 万 | 355 万 | 276 万 |
| 宿主指令 | 106.2 万 | 247 万 | 187 万 |
| IPC | 0.75 | 0.70 | 0.68 |

改动前 IPC 和对照模拟器差不多，指令数是对照模拟器的 2.3 倍，只是把行转换、写出去就要 66 万周期。所以是渲染算法比对照模拟器差。改动都不改变画面，PC 上用 `gbx_gba_frames` 比较了 17 组帧哈希：OG2 从开机跑 5030 帧、OG2 两个槽位各 1200 帧、另外 6 个游戏从开机各 4000 帧，经过 RGB565 的显示缓冲和 BGR555 的整帧两条路径。

- BG 的 tile 循环按 256 像素的块取 map，中间的 tile 连续读，4 色和 256 色各一份循环。
- 行缓冲直接是 RGB565：没有颜色特效的段直接查一份 RGB565 的调色板，亮度特效查一份按 EVY 算好的；带混合的段仍然用 BGR555 计算，画完再转换。整行写出去只剩一次复制。
- OBJ 用覆盖位图记哪些像素已经有前面的 OBJ，一次处理一段连续的像素；仿射 OBJ 先算好 tile 行的跨度，按位图的字处理。
- OAM 改了以后，只把属性里的 Y、形状和大小变了的 OBJ 移到新的行上，不再每行重建整张 OBJ 的行表。开机的 StarTeam 画面有 126 个 OBJ、OAM 每行都在变，以前每帧 `objects()` 要 2.9M 到 3.7M 条指令。

渲染器的代码和堆共用片内 RAM 的低段。BG 循环第一版多了约 8KB 代码，载入游戏时 `Renderer` 对象（12544 字节）放不进片内；每个 tile 只内联一份处理代码以后，三个 `paint` 合计 22.5KB，和改动前差不多，`Renderer` 留在片内。

槽位 1：渲染器每帧从 4.28M 周期、3.04M 指令降到 3.36M、2.23M。两次 600 帧 10041ms 和 10039ms，CPU 等渲染 0 次，最长的一帧 16.9ms 和 18.3ms。

#### 游戏页的状态格子

最长的一帧每次都在 14M 周期上下，各部分的指令数加起来比整帧少两三百万。临时关掉游戏页每秒重画 VFD 状态格子以后，槽位 1 最长的一帧从约 39ms 降到 17.3ms：LVGL 和呈现任务的优先级都高于渲染线程，这次刷新占了核 0。要降低这次刷新的代价，界面外观不变，可以分帧更新，按键和触摸的响应要保证。

读数每秒变一次，4 个格子一起重画，自己的绘制共约 21ms，pack 在 flash 映射的地址上。现在每个格子的底图在建页时复制到 PSRAM，VFD 字库的图集载入时复制到 PSRAM，读数变了以后格子逐个重画，两次之间至少隔 100ms。槽位 1 最长的一帧降到 20.8ms。把混合里的除以 255 换成乘法没有变化（编译器已经把除以常数编成了乘法），没有保留；任务优先级没有改。

### A7：块中间的边界进分发表

演示动画每帧约 130 次从中断返回到块中间，大多是 BIOS 里写 HALTCNT 之后的那条指令。返回走分发表，表里只有块的起点，所以每次都要回 C++ 找块内的边界。现在运行从 C++ 在块中间继续时，把这个边界也写进分发表，下一次返回到这里就不回 C++。

| | 回 C++ 继续块中间（每帧） | 核 1 每帧 | 主机指令每帧 |
|---|---|---|---|
| 演示动画，改动前两次 | 132.3 | 499 万、501 万 | 244 万 |
| 演示动画，改动后两次 | 1.6 | 489 万、479 万 | 238 万 |
| 槽位 1，改动前两次 | 63.3 | 513 万、509 万 | 244 万 |
| 槽位 1，改动后 | 1.9 | 499 万 | 235 万 |

槽位 1 的改动前那一行是渲染器改动前测的。改动后槽位 1 这次 600 帧 10046ms，CPU 等渲染 0 次。

### A6：已链接的出口直接跳到目标块

先试过另一种做法：出口先比较剩余周期，再用 lui、addi、jr 跳到目标，跳之前先数完成的指令。没有链接的出口因此要数两次指令，每个出口多出约 30 字节，核 1 反而慢了，每帧 531 万到 540 万周期，没有保留。改为照对照模拟器的设计做，不自己另想做法。

照对照模拟器做，只在宏打开时：出口调用 link stub 的那一个字就是链接槽，链接以后改成一条 `jal`，目标在第二级（PSRAM）时超出 `jal` 的范围，仍然经过 stub；剩余周期在目标块的入口检查，用完了就回 C++；C++ 进入块之前先补上取指的 catch-up，相当于从入口检查之后进入。对照模拟器目标远的时候改成 lui 加 jalr，我们的链接槽后面紧跟着 stub 要读的数据字，只有一个指令字，所以没有照搬。

|---|---|---|
| 演示动画，改动前两次 | 489 万、479 万 | 238 万 |
| 演示动画，改动后两次 | 478 万、489 万 | 233 万 |
| 槽位 1，改动前 | 499 万 | 235 万 |
| 槽位 1，改动后 | 491 万 | 230 万 |

表里槽位 1 的两行都是紧接着演示动画测的，没有重新载入游戏，块已经编译过，每帧只编译约 0.01 个块。重新载入游戏以后从头测，改动后每帧 511 万周期、238 万条主机指令，每帧编译约 2 个块。演示动画上的差别分不出来；核 1 的采样（`prof 1 8000`）里，link stub 从 3.8% 降到 1.0%。剩下每帧约 1300 次经过 stub 的链接都和第二级有关。

### 经过 stub 的 EWRAM 读

演示动画每帧 2102 次，几乎都是 Thumb。约 1200 次来自 IWRAM 里的一段 Thumb 代码，每个可见行跑一次：从变量里取出一张表的指针，按行号读出这一行的值，写到 BG 的滚动、窗口和混合寄存器。其余的在 ROM 的 Thumb 代码里。这些读的基址都是从内存读出来的指针，编译时没有区域提示。

对照模拟器的 Thumb 读，除了 ROM 代码里 PC 相对的常数，全部调用同一个辅助函数，先判断 IWRAM，再判断 EWRAM，不预测区域，指令数和我们 stub 的 EWRAM 路径差不多。对照模拟器只在 ARM 的单个读写里把 IWRAM 和 EWRAM 两条路径都内联。所以照着对照模拟器做不会变，这一项没有改动。按指令数估计，就算全部改成内联，每帧也只省约 2 万条主机指令，不到 1%（未实测）。

槽位 1 的两行都是重新载入游戏以后从头测的。演示动画没有变化，槽位 1 每帧慢了约 17 万周期，所以没有保留。从计数看有两个原因：

- 块变长以后，条件跳转后面的代码不再是新块，寄存器在入口的值不再能给它们区域提示，经过 stub 的 EWRAM 读写多了约 450 次和 270 次。对照模拟器的 Thumb 读写本来就都调用辅助函数，所以它没有这个损失。

### A3：ARM 写 VRAM，调色板和 OAM 的写

V-Rally 3 槽位 2 每帧 7012 次 VRAM 写经过 stub，全部是 ARM 指令，包括写 VRAM 的 `stmia`；调色板和 OAM 的写每帧各约 80 次，都回 C++。对照模拟器的 ARM 单个写入在块里直接写 VRAM 和 OAM 的字，调色板的字调用一个短的汇编函数，写 VRAM 的 STM 也直接写。照这个做，区域按我们的提示判断：

- ARM 的半字和字写入，基址的区域提示是 VRAM 时在块里直接写，并标记这一页给渲染器。字节写仍然经过 stub。
- ARM 的 STM 基址的区域提示是 VRAM 时，走 A4 的整段写入。
- 调色板和 OAM 的半字和字写入在 stub 里完成。对照模拟器写调色板时要转换颜色，我们的渲染器在核 0 上自己转换，所以这里只存值。

### A8：出口只计算后面会读的标志位

对照模拟器在块的出口往后看目标处最多 8 条 BIOS 或 ROM 的指令：记下每条指令读哪些标志位、一定写哪些，遇到跳转、写 R15、MRS、MSR、SWI 就停；停下时还没被写过的标志位都算会读。出口只计算会读的那些。

照这个做，只在宏打开时：静态出口的目标在 BIOS 或 ROM、而且不换状态时，出口只计算会读的标志位，其余的留在 NZCV 的寄存器里不更新。被跳过的标志位在目标的代码读到它们之前一定会被重写；在这之间进中断时它们进 SPSR，返回时原样恢复，也不会被读到。

### 载入以后的声音缓冲

载入游戏后马上就开始跑，开头编译代码时会欠载，能缓解就缓解，做不成不影响 6-4 完成。

块是执行到才编译的，开始运行之前不知道要编哪些代码；块的键里有 ROM 的等待周期，游戏开机后很快会改 WAITCNT；访存的区域提示要用块入口时寄存器的值。所以没有在开始前编译，改为声音晚一点开始播放：GBA 游戏载入以后，或者读即时存档以后继续运行时，音频队列的目标从 64ms 提高到 140ms，输出等队列里攒够 100ms 才开始播放；之后目标每帧降 1ms，约 76 帧降回 64ms，这一段模拟比原速慢约 6%。只改了 app 的节奏控制和音频任务，模拟核心不变，2X 和 GB 游戏都不受影响。

分析版，每个游戏载入后约 1.5 秒内的欠载次数（`stat` 的 `u`）：

| 游戏 | 改动前 | 改动后 |
|---|---|---|
| 黄金太阳 2 | 1 | 0、0 |
| 逆转裁判 | 2 | 0、0 |
| 马里奥高尔夫 | 4 | 1、1 |

读即时存档以后（黄金太阳 2 槽位 1、马里奥高尔夫槽位 2、逆转裁判槽位 1），改动后都没有欠载；改动前的读档没有测。OG2 载入以后的 StarTeam 语言菜单本来就只有原速的 87% 到 96%，一直在欠载，不是编译造成的，这个改动解决不了。

### 最后的测试

Sila P4，测试固件 `sila_p4-test-release`，宏关闭。全量回归先跑了前三项：

- `run_jit.py` 全部通过。
- ARM7TDMI 单步全量 2250000 条两个后端都通过，JIT 全部原生执行，和解释器没有差别。
- GBA 全部 ROM 171 个，和 6-2 宏关闭的全量比，有 3 个必过的用例不同：alyosha 的 `thumb/Push_no_regs`、`thumb/Pop_no_regs` 在 JIT 上失败，jsmolka 的 `arm/arm` 两个后端都通过，但是周期数不同。原因在 A4：寄存器列表为空时，ARMv4 只传 R15 一个字，基址仍然移动 40h（GBATEK “Strange Effects on Invalid Rlist's”），块里一次读写的路径却按 16 个字收了周期。改成按实际传的字数收。

改完只跑相关的测试：这 3 个 ROM 通过，两个后端的结果一致；`run_jit.py` 全部通过；GBA 固定回归 25 个、加 `--small-pool` 25 个、`--states` 8 个都通过；GB 固定回归加不加 `--small-pool` 都通过，两个后端结果一致。全量里剩下的 `--tiny-cache`、SM83 单步全量和 GB、GBC 全部 ROM 没有跑。

用户审阅时指出两处只在宏打开时出现的问题，都改了：

- A6 在进入块之前做的 catch-up 里，如果 DMA 改写了流水线里的指令，旧的 opcode 没有保存，块的入口检查退出以后流水线按新的内存重建。现在 catch-up 之前和 gateway 一样标记流水线，`code_written()` 会保存旧的 opcode。
- A8 往后看时，把空列表的 POP 和 LDM 当成了顺序执行的指令，可是它们会加载 R15。现在遇到它们就停下。

宏打开的测试构建，GBA 全部 ROM 171 个：每个用例的结果，以及两个后端各自的判定，都和开工时的代码用同样的构建跑出来的相同。

其他构建：7 个板子的 release 和 test-release 预设都能编译，PC 的 debug 构建和 `gbx_host_test`、`gbx_settings_test` 通过。
