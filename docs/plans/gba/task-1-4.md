# 任务 1-4：ARM7TDMI 单步测试通路

把 ARM7TDMI 的单步用例接进板上的测试通路：runner 选出用例、发送运行清单，测试固件从 SD 卡读取用例包，用 1-3 的解释器执行，在板上判定并分批回传结果，最后由 runner 保存报告。做法和 SM83 的单步测试相同，1-5 的 JIT 也走这条通路。这个任务依赖 1-3。

开工时在[任务状态](status.md)里把这个任务标为“进行中”。

## 先读

- [真机测试计划](../../hardware-testing.md)的“共用的二进制传输”“选择本次运行的测试”和“运行 SM83 单步用例”。
- 现有的 SM83 单步通路：`tests/protocol/execution.h`、`tests/device/sm83_runner.cpp`、`tests/runner/run_sm83.py`、`baseline.py`、`rejudge_sm83.py` 和 `tools/reference_identity.py`。传输、会话、批次确认、基准和离线复判都已经实现，直接复用，不另写一套。
- [GB 任务 1-2](../gb/task-1-2.md) 和 [GB 任务 1-5](../gb/task-1-5.md)。
- 1-1 生成脚本开头的用例包格式和字段说明。

## 范围

- 定义 ARM7TDMI 的执行请求和结果记录，放在 `tests/protocol/` 下，板子和 runner 两边各实现一份。默认在板上判定，通过的用例只返回状态，失败时返回实际结果；诊断模式返回所选用例的全部实际结果，由 runner 独立判定。实际结果用无损的差分编码。用例的初始状态和预期值由 runner 从原始套件读取，不回传。
- 判定比较 R0 至 R15、各模式的分组寄存器、CPSR、5 个 SPSR、流水线，以及每次总线访问的类型、宽度、地址、数据和 N/S 标记，访问的先后顺序也要一致。R15 不比较 ARM 状态下的 bit 1–0 和 Thumb 状态下的 bit 0，依据见 1-3 的开发核对结果。`cycle` 不参与判定，因为套件说明它没有正确记录；两边 `cycle` 不同的用例数记入报告，供里程碑 2 排查时序时参考。
- 1-3 列出的没有定义结果的 R15 写入和 CP14 的 MRC、MCR 照常执行，不和套件比较，直接计为通过，报告里单独列出条数。1-5 用它们检查 JIT 和解释器的结果一致。
- 测试固件按运行清单从用例包读取选中的部分，逐条执行。每条用例开始前，CPU 和总线都回到用例给定的初始状态。
- runner 读取 `refs/tests/arm7tdmi`，按文件或单个用例生成运行清单，执行前列出用例数和跳过的原因。用例 ID 由源文件名和用例序号组成。握手时核对卡上的数据清单，不对应就拒绝执行。
- 解释器的套件验证基准、只重跑失败的用例和离线复判，规则都和 SM83 相同，基准的标识覆盖 GBA 的解释器和测试代码。
- 这时测试固件还没有 GBA 的 JIT，握手里如实报告，报告中 JIT 标为 `NOT RUN`。
- 报告全量运行的耗时，分开读卡、执行和回传，供 1-5 估算两个后端的总耗时。

## 不做

- JIT，这是 1-5 的内容。
- 整机 ROM 的测试索引和执行，这些在里程碑 2。
- 自动重传、断点续跑和根据 Git diff 选择测试。

## 约束

- 写代码时就要注意性能。测试固件的执行路径决定单步全量的耗时，读取、复位、执行和判定都不能有明显低效的写法；解释器本身的性能要求见 1-3。
- 板上和电脑端遵守同一套判据。板上失败时必须返回实际结果，runner 才能报告第一处差异。
- 只维护最新的测试协议，runner 与固件不匹配时明确报错。
- 超时、板子重启、通信错误和判定失败分开报告，任何一种通信问题都不能算成通过。
- 改动共用的测试通路时，不能影响 GB 的测试。开发期间不运行 GB 和 GBC 的测试，在 1-5 收尾时检查。
- 开发期间只构建 `sila_p4-test-release` 和 PC 的 debug 版。做完一段开发才上板，只运行改动影响到的用例，全量只在完成标准要求时运行一次。

## 由你决定

消息类型和记录的字段布局、runner 的命令行，以及报告的格式。字段布局写在协议头文件的注释里，不写进文档。

## 完成标准

- 在 Sila P4 上用解释器跑完全部单步用例，除了 1-3 列出、用户确认排除的用例以外全部通过，报告中 JIT 标为 `NOT RUN`。如果 1-3 的实现有错，就在这个任务里修。
- 确认判定真的能发现错误：临时改错一条指令的实现，runner 能指出受影响的用例和第一处差异，然后改回去。这一步不留下测试代码。
- 只重跑失败用例的功能可用，数据清单不对应时 runner 拒绝执行。
- 报告给出全量运行的耗时和各部分的比例。

## 收尾

- 满足全部完成标准以后，在[任务状态](status.md)里把这个任务标为“已完成”。
- 在真机测试计划中写明 ARM7TDMI 单步用例的运行方法和判据，测试结果保存在运行报告中。
- 向用户汇报运行结果、总耗时和遇到的问题。

## 实现与验证结果

板上的 ARM7TDMI 单步通路已经接通。协议见 `tests/protocol/arm7_execution.h`，用法和判据见[运行 ARM7TDMI 单步用例](../../hardware-testing.md#运行-arm7tdmi-单步用例)。下面的结果都来自 Sila P4（ESP32-P4 v1.3，360MHz），ESP-IDF v6.1，`sila_p4-test-release`，固件是 1-3 完成时的代码加上这个任务的改动。

全量运行的 2,250,000 条用例全部通过，其中 6,206 条没有定义结果的 R15 写入和 1,500 条 CP14 的 MRC、MCR 照常执行，没有和套件比较。JIT 标为 `NOT RUN`。376,292 条用例的 `cycle` 和套件不同。1-3 在 PC 上数出的是 377,792 条，多出的 1,500 条正好是 CP14 的条数：报告只在总线访问的条数和用例相同时比较 `cycle`，CP14 按 GBATEK 执行以后访问条数和用例不同，所以不再计入。

| 耗时 | 秒 |
|---|---|
| 墙钟，runner 计时，包括连接前的核对 | 53.6 |
| 板上合计 | 50.5 |
| 执行，包括解码、复位、判定和编码结果 | 19.9 |
| 等待读卡 | 26.3 |
| 回传，包括等 runner 确认 | 4.3 |
| 读卡任务读 SD 卡，和上面三项同时进行 | 45.9 |

读卡任务在另一个核上读完 497MB 的用例包，约 10.8MB/s，执行和回传的同时它也在读，所以全量的耗时由读卡决定。三项不并行的话，相加约 70 秒，这个数没有实测。回传的结果一共只有 31,467 字节，回传时间主要花在每个请求结束时等 runner 确认，45 个请求每个约 0.1 秒。1-5 估算时，执行时间要加上 JIT 的那一份：两个后端的执行时间加起来不超过读卡时间，总耗时就还在 50 秒左右；超过以后，总耗时随执行时间增长。

判定能发现错误：临时把 BIC 结果的 bit 31 取反（ARM 和 Thumb 共用这段代码），运行 `arm_data_proc_immediate` 和 `thumb_data_proc`，有 4,614 条失败，分别是 1,512 条和 3,102 条，每条都报告了第一处差异，比如 `v1/arm_data_proc_immediate.json.bin::44` 的 `final.r0` 预期 `6e0a649d`，实际 `ee0a649d`。离线复判这份报告，结果是 `PARTIAL`：4,614 条失败，另外 95,386 条通过的用例没有保存实际结果，标为 `UNVERIFIED`。改回以后用 `--rerun-failed` 只重跑这 4,614 条，全部通过。

第一次只重跑失败用例时超时了。当时按序号选择的用例逐条读取，每读一条都要先回到偏移表；FATFS 没有打开 fast seek，往回 seek 要从文件开头沿簇链走，一个请求有几千次。现在按序号选择的用例也由读卡任务从第一条选中的记录顺序读到最后一条，跳过没有选中的，改了以后这 4,614 条用 2.8 秒跑完。

runner 在每个文件发出请求之前，把选中的用例重新编码，和本地的 `cases.bin` 逐字节比较，文件序号也按 `cases.bin` 的索引对应，这样本地的源文件改动、删除或改名时不会把别的用例的结果记到所选用例名下。比较全部 2,250,000 条在 PC（macOS，Python 3.12）上要 8.2 秒；全量运行时它在后台线程里和板上执行同时进行，墙钟是 53.6 秒，加这一步之前是 53.3 秒。临时改掉一条预期值，或者让一个文件对应到别的文件的记录，都在发送请求前报错。

另外检查了：本地清单和卡上的不一致时，runner 报错，没有发送用例。诊断模式下运行 `arm_mcr_mrc`、`arm_ldm_stm` 和 `thumb_bx` 各自的前 2,000 条，由 runner 独立判定，全部通过，其中 63 条 CP14 没有比较；离线复判这份报告也是 `PASS`，对复判生成的报告再复判一次，结果相同。

和用户商定，GB 和 GBA 的用例包都不在板上校验。板子开机只计算清单的 SHA-256，打开用例包时检查头部和索引；SM83 原来开机时对整个用例包算 SHA-256，这一步去掉了。

共用的测试通路有这些改动：

- 单步 runner 的选择、传输、报告和离线复判移到 `tests/runner/single_step.py`，SM83 的 runner 改成在它上面实现，命令行和报告字段不变。
- 基准标识分成 SM83 和 ARM7TDMI 两份，各自不包括另一个系统的核心代码和 runner，改一个系统不会让另一个系统的基准失效。
- HELLO 增加了 GBA 的清单校验值和 ARM7TDMI 的标识，执行协议升到 v6。v5 的报告不能再复判，也不能作为基准。

按约束，开发期间没有在板上运行 GB 的测试。SM83 的 runner 只用 `--list` 和构造的结果批次检查过选择、判定、复判和基准，板上的检查留到 1-5 收尾。

`sila_p4-test-release` 和 PC 的 debug 版都编译通过，没有警告。
