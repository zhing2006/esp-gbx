# 任务 6-1：两个后端的性能优化

这是[路线图](../../roadmap.md#gba) GBA 段里程碑 6 的第一个任务：用即时存档回到游戏中负载重的位置，测出解释器和 JIT 的瓶颈，逐项优化，只保留正确而且有实测收益的改动。双核分工和 2X 在 6-2。这个任务依赖 5-3。

## 先读

- 路线图 GBA 段开头的几段和里程碑 6，[真机测试计划](../../hardware-testing.md)的“每个任务的双后端优化”和“性能分析版固件”，[调试设计](../../debug-design.md)的“串口控制台”和“详细性能诊断”。
- [架构](../../architecture.md)的“ARM7TDMI JIT”和“JIT 后端”：块间连接、分发表、成批运行、两级代码缓存和 gateway 的 stub 的现有做法。
- GB 段的 [3-4](../gb/task-3-4.md) 和 [5-2](../gb/task-5-2.md)，以及 5-3 列出的剩余瓶颈。

## 范围

- 先确定测量的场景：用户提供游戏和即时存档，选几个负载重的位置，覆盖 CPU 重、渲染重和 DMA 或声音重的情况。测量用 `sila_p4-profile` 的串口控制台载入游戏和槽位，统计固定的时长，记录 `SPEED`、模拟任务的比例、两个核的 `IDLE`、`FRAME` p95 和平均值、欠载次数，以及 JIT 的编译、失效、回退次数和代码池用量。分析热点时用 `sila_p4-test-profile` 和 `tools/profile_report.py`。场景选定以后、开始优化之前，按优化前的速度把场景分成轻中负载和重负载，和用户确认，路线图里程碑 6 的速度目标按这个划分判定。
- JIT 的候选方向如下，每一项先测出它针对的开销，再决定做不做：
  - 预取缓冲借给生成的代码时，ROM 里的代码读取 ROM 的数据，包括 Thumb 的 PC 相对读取，都经过 C++ 的慢路径；先测出它们在执行中的比例。
  - LDM、STM、PUSH 和 POP 的批量访问。
  - 在下一个设备事件之前合并取指计时，减少逐条检查期限和累加周期的指令。合并的区间不能越过最早的设备事件，也不能漏算或重复计算等待周期和预取。
  - ROM 和 IWRAM、EWRAM 之间的 refill，以及切换 ARM 和 Thumb 状态的 refill，都在 C++ 里计时。
- 解释器同样按实测的瓶颈优化，比如解码、总线分派和等待周期的计算。
- 在 Sila P4 上用同样的游戏和场景测出对照模拟器的速度，作为已知的性能参考线，目标是超过它。
- 降低精度是最后的手段：保持精度的优化都做完、仍然达不到路线图的速度目标时才做，比如把逐条指令检查设备事件改成一段代码检查一次。降低精度的做法用一个编译宏控制，默认打开；游戏出现兼容问题时关掉它做对比。宏关闭时两个后端的结果一致、测试照常通过；宏打开时哪些测试的结果会变，做之前列出来和用户确认。
- 每一项改动都分开测量编译、代码发布和缓存命中以后的执行开销，同时记录代码体积和片内 RAM 的用量。Zba、Zbb、Zbs 相关的改动另外在 Sila P4X 上测。

## 不做

- 双核负载的重新分配和 2X，这些在 6-2。
- 在保持精度的优化做完之前降低精度，以及不用编译宏控制的降低精度的改动。
- 只为凑数而做的改动。没有实测收益的尝试撤销，在报告里说明。

## 约束

- 写代码时就要注意性能，解释器和 JIT 都一样。在满足功能的前提下选性能最好的实现，不写明显低效的代码，也不留给以后的优化任务再改。
- 每项优化都要通过相关的测试：受影响的单步用例文件、相关模块的 ROM、`--small-pool`、很小的分页缓存，以及 `run_jit.py` 里对应的检查。测试要能发现这项优化可能引入的错误，比如自修改代码的失效、标志位在异常时的值、合并计时越过事件。
- 比较时保持板型、芯片修订、主频、构建配置、存档位置、输入和时长一致，一次只改一个因素。改变热代码的布局时核对 map 中的地址，不把布局变化带来的差别记成优化的收益。
- 改到两个系统共用的后端或热代码时，GB 不能变慢。开发期间不运行 GB 和 GBC 的测试，测试和速度比较在 6-2 做。
- 开发期间只构建要刷进板子的固件和 PC 的 debug 版。每项优化做完才上板测量和运行受影响的测试，测量只做得到数据所需的轮数，全量回归在 6-2 做。

用户在 Sila P4（ESP32-P4 v1.3、360MHz）上用 `sila_p4-profile` 试玩，存下了下面这些即时存档。它们也是测量的场景。

|---|---|---|---|

| V-Rally 3 欧版 | 2 | 选车画面 | 再按一次 A 进入选赛道，存档灯亮起，游戏卡住，整个界面定时闪烁 |

## 记录

### 测量方法

- 板子是 Sila P4（ESP32-P4 v1.3、360MHz），固件是 `sila_p4-profile`，后端是 JIT。串口控制台用 `load` 载入游戏，`slot <n>` 载入槽位，等 3 秒以后统计 10 秒。`stat` 的 `render` 行给出渲染器每帧的耗时，`tasks` 给出各任务占核的比例，`prof 0` 给出核 0 的热点。
- PC 上的 `gbx_gba_frames`（`host/tools/gba_frames.cpp`）从槽位文件运行 300 帧，打印每帧的 hash 和用到的 PPU 功能。改渲染器的前后两次输出必须相同；这只用来比较两次构建，不保存成标准答案。
- 槽位文件用 `file` 命令从卡上取回。开发者本地的测量脚本和取回的槽位放在 `build/m6/`，不入库。
- `stat` 的 `SPEED` 是相对 1X 的速度，在 2X 档下也一样。

### 场景的轻重和判据

和用户确认：

- 场景的轻重：Mother 3 是轻负载，马里奥高尔夫是中负载，黄金太阳 2 和 V-Rally 3 是重负载。
- 宏打开时变化的测试清单（见“宏打开时结果会变的测试”）可以接受。主固件默认打开宏，测试固件默认关闭，验收和回归都用测试固件。
- “稳定”不看 `FRAME`，看画面交付间隔的 p95 不超过 25ms，路线图和[调试设计](../../debug-design.md)都按这个写。
- `FRAME` 是模拟一帧的耗时，从开始模拟到模拟的 PPU 结束这一帧，和 `EMU` 计数的帧相同，不包括另一个核上画完这一帧和混音的时间（用户提议）。本文记录的 `FRAME` 都是这个定义。
- V-Rally 3 的 JIT 目标改成稳定原速，作为例外。

### 对照模拟器的速度

对照模拟器（Sila P4 版，PIE 仿射渲染打开，L2 缓存 256KB）放在仓库外构建。它没有即时存档，所以每个场景写成从开机起的按键脚本，到和我们的场景相同的画面以后统计 600 帧，最后一帧和我们的场景核对过。它在核 0 上一个核跑 CPU 和渲染，没有显示和声音：

| 场景 | 对照模拟器 | 其中渲染（每帧） | 我们的 JIT，1X，当时 |
|---|---|---|---|
| V-Rally 3，赛道上 | 138.1% | 4.8ms | 约 82% |
| 黄金太阳 2，按 A 开始以后 | 129.2% | 4.0ms | 约 82% |
| 马里奥高尔夫，球场上 | 108.4% | 6.3ms | 85% |
| Mother 3，输入名字 | 284.9% | 2.7ms | 99.6% |

V-Rally 3 上对照模拟器模拟一帧的 CPU 和设备约 7.3ms，渲染 4.8ms；我们当时的核 1 一帧约 20ms，核 0 渲染约 13ms，两部分都慢 2.7 倍左右。

### V-Rally 3 的瓶颈

- 每帧约 12.6 万条 GBA 指令，其中 11.9 万条在 IWRAM。两个贴纹理的内循环（0x03003B88 起 21 条、0x03004028 起 24 条，每次从 EWRAM 的纹理读 4 个字节，写 VRAM 一个字）约占 GBA 时间的 37%。核 1 一帧约 680 万个周期，平均每条 GBA 指令约 54 个周期，对照模拟器约 21 个（含设备）。
- 核 1 每秒 3.6 亿个周期里，L1 指令缓存缺失等待约 7300 万，数据缓存缺失约 4100 万，两个核争用数据缓存约 3900 万，IPC 0.48。核 0 渲染和呈现时，核 1 慢约 19%，因为两个核共用 L1 数据缓存、L2 缓存和 PSRAM。
- 访存 stub 里读 EWRAM 平均约 18 个周期，读 VRAM 约 47 个，合计只占核 1 的 4% 左右；VRAM 和 EWRAM 都在 PSRAM，stub 的时间主要不是花在读数据上。
- 热的代码超过 16KB 的指令缓存，在片内也一样要从下一级取。代码池换成 32KB 时速度几乎不变（81.3%）。

### 渲染器和核 0

都不改变画面，PC 上用 `gbx_gba_frames` 比较了改动前后的帧 hash。

| 改动 | 场景 | 改动前 | 改动后 |
|---|---|---|---|
| 调色板查表，OBJ 先按 OAM 建好每行的列表，仿射 BG 和 OBJ 按 PA、PC 递增坐标 | 马里奥高尔夫槽位 2，渲染每帧 | 18.44ms | 15.06ms |
| `compose` 按窗口值相同的一段像素处理，每行先画进片内的行缓冲 | 同上 | 15.06ms | 13.04ms，屏幕每秒显示 24.8 帧 |
| 2X 没有绘制的帧不交给显示，调色板的页只更新变化了的颜色，BG2 的位图不旋转、不缩放时按行直接取 | V-Rally 3 赛道上，2X 档 | 66.9% | 74.1% |
| 直接按屏幕的 RGB565 写显示的缓冲，呈现任务不再转换颜色 | V-Rally 3 赛道上，1X | 73.7% | 77.6%，呈现任务占核 0 从 13.5% 降到 1.7% |
| 不需要颜色特效的行直接从后往前画 | 马里奥高尔夫，2X 档 | 106.2% | 128.5% |
| 调色板按 16 色一页交给渲染器（V-Rally 3 几乎每两行改一次调色板） | V-Rally 3 赛道上，1X | 87.9% | 93.4% |
| 每行只写一次 PSRAM，`frame_` 要读时再从显示的缓冲转回 BGR555 | V-Rally 3 赛道上，1X | 93.4% | 99.8% |

GBA 的工作线程优先级从 5 降到 1，低于呈现任务、LVGL、ROM 缓存的读卡任务和存档、槽位、游戏列表的任务。它的队列能放下一帧以上的行，所以这些任务运行的几毫秒里，CPU 所在的核不用等。GB 的工作线程仍然是 5，因为它的队列只有 16 行，约 2ms。改完以后在各个槽位上按 A，任务看门狗都没有再报告：

| 场景 | `SPEED` | 产出 / 显示（帧每秒） | 核 0 的渲染 / 呈现 | 核 1 空闲 |
|---|---|---|---|---|
| 马里奥高尔夫槽位 2，选项菜单 | 75.2% | 45.3 / 44.8 | 73.0% / 18.2% | 0% |
| V-Rally 3 槽位 2，选赛道 | 79.8% | 47.4 / 47.0 | 73.4% / 19.0% | 44% |
| 黄金太阳 2 槽位 1，按 A 以后 | 71.2% | 42.9 / 42.8 | 76.9% / 14.9% | 6% |
| Mother 3 槽位 1，按 A 以后 | 100.4% | 59.5 / 57.5 | 68.2% / 19.8% | 30% |

### 片内内存落到 LP SRAM

`allocate_internal()` 在 L2MEM 不够时会落进堆里的 LP SRAM，HP 核访问 LP SRAM 很慢，见 [ESP32-P4 的性能特性](../../esp32p4-performance.md)。分发表所在的 `Tables` 落在那里时，查一次分发表要约 770 个周期。`allocate_internal()` 改为要求 `MALLOC_CAP_DMA`，只用 L2MEM，不够时再用 PSRAM。分发表在 PSRAM 时查一次约 75 个周期，`dispatch` 从核 1 的 11% 降到 2.9%，V-Rally 3 赛道上从 77% 升到 83.9%。

### JIT

| 改动 | 场景 | 改动前 | 改动后 |
|---|---|---|---|
| 代码池淘汰的 BIOS、ROM 块留在第二级执行 | V-Rally 3 赛道上 | 52% | 60% |
| RAM 块的副本也在第二级原地执行，和代码池里的块一样监视写入 | 同上 | 60% | 66.9% |
| RAM 块的记录从 512 个改成 4096 个，第二级的块按入口次数回到代码池，每帧最多 16 个 | 黄金太阳 2 | 81.7% | 86.5% |
| 回到 C++ 的三处：块计数用完以后当作块的开头查找；只有 ROM 里的代码要求 N、S 一致；两条路径 S 不同的出口也能链接 | 马里奥高尔夫 | 85% | 89%–90% |
| 预测在 IWRAM 和 EWRAM 的访存内联：按基址寄存器在块入口的值预测区域 | V-Rally 3，2X 档 | 101.8% | 106.0% |
| 块跳回自己的入口时直接跳转 | V-Rally 3，每帧经过 link stub | 约 6650 次 | 约 3950 次 |
| 编译时跟踪寄存器指向的区域 | V-Rally 3，每帧经过访存 stub | 约 2.6 万次 | 约 1.7 万次 |
| RAM 块的记录按代码所在的 256 字节分桶 | 黄金太阳 2，2X 档 | 168.7%、165.2% | 174.7% |
| 2X 档不把 FIFO 的采样交给混音器，回到 1X 时补交当前的采样 | 黄金太阳 2，2X 档 | 161.4% | 175.2% |

前两行在 2X 档测，`SPEED` 仍是相对 1X 的速度。“回到 C++ 的三处”在黄金太阳 2 上从 86.5% 到 89%–90%，V-Rally 3 从 81%–84% 到 83%–84%。自循环的直接跳转在 2X 档的四个场景上都在波动以内。

### 降低精度：`GBX_GBA_RELAXED_TIMING`

宏打开时（正式固件的默认），ROM 取指令不模拟预取缓冲：预取打开时每次 1 个周期，相当于缓冲总是来得及；预取关闭时按 S 或 N 访问计时；ROM 块跳到自己的 ROM 区域、IWRAM 或 EWRAM 时，refill 在原生代码里按 N 加 S 计时。先在 JIT 上做：

| 场景 | 之前 | 之后（1X） | 之后（2X 档） |
|---|---|---|---|
| V-Rally 3，赛道上 | 83%–84% | 88.0% | 89.0% |
| 黄金太阳 2，按 A 开始以后 | 89%–90% | 100.3%，核 1 空闲 12% | 118.1% |
| 马里奥高尔夫，球场上 | 89%–90% | 100.2%，核 1 空闲 23% | 106.2% |
| Mother 3，输入名字 | 99.6% | 100.2% | 193.2% |

后来解释器和 JIT 改用同一个宏，解释器从 ROM 取指令也用同样的规则。性能分析版，解释器 1X：马里奥高尔夫 87.5% 到 91.6%，黄金太阳 2 56.1% 到 56.5%，V-Rally 3 36.1% 到 36.6%，Mother 3 97.4% 到 97.8%。

JIT 的等待循环整圈跳过也只在宏打开时编译，因为宏关闭时 ROM 取指令按预取缓冲计时，每圈的周期不一定固定。马里奥高尔夫约 69%、黄金太阳 2 约 42% 的时间在一个 4 到 5 条 Thumb 指令的循环里，等 VBlank 中断处理程序置位一个标志。连续两圈的周期数相同时，把剩余周期里能完整走完的圈数一次跳过，事件仍然落在同一条指令的边界上：

| 场景 | 之前 | 之后 |
|---|---|---|
| 马里奥高尔夫，1X | 100.2%，核 1 空闲 23% | 100.2%，核 1 空闲 56% |
| 黄金太阳 2，1X | 100.3%，核 1 空闲 12% | 100.2%，核 1 空闲 39% |
| 马里奥高尔夫，2X 档 | 139.6% | 197.2% |
| 黄金太阳 2，2X 档 | 126.1% | 157.8% |
| V-Rally 3，1X | 99.8% | 100.5% |
| V-Rally 3，2X 档 | | 103.4% |
| Mother 3，2X 档 | 197.7% | 199% |

1X 的几行是只比较一圈就跳过的第一版测的，2X 档是连续两圈相同才跳过的版本。

### 宏打开时结果会变的测试

宏关闭时（`sila_p4-test-release`），GBA 的固定回归、`--small-pool`、`--states` 和全量（`--all`）在两个后端上都通过：全量 153 个通过，另有 17 个“仅报告”的失败和 1 个人工检查，和宏的改动之前相同。

只有 JIT 放宽时，宏打开的全量里解释器全部和宏关闭时相同，变的都是 JIT：

- 宏关闭时通过、打开后 JIT 不满足套件判据的，74 个：alyosha 的 `Bus/DMA_CPU_Bus_Interaction`，`DMA` 6 个（`DMA_ROM_Fixed`、`DMA_pause_timing` 的 5 个），`Interactions` 8 个（`Halt_DMA_IRQ`、`Halt_IRQ`、`Internal_Cycle_DMA_*` 6 个），`Serial` 7 个（`serial_time` 系列），`arm/Coprocessor_14`，`fifo_dma` 5 个（`fifo_2` 至 `fifo_5`、`fifo_dma_disable_4`），`irq` 15 个（`BL_IRQ` 4 个、`IE`、`IF`、`IF_Timer`、`IRQ_sub` 4 个、`halt_pc` 4 个），`ppu` 的 `start_up` 4 个，`prefetcher` 17 个（全部），`psr`，`thumb` 的 `Pop_no_regs` 和 `Push_no_regs`，`timer` 和 `timer_disable`，`timing` 4 个（`cpy_data_bios`、`dma_from_bios`、`prefetch_enable` 两个）；nba-hw-test 的 `dma/force-nseq-access`。其中 `fifo_dma_disable_4` 是“仅报告”。
- 两个后端都满足判据，但是结束时的状态不同（多是模拟时间），42 个：alyosha 的 `Bus` 2 个、`DMA` 3 个、`Interactions` 6 个、`STM_ALU_IMM`、`Serial` 2 个、`fifo_dma_disable_3` 和 `_5`、`irq/BL_1`、`memory` 的两个 8 位写入、`thumb/blx`、`thumb/cpy`、`timing/dma_long`，GBX 自写的 `rom32_dma`、`rtc` 和 6 个存档芯片的 ROM，nba-hw-test 的 `bus/128kb-boundary`、`dma/latch`、`dma/start-delay`、`haltcnt`、`ppu` 5 个和 `timer` 3 个。其中 3 个是“仅报告”。
- 本来就失败的 17 个“仅报告”仍然失败，其中 11 个两个后端结束时的状态也不同了。

解释器也放宽以后：

- 解释器有 59 个不再满足判据，全部在 JIT 的 74 个里：74 个中除了 `DMA_ROM_Fixed`、`DMA_pause_timing` 的 5 个、`Halt_DMA_IRQ`、`Halt_IRQ`、`Internal_Cycle_DMA_IRQ_br`、`Internal_Cycle_DMA_IRQ_br1_IWRAM`、`Internal_Cycle_DMA_IRQ_nop_IWRAM`、`Internal_Cycle_DMA_MUL_IRQ`、`timing/dma_from_bios`、`timing/prefetch_enable_2` 和 nba-hw-test 的 `dma/force-nseq-access` 这 15 个以外的都是。
- JIT 不满足判据的仍然是那 74 个。
- 两个后端都满足判据、但结束时的状态不同的，从 42 个降到 32 个，多是模拟时间。
- “仅报告”的用例里，`STM_ALU_IMM` 两个后端的状态不同了，`fifo_dma_disable_4` 不满足判据。

这些测试量的都是周期：预取缓冲、中断和 DMA 的时刻、定时器读数。宏打开时不模拟预取缓冲，ROM 里代码的周期就和硬件不同。6-3 在宏里加了几项，之后的变化见 [6-3](task-6-3.md) 的“板上的测试”。

### 解释器

PC 上 6 个槽位各 600 帧，每帧的 hash 和结束时的 CPU、时间、各块内存都和改动前的解释器相同；宏打开和关闭两种构建都比较了。

- 等待循环整圈跳过，规则和 JIT 共用（`arm7_spin.h`）。解释器连预取缓冲的状态一起比较，所以这一项不降低精度，不受宏控制。
- 按表分派到专用的处理函数：ARM 按位 27–20 和 7–4、Thumb 按位 15–6 查表，处理函数按决定操作的位特化；不常走的部分放在单独的函数里。
- 只有取指令一个总线周期的指令最后取指令，处理函数不建栈帧；ADD、SUB 等直接算 C 和 V，不设 C 的运算不算移位器的进位；单个读写和 LDM、STM 在 IWRAM、EWRAM 里时有快路径。
- P4 没有 Zbb，`std::countr_zero()` 和 `std::popcount()` 都编译成 libgcc 的函数调用，所以换成了查表和移位相加（`components/core/src/gba/bits.h`），两个后端共用。

| 场景 | 开工时 | 等待循环跳过 | 按表分派 | 宏打开、不建栈帧和快路径 |
|---|---|---|---|---|
| 马里奥高尔夫，球场上 | 28.4% | 70.3% | 87.4% | 100.1% |
| 黄金太阳 2，按 A 开始以后 | 24.2% | 37.8% | 55.7% | 66.8% |
| V-Rally 3，赛道上 | 22.8% | 25.1% | 36.8% | 41.4% |
| Mother 3，输入名字 | 52.8% | 55.1% | 98.0% | 98.7% |

GBA 的执行核心和 JIT 的代码池都在片内 RAM 的高段：执行核心的代码多了，JIT 预留的连续空间就可能分不出来。执行核心到约 127KB 时，JIT 的预留失败，载入游戏时报“the JIT cannot start”。收尾时执行核心约 117KB。

### 试过、没有保留的

- L2 缓存改成 256KB、代码池改成 64KB：V-Rally 3 75.5%，只多了 2 个点左右。
- 块中间的边界也放进分发表，让中断返回不回 C++：V-Rally 3 回到 C++ 的次数翻倍，速度降到 70%，原因没有查清。
- 宏打开时只在写入前后的边界检查停止：V-Rally 3 到 89.6%，但是马里奥高尔夫降到 27%。游戏在 IME 为 0 时进入 BIOS 的 HALT，IE&IF 一直有位，HALT 一进入就醒，每秒回到 C++ 约 7.5 万次。中断晚到几条指令就改变了游戏的流程。
- 改写代码以后，旧版本从第二级找回时直接搬回代码池：黄金太阳 2 的 2X 从 126.1% 降到 118.4%，马里奥高尔夫从 139.6% 降到 134.5%，V-Rally 3 从 99.8% 降到 97.9%。
- 把 VRAM（96KB）放进片内 RAM。代码池减到 96KB 或 112KB 时，片内仍然没有连续的 96KB，马里奥高尔夫 2X 档降到 83%。像对照模拟器那样把生成的代码放在 PSRAM、代码池减到 48KB 时，VRAM 分到了片内，但是 2X 档马里奥高尔夫 192.9% 降到 136.3%，黄金太阳 2 154.6% 降到 136.6%，V-Rally 3 106.0% 降到 100.7%，Mother 3 197.7% 降到 195.4%。
- 只为测量：映射到 GBA 内存的块在指令之间不检查剩余周期。V-Rally 3 一帧从 16.16ms 降到 13.93ms，约 1.16 倍，离 1.5 倍还差得远；马里奥高尔夫 2X 档降到 25.1%，黄金太阳 2 `FRAME` 平均只有 3.55ms，游戏的运行变了。
- 解释器在分派前统一取指令：四个场景都慢了约 10%，原因没有查清。
- 解释器的处理函数结尾直接跳进下一个处理函数（尾调用）：慢了 10% 到 17%，可能的原因见 [ESP32-P4 的性能特性](../../esp32p4-performance.md)。
- 解释器的 Thumb 处理函数内联 IWRAM 取指令：黄金太阳 2 没有变快，代码多 3.4KB。宏打开时再内联 ROM 取指令：执行核心涨到约 127KB，JIT 预留不到代码池，解释器只快了一点（马里奥高尔夫 93.2%，Mother 3 98.0%）。
- 解释器的单个读写快路径再加上读 ROM 和写调色板、VRAM、OAM：V-Rally 3 从 41.4% 到 42.2%，但是 Mother 3 两次都是约 90%，执行核心涨到 122.5KB。
- 解释器的 ARM 条件不用分支判断，按条件选出跳过指令的处理函数：Mother 3 `FRAME` 平均从 15.9ms 降到 15.4ms，但 V-Rally 3 和黄金太阳 2 慢了 3% 到 5%。现在只有条件不是 AL 时才不用分支。

### Review 以后的修正

用户静态审核了开工以来的改动，提出 6 个问题，都成立，都修好了：

- 解释器的等待循环可能把离开循环、写了内存、再从另一条跳转回到开头的路径当成等待循环跳过，宏打开和关闭都受影响。
- 单步入口 `arm7_step_mapped()` 也会快进，lockstep 的指令计数会对不上。
- 2X 档的 FIFO 回到 1X 后，混音器可能一直输出旧值。
- 暂停以后继续或读档以后，第一帧的颜色是错的。
- JIT 的自循环绕过了不连接的观察模式。
- 上一项的清空如果发生在观察器自己的回调里，`run()` 可能把链接写进已经回收的代码。

PC 上宏打开和关闭两种构建，6 个槽位各跑 600 帧，结束时的状态和每帧的哈希都和修改之前相同。修正以后在性能分析版上复测的结果就是“结果”里的表，和修正之前的差别都在测量的波动以内。

### 最后的测试

Sila P4（ESP32-P4 v1.3、360MHz），测试固件 `sila_p4-test-release`（宏关闭）：

- GBA 固定回归 25 项、`--small-pool` 25 项、`--states` 8 项都通过，两个后端一致。
- `gbx` 套件 31 项通过，包括 32MB 的 `rom32_cpu` 和 `rom32_dma`。
- 固定回归的 lockstep（不连接和 `--linked`）各有 20 项通过。另外 5 个 GBX 的 PPU 场景，在 48000Hz 的 PCM 下解释器一侧报 39340 帧 PCM 丢失，但两个后端没有出现不同；PPU 模块的 55 个 ROM 用 `--rate 0` 跑 lockstep，45 项通过，其余 9 项是原本就只记入报告的失败，1 项要人工判断，都没有出现不同。lockstep 带 PCM 时丢帧的原因没有查。
- 解释器按表分派改完以后跑过 ARM7TDMI 单步全量（225 万条，解释器全部通过，JIT 和解释器没有不同）和宏关闭时的 GBA 全量（结果和改之前相同）。
- 全部板子的正式固件和测试固件、PC 的 debug 构建都通过，没有新的警告。

Review 的问题修完以后只跑相关的测试，里程碑 6 就此完成，不跑全量回归（两种宏设置的 GBA 全量、ARM7TDMI 单步全量、GB 和 GBC 全量）。Sila P4X 上的测试不属于里程碑 6，以后换了板子再测。
